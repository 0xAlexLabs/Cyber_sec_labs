<a id="goal"></a>
## 🎯 Цель
Функционал смены email защищён CSRF-токеном, но токены **не интегрированы в систему управления сессиями** сайта. Задача:

1. Использовать exploit server для размещения HTML-страницы с CSRF-атакой.
2. Изменить email жертвы через CSRF.

Для проработки атаки даны два аккаунта: `wiener:peter` и `carlos:montoya`.

<a id="theory"></a>
## 🧠 Краткая теория
CSRF (Cross-Site Request Forgery) — атака, при которой злоумышленник заставляет браузер жертвы выполнить нежелательное действие на уязвимом сайте, где жертва аутентифицирована.

CSRF-токен эффективен только тогда, когда он **привязан к сессии жертвы**. Частая ошибка реализации — глобальный пул токенов: сервер выдает токены, не привязанные ни к чему (или хранит их глобально), и любой валидный токен, выданный **любому** пользователю, принимается для **любой** сессии. Атакующий просто логинится под своим аккаунтом, получает собственный валидный CSRF-токен и жестко вшивает его в эксплойт — сервер не может определить, что токен выдан другому пользователю.

<a id="idea"></a>
## 🧩 Ключевая идея
Получить валидный CSRF-токен из **собственного** аккаунта и встроить его в эксплойт.

- Атакующий может залогиниться на целевом сайте как обычный пользователь и получить настоящий CSRF-токен.
- Поскольку токены не привязаны к сессиям, сервер жертвы примет токен атакующего.
- Токен жестко зашивается в HTML эксплойта — не нужно похищать токен жертвы.
- Автосабмит формы через JavaScript делает атаку незаметной для жертвы.

<a id="attack-scheme"></a>
## 🗺 Схема атаки
1. **Разведка:** Перехват `POST /my-account/change-email` от аккаунта №1 (wiener), фиксация csrf-токена.
2. **Проверка:** Логин под аккаунтом №2 (carlos) и подстановка токена wiener'а → принято → токен не привязан к сессии.
3. **Эксплойт:** HTML-форма POST на `/my-account/change-email` с жестко зашитым валидным csrf-токеном.
4. **Проверка:** View exploit на себе → email изменён.
5. **Доставка:** Deliver to victim → лаба решена.

⚠️ Важно: токены **одноразовые**, поэтому в эксплойт на момент доставки должен быть вшит свежий, неиспользованный токен.

<a id="step1"></a>
## 🔍 Шаг 1 — Анализ легитимного запроса
Авторизовался под `wiener:peter` в браузере Burp, отправил форму «Update email» и перехватил результирующий запрос в Burp Proxy. Записал значение `csrf`, после чего **сбросил (drop)** запрос — не «сжигая» токен.

```http
POST /my-account/change-email HTTP/1.1
Host: LAB-ID.web-security-academy.net
Cookie: session=SESSION_WIENER
Content-Type: application/x-www-form-urlencoded

email=test@test.com&csrf=CSRF_TOKEN_WIENER
```

<a id="step2"></a>
## 🔍 Шаг 2 — Тест токена между сессиями
Открыл приватное/инкогнито окно браузера, залогинился под вторым аккаунтом `carlos:montoya` и отправил его запрос смены email в Burp Repeater.

В Repeater **заменил csrf-токен carlos на токен wiener'а** (`CSRF_TOKEN_WIENER`) и отправил запрос.

<a id="step3"></a>
## 🔍 Шаг 3 — Подтверждение: токен не привязан к сессии
**Результат:** запрос **принят** — сессия carlos успешно использовала CSRF-токен wiener'а.

*Вывод: токены хранятся в глобальном пуле, а не привязаны к сессии пользователя. Любой валидный токен подходит любому пользователю — атакующий может просто вшить свой токен в эксплойт.*

<a id="step4"></a>
## 🔍 Шаг 4 — Формирование CSRF-эксплойта
Собрал эксплойт со свежим (неиспользованным) CSRF-токеном, полученным из собственного аккаунта атакующего, поскольку токены одноразовые:

```html
<form method="POST" action="https://LAB-ID.web-security-academy.net/my-account/change-email">
    <input type="hidden" name="csrf" value="CSRF_TOKEN_WIENER">
    <input type="hidden" name="email" value="attacker@web-security-academy.net">
</form>
<script>
    document.forms[0].submit();
</script>
```

*Важно: инпут `csrf` содержит собственный валидный токен атакующего — сервер не проверяет, какой сессии он был выдан.*

<a id="step5"></a>
## 🔍 Шаг 5 — Проверка эксплойта на себе
Разместил HTML в поле «Body» exploit-сервера, сохранил и нажал «View exploit». Убедился, что POST проходит с зашитым токеном и email меняется. Затем изменил адрес в эксплойте, чтобы он не совпадал с текущим.

⚠️ Если токен был израсходован при тестировании — запроси **свежий** (залогинься заново / открой страницу аккаунта) перед доставкой.

<a id="step6"></a>
## 🔍 Шаг 6 — Доставка эксплойта жертве
Сохранил эксплойт со свежим токеном и нажал «Deliver to victim». Email жертвы изменён → лаба решена.

<a id="requests"></a>
## 📨 Примеры запросов
**Легитимный запрос от wiener (со своим токеном)**
```http
POST /my-account/change-email HTTP/1.1
Host: LAB-ID.web-security-academy.net
Cookie: session=SESSION_WIENER
Content-Type: application/x-www-form-urlencoded

email=test@test.com&csrf=CSRF_TOKEN_WIENER
```

**Межсессионный тест: сессия carlos + токен wiener'а**
```http
POST /my-account/change-email HTTP/1.1
Host: LAB-ID.web-security-academy.net
Cookie: session=SESSION_CARLOS
Content-Type: application/x-www-form-urlencoded

email=test@test.com&csrf=CSRF_TOKEN_WIENER
```

<a id="response"></a>
## 📥 Пример результата
**Межсессионный тест токена**
- Сессия carlos + валидный токен wiener'а → 302 Redirect (успех)  
→ Токен принят, несмотря на то что выдан другой сессии

**Эксплойт**
- Сессия жертвы + зашитый токен атакующего → 302 Redirect (успех)  
→ Email изменён токеном, который никогда не выдавался жертве

<a id="attack-chain"></a>
## 🧾 Полная цепочка атаки
1. Логин под wiener → фиксация csrf-токена из `POST /my-account/change-email` (запрос сброшен).
2. Инкогнито → логин под carlos → Repeater → подстановка токена wiener'а → принято (токен не привязан к сессии).
3. Exploit Server → HTML-форма с зашитым токеном атакующего + автосабмит.
4. View exploit → проверка на себе → email изменён.
5. Обновление токена (одноразовый), смена email в эксплойте.
6. Deliver to victim → email жертвы изменён → **Solved**.

<a id="breakdown"></a>
## 🔬 Почему атака сработала
- **Токены не привязаны к сессии:** сервер хранит CSRF-токены в глобальном пуле; любой валидный токен принимается для любой сессии.
- **Атакующий — тоже пользователь:** сайт выдает настоящие токены аккаунту атакующего — похищение токена не требуется.
- **Нет привязки к контексту запроса:** ничто криптографически не связывает токен с сессией жертвы или конкретным действием.
- **Одноразовость не мешает:** атакующий всегда может получить свежий валидный токен непосредственно перед доставкой эксплойта.
- **Автосабмит:** JavaScript отправляет форму мгновенно, жертва не замечает атаки.

<a id="pentester"></a>
## 🧠 Как думать как пентестер
1. **Тестируйте токены между двумя своими аккаунтами:** если токен аккаунта A работает для аккаунта B, токены не привязаны к сессии.
2. **Спрашивайте: где хранятся токены?** Привязка к сессии vs глобальный пул определяет целый класс атак.
3. **Не нужно похищать токен жертвы:** если токены взаимозаменяемы, достаточно собственного.
4. **Следите за жизненным циклом токена:** одноразовые токены требуют свежего значения в момент доставки — не «сжигайте» его при тестировании.
5. **Минимизируйте эксплойт:** форма + скрытые инпуты + автосабмит — всё, что нужно.

<a id="mistakes"></a>
## ❌ Типичные ошибки
- **Израсходовали токен при тестировании:** токены одноразовые — если протестировать «View exploit» тем же токеном, он может быть сожжён; перед «Deliver to victim» возьмите свежий.
- **Попытки похитить токен жертвы:** здесь это не нужно — изъян в том, что любой валидный токен работает.
- **Переслали вместо сброса запрос на Шаге 1:** если запрос был отправлен, токен мог быть израсходован; по методичке значение нужно записать и сбросить запрос (drop).
- **Забыли сменить email в эксплойте:** если адрес совпадает с текущим, изменение не происходит.
- **Забыли автосабмит:** без `<script>` форма не отправится автоматически.

<a id="defense"></a>
## 🛡 Защита
- **Привязывать CSRF-токен к сессии пользователя** — хранить токен внутри объекта сессии и валидировать пару (сессия, токен).
- Предпочитать **посессионные токены**, производные от данных сессии (например, HMAC от session ID), а не глобальный пул.
- Использовать CSRF-защиту уровня фреймворка, привязывающую токены к сессиям по умолчанию.
- **SameSite-cookies** (Lax/Strict) как эшелонированная защита.
- Проверка заголовков **Origin/Referer** для запросов, изменяющих состояние.

<a id="conclusion"></a>
## 🧾 Итог
Лаба демонстрирует, что CSRF-токен является защитой только тогда, когда он привязан к сессии жертвы. Здесь токены живут в глобальном пуле: любой валидный токен принимается для любого пользователя, поэтому атакующий просто вшивает собственный токен в эксплойт. Ключевой урок: недостаточно проверять наличие и валидность токена — сервер должен удостовериться, что токен принадлежит именно сессии запрашивающего.
