<a id="goal"></a>
## 🎯 Цель
Функционал смены email защищён CSRF-токеном, но проверка токена выполняется **только для POST-запросов**. Задача:

1. Использовать exploit server для размещения HTML-страницы с CSRF-атакой.
2. Изменить email жертвы через CSRF.

*Подсказка: защита применяется только к определённым типам запросов.*

<a id="theory"></a>
## 🧠 Краткая теория
CSRF (Cross-Site Request Forgery) — атака, при которой злоумышленник заставляет браузер жертвы выполнить нежелательное действие на уязвимом сайте, где жертва аутентифицирована.

Стандартная защита — CSRF-токен, который должен присутствовать в каждом state-changing запросе. Однако если сервер проверяет токен только для POST, а GET-запросы обрабатывает без проверки, защита обходится простой сменой метода. GET-запрос легко инициировать через `<form method="GET">`, `<img>` или навигацию браузера — без каких-либо ограничений CORS.

<a id="idea"></a>
## 🧩 Ключевая идея
Смена метода POST → GET обходит проверку CSRF-токена.

- GET-запрос можно инициировать с любого домена через простую HTML-форму — браузер автоматически отправит cookies жертвы.
- Отсутствие токена в GET означает, что эксплойт не требует знания CSRF-токена жертвы.
- Автосабмит формы через JavaScript делает атаку незаметной для жертвы.

<a id="attack-scheme"></a>
## 🗺 Схема атаки
1. **Разведка:** Перехват `POST /my-account/change-email` с csrf-токеном.
2. **Проверка:** Изменение csrf → отказ (токен валидируется для POST).
3. **Обход:** Change request method → GET → токен не проверяется.
4. **Эксплойт:** HTML-форма `method="GET"` + автосабмит.
5. **Проверка:** View exploit на себе → email изменён.
6. **Доставка:** Deliver to victim → лаба решена.

<a id="step1"></a>
## 🔍 Шаг 1 — Анализ легитимного запроса
Авторизовался под `wiener:peter`, отправил форму «Update email» и перехватил запрос в Burp Proxy.

```http
POST /my-account/change-email HTTP/1.1
Host: LAB-ID.web-security-academy.net
Cookie: session=SESSION_COOKIE
Content-Type: application/x-www-form-urlencoded

email=test@test.com&csrf=CSRF_TOKEN
```

<a id="step2"></a>
## 🔍 Шаг 2 — Проверка валидации токена
Отправил запрос в Burp Repeater, изменил значение `csrf` на произвольное → сервер вернул ошибку. Токен проверяется для POST-запросов.

<a id="step3"></a>
## 🔍 Шаг 3 — Смена HTTP-метода
Через контекстное меню Repeater выбрал «Change request method» — запрос преобразовался в GET:

```http
GET /my-account/change-email?email=test@test.com&csrf=CSRF_TOKEN HTTP/1.1
Host: LAB-ID.web-security-academy.net
Cookie: session=SESSION_COOKIE
```
**Результат:** CSRF-токен больше не проверяется, email успешно изменяется даже при неверном/отсутствующем токене.

*Вывод: защита привязана к HTTP-методу, а не к самому действию.*

<a id="step4"></a>
## 🔍 Шаг 4 — Формирование CSRF-эксплойта
Поскольку GET-запрос можно инициировать простой формой (метод по умолчанию — GET), создал HTML для exploit-сервера:

```html
<form action="https://LAB-ID.web-security-academy.net/my-account/change-email">
   <input type="hidden" name="email" value="attacker@web-security-academy.net">
</form>
<script>
   document.forms[0].submit();
</script>
```
*Важно: параметр email уходит в query string, CSRF-токен не требуется.*

<a id="step5"></a>
## 🔍 Шаг 5 — Проверка эксплойта на себе
Разместил HTML в теле exploit-сервера, сохранил, нажал «View exploit». В Burp Proxy убедился, что запрос уходит как GET и email меняется. Затем изменил адрес в эксплойте, чтобы он не совпадал с текущим.

<a id="step6"></a>
## 🔍 Шаг 6 — Доставка эксплойта жертве
Сохранил эксплойт и нажал «Deliver to victim». Email жертвы изменён → лаба решена.

<a id="requests"></a>
## 📨 Примеры запросов
**Легитимный POST (с токеном)**
```http
POST /my-account/change-email HTTP/1.1
Host: LAB-ID.web-security-academy.net
Cookie: session=SESSION_COOKIE
Content-Type: application/x-www-form-urlencoded

email=test@test.com&csrf=CSRF_TOKEN
```

**Обход через GET (без проверки токена)**
```http
GET /my-account/change-email?email=attacker@web-security-academy.net HTTP/1.1
Host: LAB-ID.web-security-academy.net
Cookie: session=SESSION_COOKIE
```

<a id="response"></a>
## 📥 Пример результата
**Проверка валидации токена (POST)**
- POST с изменённым csrf → "Invalid CSRF token" (отказ)
- POST с корректным csrf → 302 Redirect (успех)

**Обход через GET**
- GET с неверным/отсутствующим csrf → 302 Redirect (успех)  
→ Email изменён без проверки токена

<a id="attack-chain"></a>
## 🧾 Полная цепочка атаки
1. `POST /my-account/change-email` → перехват, есть csrf-токен.
2. Repeater → изменение csrf → отказ (токен валидируется).
3. Change request method → GET → токен не проверяется.
4. Exploit Server → HTML-форма `method="GET"` + автосабмит.
5. View exploit → проверка на себе → email изменён.
6. Deliver to victim → email жертвы изменён → **Solved**.

<a id="breakdown"></a>
## 🔬 Почему атака сработала
- **Неравномерная защита:** CSRF-токен проверяется только для POST, GET обрабатывается без проверки.
- **Семантика HTTP нарушена:** GET используется для state-changing операции, хотя должен быть безопасным и идемпотентным.
- **GET легко инициировать cross-origin:** `<form method="GET">` не требует CORS-префлайта, cookies жертвы отправляются автоматически.
- **Автосабмит:** JavaScript отправляет форму мгновенно, жертва не замечает атаки.

<a id="pentester"></a>
## 🧠 Как думать как пентестер
1. **Проверяйте все HTTP-методы:** POST, GET, PUT, DELETE — защита может быть только на одном.
2. **Тестируйте Change request method:** частая ошибка — валидация привязана к методу.
3. **Ищите state-changing GET:** операции, меняющие состояние через GET, — красный флаг.
4. **Проверяйте удаление токена:** если токен можно убрать и запрос проходит — защита неполная.
5. **Используйте Exploit Server:** стандартный инструмент PortSwigger для CSRF-лаб.

<a id="mistakes"></a>
## ❌ Типичные ошибки
- **Забыли сменить email в эксплойте:** если адрес совпадает с текущим, изменение не происходит — лаба не засчитывается.
- **Использование POST в эксплойте:** форма по умолчанию GET, но если явно указать `method="POST"`, токен потребуется.
- **Не проверили на себе:** «View exploit» помогает убедиться, что запрос уходит как GET и email меняется.
- **Забыли автосабмит:** без `<script>` форма не отправится автоматически — жертва должна нажать кнопку.
- **Неверный URL лабы:** action должен указывать на реальный LAB-ID.

<a id="defense"></a>
## 🛡 Защита
- **Проверять CSRF-токен независимо от HTTP-метода** — валидация привязана к действию (endpoint), а не к типу запроса.
- **Не использовать GET** для state-changing операций — соблюдать семантику HTTP-методов.
- Применять фреймворки со встроенной CSRF-защитой, покрывающей все небезопасные методы.
- **SameSite-cookies** (Lax/Strict) как эшелонированная защита.
- Проверка **Origin/Referer** для запросов, изменяющих состояние.

<a id="conclusion"></a>
## 🧾 Итог
Лаба демонстрирует классическую ошибку: защитный механизм реализован неравномерно — только для одного HTTP-метода. Ключевой урок: безопасность действия не должна зависеть от способа его вызова — если endpoint меняет состояние, он должен быть защищён при любом методе. Смена POST на GET обошла CSRF-защиту, а простая HTML-форма с автосабмитом позволила изменить email жертвы.
