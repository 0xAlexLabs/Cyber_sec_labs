<a id="goal"></a>

## 🎯 Goal

Use UI redressing techniques to:

```text
1. Construct an HTML page that frames the target's account settings page.
2. Trick a logged-in user into clicking a decoy button ("Click me").
3. Force the user to unknowingly click the hidden "Delete account" button, bypassing CSRF protections.
```

<a id="theory"></a>

## 🧠 Short Theory
Clickjacking (UI redressing) is an attack where a malicious site frames a vulnerable application inside an iframe. The attacker makes the iframe transparent and overlays it on top of attractive or harmless-looking decoy elements. When the victim clicks the decoy, they are actually clicking on an actionable element within the hidden framed application.

Common clickjacking targets include:

```text
- Account deletion or password changes.
- Transferring funds or confirming purchases.
- Granting permissions (e.g., camera, microphone, OAuth).
- Modifying security settings.
```
Because the action is performed within the legitimate application's frame by the authenticated user's browser, traditional CSRF tokens are entirely useless against this attack.

<a id="idea"></a>

## 🧩 Core Idea
The target application generates a unique CSRF token for the "Delete account" form. However, because the application allows itself to be embedded in an iframe on any domain, an attacker can visually deceive the user into clicking the submit button. 

```text
Attacker site:      Renders a "Click me" button.
Hidden iframe:      Overlays the "Delete account" button exactly on top of "Click me".
Victim clicks:      Browser sends a POST request with the valid CSRF token generated by the framed page.
Target server:      Validates the CSRF token, verifies the session, and deletes the account ✅
```

<a id="clickjacking"></a>

## 📡 What Is Clickjacking and UI Redressing
Clickjacking manipulates the visual presentation of a web page (UI redressing). It relies on the browser's ability to layer elements using CSS properties like `z-index`, `position`, and `opacity`. The target site must lack framing protections (like `X-Frame-Options` or CSP `frame-ancestors`).

<a id="csrf"></a>

## 🌐 The Role of CSRF Tokens
CSRF tokens are designed to prevent Cross-Site Request Forgery, where an attacker forges a cross-domain request. 

Developers often assume:

```text
"If I implement robust Anti-CSRF tokens, state-changing actions are secure from cross-origin exploitation."
```
In reality, clickjacking completely circumvents CSRF tokens. Since the target application is loaded normally inside the iframe, the application itself injects the valid token into the form. The user's own click triggers the legitimate form submission.

<a id="iframe"></a>

## ⚡ The Invisible iframe Technique
To successfully trick the victim, the attacker must align the invisible target element with a visible decoy.

Key CSS properties used:

```text
- opacity: 0.0001 (Makes the iframe virtually invisible to the human eye, but fully clickable).
- z-index: 2 (Places the iframe above the decoy element which has z-index 1).
- position: absolute/relative (Allows precise pixel-perfect alignment of elements).
```

## 🧾 Complete Attack Chain
```text
1. Identify target sensitive action (Account deletion).
2. Verify target page can be framed (absence of X-Frame-Options/CSP).
3. Draft HTML payload with target site embedded in an iframe.
4. Overlay a decoy element beneath the target button using z-index.

```

<a id="breakdown"></a>

## 🔬 Why the Attack Worked
1. Lack of Framing Protections
The target application did not return `X-Frame-Options` or `Content-Security-Policy: frame-ancestors` headers, allowing any malicious domain to embed it.

2. Transparent Overlay
CSS layering (`z-index` and `opacity`) successfully decoupled the visual representation of the page from the functional click targets.

3. Legitimate Session Context
Because the iframe loads the page within the victim's browser context, all cookies and dynamically generated anti-CSRF tokens were automatically included and valid.

<a id="pentester"></a>

## 🧠 Pentester Mindset
When testing web applications for Clickjacking:

```text
Are sensitive pages (settings, transfers, deletions) frameable by external domains?
Are state-changing actions executed immediately on a single click without secondary confirmations (like a password prompt)?
Does the application rely solely on CSRF tokens while ignoring UI redressing vectors?
```

<a id="mistakes"></a>

## ❌ Common Mistakes
Mistake 1. Clicking the button during testing
If you click the button while calibrating the opacity, you will delete your own test account and will need to wait for the lab to reset.

Mistake 2. Using absolute URLs with user IDs
Including query parameters like `?id=wiener` in the iframe `src` will break the exploit if the victim's session does not match the ID. Always rely on the active session context.

Mistake 3. Misaligning the button
If the decoy text is not precisely under the clickable area of the target button, the victim's click will fall on a dead zone of the iframe.

<a id="defense"></a>

## 🛡 Mitigation
1. X-Frame-Options Header
Implement the legacy HTTP response header to prevent framing:
`X-Frame-Options: DENY` (disallow framing entirely) or `X-Frame-Options: SAMEORIGIN` (allow framing only by the same domain).

2. Content-Security-Policy (CSP)
Use modern CSP directives which override X-Frame-Options:
`Content-Security-Policy: frame-ancestors 'none';` (or specify trusted domains).

3. Defense in Depth: UI Requirements
For critical actions (like account deletion), require the user to re-enter their password or solve a CAPTCHA. Clickjacking cannot easily automate keyboard input.

<a id="conclusion"></a>

## 🧾 Conclusion
The lab demonstrated exploiting a Clickjacking (UI redressing) vulnerability:

```text
1. Proved that CSRF tokens are ineffective against clickjacking.
2. Constructed a malicious payload using CSS opacity and z-index positioning.
3. Successfully hijacked a victim's click to perform a critical state-changing action.
```

Main lessons:
```text
- CSRF tokens protect against forged requests, not visual deception.
- Applications must explicitly restrict framing via CSP or X-Frame-Options.
- Sensitive actions should incorporate defense-in-depth mechanisms like re-authentication.
```
