<a id="goal"></a>

## 🎯 Цель

Использовать техники UI redressing для:

```text
1. Создания HTML-страницы, которая встраивает страницу настроек аккаунта жертвы во фрейм.
2. Обмана авторизованного пользователя для нажатия на кнопку-приманку («Click me»).
3. Принуждения пользователя незаметно для него нажать на скрытую кнопку «Delete account», обходя защиту CSRF.
```

<a id="theory"></a>

## 🧠 Краткая теория
Clickjacking (UI redressing) — это атака, при которой вредоносный сайт встраивает уязвимое приложение внутрь iframe. Атакующий делает iframe прозрачным и накладывает его поверх привлекательных или безобидных элементов-приманок. Когда жертва кликает по приманке, на самом деле она кликает по активному элементу внутри скрытого приложения.

Типичные цели для кликджекинга:

```text
- Удаление аккаунта или смена пароля.
- Перевод средств или подтверждение покупок.
- Выдача разрешений (камера, микрофон, OAuth).
- Изменение настроек безопасности.
```
Поскольку действие выполняется внутри фрейма легитимного приложения авторизованным браузером пользователя, традиционные CSRF-токены абсолютно бесполезны против этой атаки.

<a id="idea"></a>

## 🧩 Ключевая идея
Целевое приложение генерирует уникальный CSRF-токен для формы удаления аккаунта. Однако, поскольку приложение позволяет встраивать себя в iframe на любом домене, атакующий может визуально обмануть пользователя и заставить его нажать кнопку отправки формы.

```text
Сайт атакующего:    Отображает кнопку «Click me».
Скрытый iframe:     Размещает кнопку «Delete account» ровно поверх «Click me».
Клик жертвы:        Браузер отправляет POST-запрос с валидным CSRF-токеном, сгенерированным на странице во фрейме.
Целевой сервер:     Проверяет CSRF-токен, валидирует сессию и удаляет аккаунт ✅
```

<a id="clickjacking"></a>

## 📡 Что такое Clickjacking и UI Redressing
Кликджекинг манипулирует визуальным представлением веб-страницы (UI redressing). Он опирается на возможности браузера наслаивать элементы друг на друга с помощью CSS-свойств, таких как `z-index`, `position` и `opacity`. Целевой сайт при этом не должен иметь защиты от встраивания (например, заголовков `X-Frame-Options` или CSP `frame-ancestors`).

<a id="csrf"></a>

## 🌐 Роль CSRF-токенов
CSRF-токены предназначены для защиты от подделки межсайтовых запросов (Cross-Site Request Forgery), когда атакующий формирует запрос с другого домена.

Разработчики часто исходят из ошибочного предположения:

```text
«Если я внедрю надежные Anti-CSRF токены, действия, изменяющие состояние, будут защищены от эксплуатации с других источников».
```
В реальности кликджекинг полностью обходит CSRF-токены. Так как целевое приложение нормально загружается внутри iframe, оно само внедряет валидный токен в форму. Собственный клик пользователя инициирует легитимную отправку этой формы.

<a id="iframe"></a>

## ⚡ Техника невидимого iframe
Чтобы успешно обмануть жертву, атакующий должен совместить невидимый целевой элемент с видимой приманкой.

Ключевые используемые CSS-свойства:

```text
- opacity: 0.0001 (Делает iframe практически невидимым для человеческого глаза, но полностью кликабельным).
- z-index: 2 (Размещает iframe поверх элемента-приманки, у которого z-index 1).
- position: absolute/relative (Позволяет выполнить точное попиксельное выравнивание элементов).
```

<a id="step1"></a>

## 🔍 Шаг 1 — Найти целевое действие
Авторизуйтесь в уязвимом приложении, используя предоставленные учетные данные (`wiener:peter`).

Перейдите на страницу `/my-account`.

Определите целевое действие: кнопка «Delete account».

<a id="step2"></a>

## 🔍 Шаг 2 — Создать базовый пейлоад
Откройте Exploit Server, предоставленный в лаборатории.

В секцию Body вставьте базовую HTML-структуру с таблицей стилей CSS, `<div>` приманкой и `<iframe>`, указывающим на целевой URL.

```html
<style>
    iframe {
        position:relative;
        width:500px;
        height: 700px;
        opacity: 0.1;
        z-index: 2;
    }
    div {
        position:absolute;
        top:500px;
        left:60px;
        z-index: 1;
    }
</style>
<div>Test me</div>
<iframe src="https://LAB-ID.web-security-academy.net/my-account"></iframe>
```

<a id="step3"></a>

## 🔍 Шаг 3 — Откалибровать элемент-приманку
Установите `opacity` у iframe на `0.1`, чтобы видеть одновременно и iframe, и текст приманки.

Нажмите **Store**, а затем **View exploit**.

Корректируйте значения пикселей `top` и `left` у `div`, пока слова «Test me» не окажутся идеально отцентрированными под кнопкой «Delete account».

*Осторожно: не нажимайте саму кнопку во время тестирования, иначе ваш тестовый аккаунт будет удален.*

<a id="step4"></a>

## 🔍 Шаг 4 — Скрыть целевой фрейм
Когда выравнивание станет идеальным, подготовьте финальную версию пейлоада для жертвы:

- Измените текст приманки с «Test me» на «Click me».
- Измените прозрачность iframe с `0.1` на `0.0001`.

<a id="step5"></a>

## 🔍 Шаг 5 — Отправить эксплойт жертве
Нажмите **Store**, чтобы сохранить финальный невидимый пейлоад.

Нажмите **Deliver exploit to victim**.

Бот, эмулирующий жертву, зайдет на ваш эксплойт, нажмет на кнопку-приманку и неосознанно инициирует удаление своего аккаунта.

## 🧾 Полная цепочка атаки
```text
1. Определение чувствительного целевого действия (удаление аккаунта).
2. Подтверждение возможности встраивания страницы во фрейм (отсутствие X-Frame-Options/CSP).
3. Создание HTML-пейлоада со встроенным целевым сайтом в iframe.
4. Размещение элемента-приманки под целевой кнопкой с использованием z-index.
5. Визуальная калибровка координат с помощью полупрозрачности (opacity: 0.1).
6. Установка opacity в 0.0001 для полного сокрытия фрейма.
7. Доставка размещенного HTML-пейлоада жертве.
8. Лаборатория помечена как Solved.
```

<a id="breakdown"></a>

## 🔬 Почему атака сработала
1. Отсутствие защиты от встраивания
Целевое приложение не отправляло заголовки `X-Frame-Options` или `Content-Security-Policy: frame-ancestors`, позволяя любому вредоносному домену встраивать себя.

2. Прозрачное наложение
CSS-наслаивание (`z-index` и `opacity`) успешно отделило визуальное представление страницы от фактических элементов, принимающих клик.

3. Легитимный контекст сессии
Поскольку iframe загружает страницу в контексте браузера жертвы, все cookie и динамически генерируемые Anti-CSRF токены были автоматически добавлены и признаны валидными.

## 🧠 Как думать как пентестер
При аудите веб-приложений на Clickjacking:

```text
Разрешено ли встраивание чувствительных страниц (настройки, переводы, удаления) внешним доменам?
Выполняются ли критические действия немедленно по одному клику без дополнительных подтверждений (например, ввода пароля)?
Полагается ли приложение исключительно на CSRF-токены, игнорируя векторы UI redressing?
```

<a id="mistakes"></a>

## ❌ Типичные ошибки
Ошибка 1. Нажатие на кнопку во время тестов
Если вы кликнете по кнопке во время калибровки прозрачности, вы удалите свой собственный тестовый аккаунт, и придется ждать перезапуска лаборатории.

Ошибка 2. Использование URL с жестко заданным ID
Включение параметров запроса вроде `?id=wiener` в `src` у iframe сломает эксплойт, если сессия жертвы не совпадает с этим ID. Всегда опирайтесь на активный контекст сессии (`/my-account`).

Ошибка 3. Неправильное выравнивание кнопки
Если текст-приманка находится не точно под кликабельной зоной целевой кнопки, клик жертвы придется на «мертвую» зону iframe.

<a id="defense"></a>

## 🛡 Защита
1. Заголовок X-Frame-Options
Реализуйте устаревший HTTP-заголовок для предотвращения встраивания:
`X-Frame-Options: DENY` (полностью запрещает встраивание) или `X-Frame-Options: SAMEORIGIN` (разрешает встраивание только на том же домене).

2. Content-Security-Policy (CSP)
Используйте современные директивы CSP, которые имеют приоритет над X-Frame-Options:
`Content-Security-Policy: frame-ancestors 'none';` (или укажите доверенные домены).

3. Глубокая защита: Требования к UI
Для критических действий (например, удаление аккаунта) требуйте от пользователя повторного ввода пароля или решения CAPTCHA. Кликджекинг не может с легкостью автоматизировать ввод с клавиатуры.

```text
- Критичные действия должны включать механизмы глубокой защиты, такие как повторная аутентификация.
```
