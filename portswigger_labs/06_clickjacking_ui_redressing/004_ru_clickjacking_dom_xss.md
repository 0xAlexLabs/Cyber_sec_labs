<a id="goal"></a>

## 🎯 Цель

Использовать техники UI redressing в качестве механизма доставки для атаки DOM-based Cross-Site Scripting (XSS):

```text
1. Использовать функцию предзаполнения формы для внедрения XSS-пейлоада в целевое поле.
2. Создать HTML-страницу, которая встраивает целевое приложение.
3. Обмануть авторизованного пользователя для нажатия на кнопку-приманку («Click me»).
4. Принудить пользователя незаметно нажать скрытую кнопку «Submit feedback», что вызовет выполнение внедренного XSS-пейлоада (вызов функции `print()`).
```

<a id="theory"></a>

## 🧠 Краткая теория
Хотя кликджекинг часто используется для выполнения действий, изменяющих состояние (например, удаление аккаунта), его истинная мощь раскрывается при связывании с другими уязвимостями. DOM XSS уязвимость может требовать взаимодействия с пользователем (например, отправки формы) для выполнения вредоносного пейлоада.

Обернув уязвимую страницу в оверлей кликджекинга, злоумышленник может заставить жертву выполнить именно то взаимодействие, которое необходимо для запуска XSS, фактически превращая XSS, зависящий от действий пользователя, в эксплойт в один клик.

<a id="idea"></a>

## 🧩 Ключевая идея
Форма «Submit feedback» целевого приложения уязвима к DOM XSS через параметр `name`. Однако XSS-пейлоад обрабатывается и выполняется только при отправке формы.

```text
Сайт атакующего:    Отображает кнопку «Click me».
Скрытый iframe:     Загружает форму обратной связи с XSS-пейлоадом, внедренным через GET-параметры URL.
Выравнивание:       Размещает кнопку «Submit feedback» ровно поверх «Click me».
Клик жертвы:        Браузер отправляет форму, обрабатывая вредоносный параметр `name`.
Целевой сервер:     DOM отражает XSS-пейлоад, выполняя `print()` ✅
```

<a id="combined"></a>

## 📡 Зачем комбинировать Clickjacking и XSS?
Иногда XSS-пейлоад не может быть выполнен автоматически при загрузке страницы (например, для него требуется событие `onclick`, отправка формы или определенный путь пользователя). Полагаться на социальную инженерию, чтобы убедить жертву ввести пейлоад и нажать кнопку отправки, ненадежно. Кликджекинг обеспечивает бесшовный, невидимый механизм доставки, который гарантирует, что жертва выполнит требуемое взаимодействие.

<a id="iframe"></a>

## ⚡ Механизм доставки
Злоумышленник использует стандартный CSS кликджекинга для сокрытия встроенного вектора XSS:

```text
- opacity: 0.0001 (Делает iframe практически невидимым для человеческого глаза, но полностью кликабельным).
- z-index: 2 (Размещает iframe поверх элемента-приманки, у которого z-index 1).
- position: absolute/relative (Позволяет выполнить точное попиксельное выравнивание элементов).
```

<a id="step1"></a>

## 🔍 Шаг 1 — Обнаружение DOM XSS уязвимости
Перейдите на страницу «Submit feedback» (`/feedback`).

Убедитесь, что поля формы могут быть предварительно заполнены с использованием параметров URL (например, `?name=test&email=test@test.com`).
Внедрите стандартный XSS-пейлоад в параметр `name`: `?name=<img src=1 onerror=print()>&email=hacker...`

Отправьте форму вручную, чтобы убедиться, что появляется диалоговое окно `print()`, подтверждая, что уязвимость DOM XSS срабатывает при отправке.

<a id="step2"></a>

## 🔍 Шаг 2 — Создание базового пейлоада
Откройте Exploit Server. В секцию Body вставьте базовую структуру HTML, встраивая целевой URL с вредоносным XSS-пейлоадом в параметре `name`.

```html
<style>
    iframe {
        position:relative;
        width:500px;
        height: 700px;
        opacity: 0.1;
        z-index: 2;
    }
    div {
        position:absolute;
        top:610px;
        left:80px;
        z-index: 1;
    }
</style>
<div>Test me</div>
<iframe src="https://LAB-ID.web-security-academy.net/feedback?name=<img src=1 onerror=print()>&email=hacker@attacker-website.com&subject=test&message=test#feedbackResult"></iframe>
```

<a id="step3"></a>

## 🔍 Шаг 3 — Калибровка элемента-приманки
Установите `opacity` у iframe на `0.1`.

Нажмите **Store**, а затем **View exploit**.

Корректируйте значения пикселей `top` и `left` у `div`, пока надпись «Test me» не окажется идеально отцентрированной под кнопкой **«Submit feedback»**.

*Примечание: Вы можете нажать «Test me» во время калибровки, чтобы убедиться, что появляется диалоговое окно печати.*

<a id="step4"></a>

## 🔍 Шаг 4 — Сокрытие целевого фрейма
Когда выравнивание станет идеальным, подготовьте финальную версию пейлоада для жертвы:

- Измените текст приманки с «Test me» на «Click me».
- Измените прозрачность iframe с `0.1` на `0.0001`.

<a id="step5"></a>

## 🔍 Шаг 5 — Отправка эксплойта жертве
Нажмите **Store**, чтобы сохранить финальный невидимый пейлоад.

Нажмите **Deliver exploit to victim**.

Браузер жертвы загрузит эксплойт, нажмет на кнопку-приманку и неосознанно запустит DOM XSS пейлоад.

<a id="attack-chain"></a>

## 🧾 Полная цепочка атаки
```text
1. Обнаружение уязвимости DOM XSS, требующей взаимодействия с пользователем (отправка формы).
2. Подтверждение, что уязвимая форма может быть предзаполнена через параметры URL.
3. Создание HTML-пейлоада, встраивающего целевой сайт с внедренным XSS-пейлоадом в URL.
4. Размещение элемента-приманки точно под целевой кнопкой отправки.
5. Визуальная калибровка координат с помощью полупрозрачности (opacity: 0.1).
6. Установка opacity в 0.0001 для полного сокрытия фрейма.
7. Доставка размещенного HTML-пейлоада жертве.
8. Клик жертвы инициирует выполнение XSS. Лаборатория помечена как Solved.
```

<a id="breakdown"></a>

## 🔬 Почему атака сработала
1. Отсутствие защиты от встраивания
Заголовки `X-Frame-Options` или `Content-Security-Policy: frame-ancestors` отсутствовали, позволяя встроить сайт.

2. Небезопасная обработка DOM
Приложение принимало пользовательский ввод из URL (параметр `name`) и небезопасно обрабатывало его в DOM при отправке формы, что сделало возможным XSS.

3. Синергетическая эксплуатация
Кликджекинг избавил от необходимости использовать социальную инженерию, заставив жертву выполнить именно то взаимодействие, которое требовалось для запуска XSS-уязвимости.

<a id="pentester"></a>

## 🧠 Как думать как пентестер
При аудите веб-приложений:

```text
Если я найду XSS-уязвимость, которая требует сложного взаимодействия с пользователем, могу ли я автоматизировать это взаимодействие с помощью Clickjacking?
Могу ли я использовать предзаполнение URL, чтобы пронести XSS-пейлоады в поля ввода, которые затем будут отправлены с помощью перехваченного клика?
```

<a id="mistakes"></a>

## ❌ Типичные ошибки
Ошибка 1. Неправильное URL-кодирование
Иногда сложные XSS-пейлоады (с пробелами или специальными символами) должны быть должным образом URL-кодированы при размещении в атрибуте `iframe src` для корректной работы.

Ошибка 2. Смещение кнопки-триггера
Если приманка выровнена с безопасной частью страницы, а не с фактической кнопкой отправки, клик жертвы не вызовет XSS.

<a id="defense"></a>

## 🛡 Защита
1. Блокировка встраивания (Нейтрализует Clickjacking)
Реализуйте `Content-Security-Policy: frame-ancestors 'none';` или `X-Frame-Options: DENY`, чтобы предотвратить встраивание приложения в iframe.

2. Санитизация и кодирование пользовательского ввода (Нейтрализует XSS)
Убедитесь, что все пользовательские данные, особенно данные, прочитанные из параметров URL, строго валидируются на стороне сервера и должным образом HTML-кодируются перед рендерингом или обработкой в DOM. Избегайте использования опасных DOM-стоков, таких как `innerHTML`.

Лаборатория продемонстрировала экспоненциальную опасность веб-уязвимостей при объединении Clickjacking с DOM XSS:

```text
1. Доказано, что Clickjacking — это высокоэффективный механизм доставки для эксплойтов, зависящих от взаимодействия пользователя.
```

```text

```
