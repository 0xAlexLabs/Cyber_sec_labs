<a id="goal"></a>

## 🎯 Цель

Использовать техники UI redressing для выполнения многошагового действия:

```text
1. Создать HTML-страницу, которая встраивает целевое приложение.
2. Обмануть авторизованного пользователя для нажатия на первую кнопку-приманку («Click me first»), чтобы инициировать запрос на удаление аккаунта.
3. Принудить пользователя нажать на вторую кнопку-приманку («Click me next»), чтобы нажать кнопку подтверждения «Yes» в модальном окне.
4. Обойти защиту приложения в виде CSRF-токена и диалогового окна подтверждения.
```

<a id="theory"></a>

## 🧠 Краткая теория
Разработчики часто предполагают, что добавление диалогового окна подтверждения (например, «Вы уверены, что хотите удалить аккаунт?») защитит критические действия от CSRF и Clickjacking. Однако **Многошаговый кликджекинг (Multistep Clickjacking)** доказывает ошибочность этого предположения.

Если злоумышленник может обманом заставить пользователя кликнуть один раз, он может заставить его кликнуть и дважды. Используя несколько стратегически расположенных элементов-приманок (тегов `div`) и режиссируя взаимодействие пользователя, атакующий может провести жертву через сложные многошаговые рабочие процессы.

<a id="idea"></a>

## 🧩 Ключевая идея
Атака основана на точном совмещении двух элементов-приманок с двумя функциональными кнопками в скрытом iframe.

```text
Сайт атакующего:    Отображает кнопки «Click me first» и «Click me next».
Скрытый iframe:     Загружает страницу настроек аккаунта.
Клик 1:             Жертва нажимает «Click me first», попадая по невидимой кнопке «Delete account».
Появление окна:     Целевое приложение открывает окно подтверждения «Yes/No» внутри скрытого фрейма.
Клик 2:             Жертва нажимает «Click me next», попадая по только что появившейся невидимой кнопке «Yes».
Целевой сервер:     Удаляет аккаунт ✅
```

<a id="dialogs"></a>

## 📡 Почему окна подтверждения не работают
Окна подтверждения предназначены для предотвращения случайных кликов, а не злонамеренного встраивания. Поскольку диалоговое окно рендерится предсказуемо в DOM приложения, его размеры и расположение кнопок статичны. Эта предсказуемость позволяет атакующему заранее идеально вычислить координаты кнопки «Yes».

<a id="iframe"></a>

## ⚡ Механика многошаговой атаки
Злоумышленник использует стандартный CSS кликджекинга, но вместо одной приманки создает несколько перекрывающихся классов:

```text
- opacity: 0.0001 (Скрывает весь iframe, включая последующие модальные окна).
- z-index: 2 (Размещает iframe поверх элементов-приманок).
- .firstClick, .secondClick (Отдельные CSS-классы для независимого управления позиционированием каждой приманки).
```

<a id="step1"></a>

## 🔍 Шаг 1 — Изучение поведения цели
Авторизуйтесь в уязвимом приложении (`wiener:peter`).

Перейдите на `/my-account`. Нажмите кнопку «Delete account» и обратите внимание на появившееся модальное окно. Запомните расположение кнопки «Yes». Нажмите «No» для отмены.

<a id="step2"></a>

## 🔍 Шаг 2 — Создание базового пейлоада
Откройте Exploit Server. Вставьте структуру HTML с двумя элементами-приманками (`.firstClick` и `.secondClick`).

```html
<style>
    iframe {
        position:relative;
        width:500px;
        height: 700px;
        opacity: 0.1;
        z-index: 2;
    }
    .firstClick {
        position:absolute;
        top:330px;
        left:50px;
        z-index: 1;
    }
    .secondClick {
        position:absolute;
        top:285px;
        left:225px;
        z-index: 1;
    }
</style>
<div class="firstClick">Test me first</div>
<div class="secondClick">Test me next</div>
<iframe src="https://LAB-ID.web-security-academy.net/my-account"></iframe>
```

<a id="step3"></a>

## 🔍 Шаг 3 — Калибровка первого действия
Установите `opacity` у iframe на `0.1`.

Нажмите **Store**, а затем **View exploit**. Корректируйте значения пикселей `top` и `left` для `.firstClick`, пока надпись «Test me first» не окажется идеально отцентрированной под кнопкой **«Delete account»**.

<a id="step4"></a>

## 🔍 Шаг 4 — Калибровка второго действия (Подтверждение)
Находясь на странице «View exploit», нажмите на полупрозрачную кнопку «Delete account» (через приманку «Test me first»), чтобы вызвать диалоговое окно подтверждения.

Теперь скорректируйте значения `top` и `left` для `.secondClick`, пока надпись «Test me next» идеально не совпадет с кнопкой **«Yes»** в появившемся модальном окне.

<a id="step5"></a>

## 🔍 Шаг 5 — Отправка эксплойта жертве
Как только оба шага будут идеально выровнены, подготовьте финальный пейлоад:

- Измените «Test me first» на «Click me first».
- Измените «Test me next» на «Click me next».
- Измените прозрачность iframe с `0.1` на `0.0001`.

Нажмите **Store**, а затем **Deliver exploit to victim**.


<a id="attack-chain"></a>

## 🧾 Полная цепочка атаки
```text
1. Определение многошагового критического действия (Удаление -> Подтверждение).
2. Создание HTML-пейлоада с несколькими элементами-приманками.
3. Выравнивание первой приманки под основной кнопкой действия.
4. Взаимодействие с полупрозрачным фреймом для отображения второго шага (окна подтверждения).
5. Выравнивание второй приманки под кнопкой подтверждения.
6. Установка opacity в 0.0001, чтобы сделать последовательность невидимой.
7. Доставка размещенного HTML-пейлоада жертве.
8. Жертва прокликивает последовательность, успешно завершая атаку.
```

<a id="breakdown"></a>

## 🔬 Почему атака сработала
1. Отсутствие защиты от встраивания
Заголовки `X-Frame-Options` или `Content-Security-Policy: frame-ancestors` отсутствовали.

2. Предсказуемый UI поток
Модальное окно появлялось по точным, предсказуемым координатам в пикселях, что позволило злоумышленнику надежно запрограммировать второй клик.

3. Неэффективная защита
Разработчик ошибочно полагал, что добавление CSRF-токена и диалогового окна подтверждения смягчит несанкционированные действия. Кликджекинг по своей природе обходит и то, и другое.

<a id="pentester"></a>

## 🧠 Как думать как пентестер
При аудите веб-приложений:

```text
Никогда не предполагайте, что двухэтапный процесс (например, оформление заказа в корзине или подтверждение удаления) защищен от кликджекинга.
Если элементы пользовательского интерфейса расположены предсказуемо, злоумышленник может связать в цепочку произвольное количество кликов.
```

<a id="mistakes"></a>

## ❌ Типичные ошибки
Ошибка 1. Слишком быстрый клик при тестировании
Если вы нажмете кнопку «Yes» во время калибровки `.secondClick`, вы удалите свой собственный тестовый аккаунт, и вам придется сбросить лабораторию.

Ошибка 2. Переменные размеры экрана
В реальном сценарии, если целевое приложение использует адаптивный дизайн (CSS Flexbox/Grid), где позиции модальных окон меняются в зависимости от размера экрана, многошаговую атаку становится гораздо сложнее осуществить надежно на разных устройствах. (В этой лаборатории макет статичен).

<a id="defense"></a>

## 🛡 Защита
1. Блокировка встраивания (Основная защита)
Реализуйте `Content-Security-Policy: frame-ancestors 'none';` или `X-Frame-Options: DENY`. Это единственное надежное решение.

2. Out-of-Band подтверждение
Вместо простого модального окна «Да/Нет» требуйте внеполосное подтверждение (например, переход по ссылке, отправленной на электронную почту, или ввод 2FA-токена) для деструктивных действий.

3. Frame Busting (Не рекомендуется)
Не полагайтесь на скрипты frame busters или простые модальные окна подтверждения как на основную линию защиты.

## 🧾 Итог
Лаборатория продемонстрировала, что многошаговые рабочие процессы не защищают от кликджекинга:

```text

```

Главные выводы:
```text
- Злоумышленники могут срежиссировать сложные взаимодействия пользователей с помощью невидимого UI redressing.
- Глубокая защита требует фактической повторной аутентификации или надежных HTTP-заголовков против встраивания, а не просто дополнительных кликов.
```
