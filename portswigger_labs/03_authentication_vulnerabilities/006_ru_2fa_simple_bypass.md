<a id="goal"></a>

## 🎯 Цель

Получить доступ к странице аккаунта пользователя `carlos`, имея его правильные логин и пароль, но не имея кода двухфакторной аутентификации.

Данные для входа:

```text
Свой аккаунт:
wiener:peter

Аккаунт жертвы:
carlos:montoya
```

---

<a id="theory"></a>

## 🧠 Краткая теория

**Двухфакторная аутентификация (2FA)** требует два разных подтверждения личности:

```text
1. Пароль — то, что пользователь знает
2. Код — то, что пользователь получает на устройство
```

Правильная логика:

```text
Пароль верный
        ↓
Ввод кода 2FA
        ↓
Код верный
        ↓
Доступ к аккаунту
```

В этой лаборатории сервер допускает ошибку: после проверки пароля он уже считает пользователя вошедшим и не проверяет прохождение 2FA при открытии страницы аккаунта.

---

<a id="idea"></a>

## 🧩 Ключевая идея

После ввода логина и пароля приложение перенаправляет пользователя на страницу ввода кода 2FA.

Но вместо ввода кода можно вручную перейти на:

```text
/my-account
```

Если сервер показывает страницу аккаунта, значит второй фактор проверяется только в интерфейсе, но не проверяется сервером при доступе к защищённой странице.

Схема атаки:

```text
carlos:montoya
        ↓
Страница ввода кода 2FA
        ↓
Ручной переход на /my-account
        ↓
Доступ к аккаунту Carlos
```

<a id="steps"></a>

## 🔍 Пошаговое решение

### Шаг 1 — Войти в свой аккаунт

Вводим:

```text
Username: wiener
Password: peter
```

Код 2FA приходит в почтовый клиент лаборатории.

После ввода кода открываем страницу аккаунта и смотрим её URL:

```text
/my-account
```

Это защищённая страница, которую мы позже попробуем открыть без прохождения второго фактора.

---

### Шаг 2 — Выйти из своего аккаунта

Нажимаем `Log out`, чтобы завершить текущую сессию.

---

### Шаг 3 — Войти под пользователем Carlos

Вводим:

```text
Username: carlos
Password: montoya
```

Пароль принимается, после чего приложение просит ввести код 2FA.

Но доступа к почте Carlos у нас нет.

---

### Шаг 4 — Пропустить страницу 2FA

Не вводим код.

В адресной строке вручную меняем URL на:

```text
/my-account
```

---

### Шаг 5 — Проверить результат

Страница успешно открывается и показывает:

```text
My Account

Your username is: carlos
Your email is: carlos@carlos-montoya.net
```

Это подтверждает, что доступ к аккаунту получен без кода 2FA.

Лаборатория решена.

---

<a id="breakdown"></a>

## 🔬 Почему атака сработала

После проверки правильного пароля сервер уже создал действующую сессию пользователя Carlos.

Уязвимая логика могла выглядеть так:

```python
if username_and_password_are_correct:
    create_authenticated_session()
    redirect_to_2fa_page()
```

Страница `/my-account` проверяла только наличие сессии:

```python
if user_has_session:
    show_account_page()
```

Но сервер не проверял отдельный признак:

```text
2FA completed = true
```

Поэтому второй этап удалось просто пропустить.

Правильная реализация должна создавать полноценную авторизованную сессию только после успешной проверки кода 2FA.

<a id="pentester"></a>

## 🧠 Как думать как пентестер

При встрече с многоэтапной аутентификацией не нужно сразу пытаться подобрать код.

Сначала стоит проверить:

```text
Можно ли пропустить этот шаг?
```

Полезный порядок действий:

```text
1. Узнать URL защищённой страницы.
2. Ввести правильный логин и пароль.
3. Остановиться на странице 2FA.
4. Вручную открыть защищённую страницу.
5. Проверить, требует ли сервер подтверждение второго фактора.
```

Главный урок:

```text
Наличие страницы с кодом 2FA ещё не означает,
что сервер действительно требует прохождение 2FA.
```

<a id="mistakes"></a>

## ❌ Типичные ошибки

### 1. Сразу пытаться подобрать код

В этой лаборатории код подбирать не нужно. Второй этап можно полностью пропустить.

### 2. Не узнать URL страницы аккаунта

Сначала полезно войти в свой аккаунт и посмотреть адрес защищённой страницы.

### 3. Проверять только интерфейс

Браузер показывает форму 2FA, но это ещё не доказывает, что сервер блокирует доступ к другим страницам.

### 4. Не различать аутентификацию и интерфейс

Безопасность должна обеспечиваться серверной проверкой, а не только последовательностью страниц в браузере.

<a id="defense"></a>

## 🛡 Защита

Правильная защита должна включать:

- временную ограниченную сессию после ввода пароля;
- отдельный серверный признак успешного прохождения 2FA;
- проверку этого признака при каждом запросе к защищённым страницам;
- создание полноценной сессии только после правильного кода;
- запрет доступа к `/my-account`, `/admin` и API до завершения 2FA;
- перенаправление непройденного пользователя обратно на страницу ввода кода.

Правильная логика:

```text
Пароль верный
        ↓
Временная сессия
        ↓
Код 2FA верный
        ↓
Полная авторизованная сессия
        ↓
Доступ к /my-account
```
