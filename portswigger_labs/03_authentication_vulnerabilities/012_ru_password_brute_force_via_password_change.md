## 🎯 Цель лаборатории

Получить доступ к аккаунту пользователя `carlos`, используя уязвимую функцию смены пароля.

Исходные данные:

```text
Собственная учётная запись: wiener:peter
Целевая учётная запись: carlos
```

Для решения необходимо:

- войти как `wiener`;
- изучить форму смены пароля;
- определить, что имя пользователя передаётся клиентом;
- найти различие в сообщениях при правильном и неправильном текущем пароле;
- превратить функцию смены пароля в password oracle;
- перебрать кандидатные пароли Carlos через Burp Intruder;
- определить правильный пароль;
- войти в аккаунт Carlos.

---

## 🧠 Что нужно знать

Функция смены пароля обычно принимает:

```text
текущий пароль
новый пароль
повтор нового пароля
```

На стороне сервера должны выполняться как минимум четыре проверки:

```text
1. Пользователь должен быть аутентифицирован.
2. Целевой аккаунт должен определяться по текущей сессии.
3. Текущий пароль должен совпадать с паролем этого аккаунта.
4. Два новых пароля должны совпадать.
```

Критически важно, чтобы сервер не позволял клиенту самостоятельно выбирать аккаунт, для которого выполняется проверка пароля.

## 🔐 Как должна работать безопасная смена пароля

Безопасная логика:

```text
Активная сессия
      |
      v
Сервер определяет пользователя
      |
      v
Проверяет текущий пароль
      |
      v
Проверяет совпадение новых паролей
      |
      v
Меняет пароль
```

Концептуальный безопасный код:

```python
user = session.authenticated_user

if not verify_password(user, current_password):
    return generic_error()

if new_password_1 != new_password_2:
    return generic_error()

change_password(user, new_password_1)
```

Сервер не должен использовать клиентский параметр:

```python
username = request.form["username"]
```

для определения аккаунта, пароль которого проверяется.

## 💥 Суть уязвимости

В лаборатории запрос содержит параметр:

```text
username=wiener
```

Хотя пользователь уже аутентифицирован через session-cookie.

Это означает, что приложение доверяет имени пользователя, переданному клиентом. После замены:

```text
username=wiener
```

на:

```text
username=carlos
```

сервер начинает проверять текущий пароль Carlos, несмотря на то что сессия принадлежит Wiener.

Одновременно приложение возвращает разные сообщения для разных состояний:

```text
Current password is incorrect
```

и:

```text
New passwords do not match
```

Это позволяет определять правильность проверяемого пароля.

## 🧩 Password Oracle

Оракулом называют систему, которая не раскрывает секрет напрямую, но позволяет делать выводы о нём по ответам.

В этой лаборатории приложение работает как password oracle.

Неверный пароль:

```text
current-password=wrong
new-password-1=123
new-password-2=abc

→ Current password is incorrect
```

Верный пароль:

```text
current-password=correct
new-password-1=123
new-password-2=abc

→ New passwords do not match
```

Логика атаки:

```text
Кандидатный пароль
        |
        v
Сервер проверяет его для Carlos
        |
        +--> Current password is incorrect
        |        Пароль неверный
        |
        +--> New passwords do not match
                 Пароль правильный
```

Важно, что два новых пароля намеренно задаются разными. Это не позволяет фактически изменить пароль Carlos, но сохраняет различие в ответах.

## ⚠️ Почему hidden-поля нельзя считать доверенными

HTML может содержать:

```html
<input type="hidden" name="username" value="wiener">
```

Поле скрыто только визуально. Оно по-прежнему полностью контролируется клиентом.

Атакующий может изменить его:

- через Burp Repeater;
- через Burp Intruder;
- через браузерные DevTools;
- собственным HTTP-клиентом;
- скриптом.

Главное правило:

```text
Hidden ≠ trusted
```

Любые данные из HTTP-запроса считаются недоверенными.

## 🎯 Проверка Carlos через Repeater

Отправляем запрос в Burp Repeater и изменяем только `username`:

```http
POST /my-account/change-password HTTP/2
Host: 0a83009103a9f078856b4164007100a6.web-security-academy.net
Cookie: session=SB4VMOJ7I5hUfMs1UBFImebala9rGAd8
Content-Type: application/x-www-form-urlencoded

username=carlos&current-password=peter&new-password-1=123&new-password-2=abc
```

Ответ:

```text
Current password is incorrect
```

Это ожидаемо, поскольку `peter` — пароль Wiener.

Главный вывод состоит не в тексте ошибки, а в том, что сервер принял `username=carlos` и начал проверять пароль чужого аккаунта.

## 🚀 Настройка Burp Intruder

Отправляем запрос в Intruder.

### 1. Attack type

Выбираем:

```text
Sniper
```

Поскольку перебирается один параметр.

### 2. Payload position

Очищаем автоматически созданные позиции:

```text
Clear §
```

Добавляем payload только в `current-password`:

```http
username=carlos&current-password=§peter§&new-password-1=123&new-password-2=abc
```

Параметры новых паролей должны оставаться разными:

```text
new-password-1=123
new-password-2=abc
```

### 3. Payload type

В разделе Payloads выбираем:

```text
Simple list
```

Вставляем список кандидатных паролей.

### 4. Grep - Match

В Settings добавляем правило:

```text
New passwords do not match
```

Эта строка будет помечать запрос, в котором текущий пароль оказался правильным.

## ⚙️ Почему атака сработала

Уязвимость возникла из-за сочетания нескольких ошибок.

### 1. Клиент выбирает целевой аккаунт

Приложение доверяет:

```text
username=carlos
```

вместо определения пользователя из сессии.

### 2. Нет корректной проверки авторизации

Сессия Wiener позволяет взаимодействовать с логикой проверки пароля Carlos.

### 3. Разные ошибки раскрывают внутреннее состояние

Ответы сообщают, на каком этапе остановилась обработка.

### 4. Нет эффективной защиты от brute force

Можно отправить множество попыток проверки текущего пароля.

### 5. Логика проверок создаёт oracle

Различие между двумя сообщениями позволяет отличить верный пароль от неверного.

Концептуально уязвимый код:

```python
username = request.form["username"]
current_password = request.form["current-password"]
new_password_1 = request.form["new-password-1"]
new_password_2 = request.form["new-password-2"]

if not verify_password(username, current_password):
    return "Current password is incorrect"

if new_password_1 != new_password_2:
    return "New passwords do not match"

change_password(username, new_password_1)
```

## 🧠 Как мыслить как пентестер

При проверке функции смены пароля задавай вопросы:

- Откуда сервер получает имя пользователя?
- Можно ли изменить `username`, `user_id`, `email` или `account_id`?
- Привязана ли операция к текущей сессии?
- Проверяется ли принадлежность аккаунта?
- Различаются ли сообщения для верного и неверного пароля?
- Различаются ли HTTP status code?
- Различается ли длина ответа?
- Есть ли разница во времени ответа?
- Можно ли отправлять большое число запросов?
- Есть ли rate limiting?
- Есть ли блокировка?
- Можно ли обойти блокировку разными новыми паролями?
- Изменяется ли пароль случайно при успешном подборе?
- Требуется ли повторная аутентификация?
- Инвалидируются ли старые сессии?

Общий подход:

```text
Не смотреть только на форму.
Нужно анализировать серверную бизнес-логику.
```

## 🛑 Типичные ошибки

### Ошибка 1. Перебирать пароль на странице входа

Лаборатория уязвима именно через функцию смены пароля.

### Ошибка 2. Оставить username=wiener

В этом случае Intruder будет подбирать пароль собственной учётной записи.

Правильно:

```text
username=carlos
```

### Ошибка 3. Сделать новые пароли одинаковыми

Опасный вариант:

```text
new-password-1=123
new-password-2=123
```

При правильном текущем пароле пароль Carlos действительно изменится.

Правильно:

```text
new-password-1=123
new-password-2=abc
```

### Ошибка 4. Добавить payload во все параметры

Payload нужен только в:

```text
current-password
```

### Ошибка 5. Искать ответ по длине без необходимости

В этой лаборатории надёжнее использовать точную строку:

```text
New passwords do not match
```

### Ошибка 6. Не очистить автоматические позиции

Burp может отметить дополнительные значения. Их нужно удалить.

### Ошибка 7. Не выйти из аккаунта Wiener

После получения пароля необходимо завершить текущую сессию и войти как Carlos.

### Ошибка 8. Считать hidden-параметр безопасным

Hidden-поля полностью контролируются клиентом.

## 🛡 Как исправить уязвимость

### 1. Определять пользователя из сессии

Правильно:

```python
user = session.authenticated_user
```

Неправильно:

```python
user = request.form["username"]
```

### 2. Не передавать username в форме без необходимости

Если операция относится к текущему пользователю, параметр `username` вообще не нужен.

### 3. Использовать единое сообщение об ошибке

Например:

```text
Unable to change password
```

Сообщение не должно раскрывать, какая именно проверка не пройдена.

### 4. Применять rate limiting

Ограничивать количество попыток:

- на аккаунт;
- на сессию;
- на IP;
- на устройство;
- на временной интервал.

### 5. Добавить progressive delays

После неудачных попыток увеличивать задержку ответа.

### 6. Использовать повторную аутентификацию

Для чувствительных операций можно потребовать повторный ввод пароля или MFA.

### 7. Логировать аномальное поведение

Признаки атаки:

- много запросов смены пароля;
- большое количество неверных текущих паролей;
- одна сессия проверяет разные аккаунты;
- высокая частота запросов;
- повторяющиеся несовпадающие новые пароли.

### 8. Не полагаться только на блокировку аккаунта

Жёсткая блокировка может использоваться для denial of service.

### 9. Инвалидировать другие сессии после смены пароля

После успешной смены пароля активные сессии желательно завершить или предложить пользователю сделать это.

### 10. Защищать операцию CSRF-механизмом

Функция смены пароля должна использовать CSRF-токен, хотя CSRF сам по себе не устраняет обнаруженную уязвимость авторизации.

## 🧾 Итог

Приложение позволило клиенту выбирать аккаунт через параметр `username` в функции смены пароля.

Сервер не связывал операцию с пользователем текущей сессии и возвращал разные сообщения для правильного и неправильного текущего пароля.

Несовпадающие новые пароли превратили функцию в password oracle:

```text
Current password is incorrect
→ кандидат неверный
```

```text
New passwords do not match
→ кандидат правильный
```

Через Burp Intruder был найден пароль:

```text
159753
```

После этого выполнен вход:

```text
carlos:159753
```

Главные выводы:

```text
Нельзя доверять username из клиентского запроса.
```

```text
Чувствительные операции должны быть привязаны к текущей сессии.
```

```text
Разные сообщения об ошибках могут раскрывать секретное состояние.
```
